# 菜谱导入、补全、营养与健康规划总执行计划

## 一、文档状态

本文用于汇总菜谱导入、后台补全、营养分析与健康规划这条线的总执行顺序。

当前阶段结论：

1. 先把规定确认完，再按计划分阶段推进。
2. 当前只冻结阶段、依赖和门禁，不进入实现。
3. 本计划是路线图，不替代每个阶段的独立执行单。

## 二、目标

这条线的长期目标是形成稳定闭环：

```text
菜谱创建/导入 -> 数据补全 -> 质量校对 -> 营养分析 -> 健康规划 -> 计划与购物联动
```

## 三、总原则

1. 先定规则，再做实现。
2. 先稳正文事实，再做派生层。
3. 先做高频食材和最小字段集，再扩覆盖面。
4. 先做规则型健康能力，再考虑更复杂的 AI 能力。
5. 当前不把这条线插入现有创建主流程。

## 四、阶段划分

### 阶段 0：规则冻结

目标：

1. 统一创建、导入、补全、营养、健康规划的边界
2. 为后续实施提供明确前置条件

产出：

1. `recipe-data-completion-rules.md`
2. `recipe-nutrition-mapping-rules.md`
3. `recipe-import-review-workbench-rules.md`
4. 本总执行计划

门禁：

1. 关键待确认项全部收口
2. 文档入口和中央变更记录完成

### 阶段 1：导入基础链路

目标：

1. 跑通“网页/后台导入 -> 导入草稿 -> 人工校对 -> 发布”

范围：

1. 导入草稿结构
2. 导入解析状态
3. 单条校对工作台
4. 发布门禁

不做：

1. 营养基表导入
2. 健康规划
3. 复杂批量规则

前置：

1. 阶段 0 完成

### 阶段 2：后台补全与质量状态

目标：

1. 对导入后菜谱补充标签、缺失项、置信度和质量状态

范围：

1. 标签候选生成
2. `completionStatus / missingFields / confidence / needsReview`
3. 质量状态存储与读取

不做：

1. 用户可编辑健康标签
2. 精细营养计算

前置：

1. 阶段 1 完成

### 阶段 3：营养基表与映射

目标：

1. 建立高频系统食材到营养基表的稳定映射

范围：

1. 营养基表底稿层
2. 标准营养基表层
3. `ingredientId -> nutrientFoodId` 映射
4. 常用单位与包装单位换算规则

不做：

1. 全量长尾食材一次性接入
2. 品牌 SKU 级营养

前置：

1. 阶段 0 完成
2. 阶段 2 的质量状态口径稳定

### 阶段 4：菜谱营养分析

目标：

1. 为菜谱详情页输出最小营养结果

范围：

1. `estimatedCalories`
2. `protein`
3. `fat`
4. `carbohydrate`
5. `perRecipe / perServing`
6. 结果文案三档

不做：

1. 医疗级建议
2. 复杂人群个性化饮食方案

前置：

1. 阶段 3 完成

### 阶段 5：规则型健康规划

目标：

1. 在稳定营养结果基础上，增加轻量健康目标与筛选

范围：

1. 高蛋白候选
2. 轻负担晚餐候选
3. 控糖谨慎提示
4. 基础过敏原避让
5. 与计划页的轻筛选联动

不做：

1. AI 饮食教练
2. 复杂慢病个性化方案
3. 厨电联动

前置：

1. 阶段 4 完成

## 八、阶段完成判断

### 8.1 当前阶段完成标准

当前阶段完成，需满足：

1. 三份规则稿和总执行计划都存在
2. 索引已更新
3. 变更记录已更新
4. 文档内的关键待确认项已单独列出，后续可继续收口

### 8.2 后续阶段开工条件

任何后续阶段开始前，都必须先确认：

1. 上游阶段规则已经冻结
2. 本阶段 owner 清楚
3. 本阶段范围和非目标清楚
4. 不会顺手扩张到当前未确认能力

## 九、当前不做

当前总计划明确不提前建设：

1. AI 对话营养师
2. OCR 识别小票或食物照片
3. 智能厨电联动
4. 零售配送打通
5. 医疗级饮食建议

## 十、待确认项

后续默认按以下口径推进；真正开工前如遇阶段依赖或范围冲突，再针对具体项复核：

1. 健康标签第一版是否完全只读
2. 导入校对工作台是否区分个人导入与后台导入两条路径
3. 营养映射中“代表值”进入正式映射的边界
4. 个人食材何时进入正式营养映射主链路
