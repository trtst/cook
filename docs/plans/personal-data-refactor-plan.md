# 个人数据与饭搭子关系重构计划

> 历史说明：饭搭子功能已于 2026-08-19 下线，本文记录的是已失效的重构方向，只保留历史追溯价值，不再作为当前产品、接口、数据库或客户端实现依据。

## 状态

- 产品规则：已入档。
- 计划状态：工程基础改造已实施；业务模块仍需按功能执行单逐项确认和真实验收。菜谱后续以 `recipe-execution.md` 为准，菜谱图片、背景图上传与资产管理延期。
- 项目阶段：未上线，允许直接替换旧业务模型，不建设兼容层。
- 权威输入：`../dining-group.md`、`../recipe.md`、`../ingredient.md`、`../configuration.md`、`../decision.md`。

## 一、目标

把现有“唯一饭搭子共享空间”重构为：

```text
个人数据
+ 多饭搭子成员关系
+ 个人四档会员
+ 饭局级协作
```

重构完成后：

1. 用户最多主理一个饭搭子，并可按本人套餐加入多个饭搭子。
2. 加入和退出不再冻结、切换、迁移或恢复个人数据。
3. 菜谱、冰箱、计划、饭局和购物清单直接归个人。
4. 菜谱导入支持固定基础版本和字段级覆盖；图片独立化保留为后续上传契约。
5. 会员只保留个人 Free、Plus、Pro、Ultra。
6. 饭搭子人数超额时只允许查看和减少关系。

## 二、实施原则

1. 不兼容旧业务：删除旧状态和旧接口，不双写、不保留 fallback 字段。
2. 保留迁移历史：创建新的前向 migration，不改写已有 migration 和 `docs/cook/`。
3. 最小纵切：每阶段形成一条可验证主链，不按表、页面或 DTO 过度拆任务。
4. 契约先行：每阶段先冻结对象、状态、接口和错误语义，再同步三端。
5. 服务端权威：所有权、成员额度、套餐、超额和内容状态均由服务端校验。
6. 数据可重算：成员数量、菜谱数量和空间账本都必须可由主事实重算。
7. 暂不扩范围：不同时引入主理人转让、共享冰箱、共享购物、OCR、AI 或通用权限中心。

## 三、保留与替换

### 保留

- Auth、User、用户口味资料。
- 统一响应、鉴权 Guard、DTO 校验、幂等、审计和 Outbox 基础。
- uni-app 平台适配层、请求层和会话清理规则。
- Admin 登录与只读查询基础。
- PostgreSQL、Prisma、NestJS 和现有扁平模块边界。

### 替换

- `UserSpace` 和唯一 `currentDiningGroupId`。
- `DiningGroup.FROZEN`、原空间冻结和恢复。
- `CarryBackSnapshot` 及迁入迁出接口。
- 饭搭子级 `EntitlementGrant` 和个人/饭搭子 Plus 合并解析。
- 客户端 `currentSpace`、`originalSpace` 和唯一饭搭子 Store。
- 后台饭搭子空间权益和冻结状态展示。

## 四、实施阶段

### 阶段一：关系与个人权益基础

这是第一条必须完整跑通的纵切，不并行建设菜谱、饭局和购物。

#### 契约

冻结以下操作的请求、响应、错误和权限语义：

1. 查询本人主理和加入的饭搭子。
2. 查询某个有效饭搭子的成员。
3. 创建邀请、接受邀请、主动退出、主理人移除成员和主理人直接解散饭搭子。
4. 查询个人四档有效权益和饭搭子超额结论。
5. 查询个人空间额度摘要，使用量在账本未落地时返回真实可解释状态。

不沿用 `/dining-groups/current`、`originalSpace`、`carryBackSnapshot` 或 `diningGroupTier` 字段。具体路径和字段在本阶段契约评审时冻结。

#### 数据库

1. 删除 `UserSpace` 和 `CarryBackSnapshot`。
2. 删除 `DiningGroup.FROZEN` 及相关时间和 SQL 状态约束。
3. 保留 `DiningGroup.ownerId` 唯一，保证每人最多主理一个饭搭子。
4. 允许用户在多个饭搭子中存在有效成员关系，同时保持 `(diningGroupId, userId)` 唯一。
5. `EntitlementGrant` 改为纯用户作用域并保存四档套餐事实；Free 仍可由服务端默认解析。
6. 调整邀请、幂等和审计事件，删除原空间和迁出快照语义。
7. 更新 seed 和真实流程验证脚本。

开发库允许随新 migration 重置旧测试数据，不建立旧空间到新关系的生产回填程序。

#### 服务端与客户端

1. 重写权益策略和饭搭子 Service，先完成双方额度并发校验。
2. 客户端 Store 改为本人饭搭子关系列表和个人权益摘要。
3. 成员页支持选择饭搭子、邀请、退出、移除、解散和超额处理。
4. “我的”页展示个人套餐、主理人数、加入数和超额结论。
5. 后台展示用户个人套餐与饭搭子关系，不再展示当前空间和饭搭子 Plus。

#### 验收

- 每人最多主理一个饭搭子。
- 免费用户主理一个后不能再加入其他饭搭子。
- 接受邀请同时校验双方额度，并发不能突破。
- 降级超额后只能查看、退出和移除。
- 加入、退出和移除不修改任何个人业务数据。
- 主理人可直接解散自己主理的饭搭子，且只解除关系，不回填或迁移任何个人数据。
- 旧当前空间、冻结恢复和迁出快照接口不再注册。

### 阶段二：个人菜谱与空间账本

该阶段完成菜谱最小闭环，不同时实现高级推荐、公共榜单或复杂搜索。

#### 契约与数据

1. 个人菜谱入口直接归用户。
2. 固定基础内容版本保持不可变。
3. 导入创建基础版本引用；文本编辑保存结构化覆盖。
4. 详情读取合并基础版本和个人覆盖，列表只读取预计算摘要所需字段。
5. 后续开放图片能力时，新增、替换或加工图片需在事务内固化个人独立版本。
6. 当前创建和更新请求不接受 `images`，已有系统图片只读且在文本编辑时保留。
7. 菜谱主页面改为“我的 / 灵感 / 合集”；灵感覆盖系统菜谱和人工审核通过的用户推荐固定版本，不提供用户搜索。
8. 逻辑空间账本覆盖基础结构化数据、覆盖数据、个人媒体和回收站。

覆盖存储的具体结构必须在 Schema 评审时确定，不默认采用通用 JSON Patch，也不为未来任意字段提前建设解释器。

#### 验收

- 未修改导入、单字段修改、新增项、删除标记和排序覆盖正确合并。
- 当前伪造 `images` 写入返回 `400`，文本编辑保留已有图片且不触发独立化。
- 同一来源未修改时避免重复入口，修改后允许再次导入。
- 来源入口普通删除不破坏仍被引用的固定版本。
- 首版不建设用户搜索、关注、评论和榜单；用户内容只通过受控推荐与人工审核进入灵感。
- 列表无 N+1，空间使用量可增量更新并全量重算。
- 其他用户可以读取菜谱，但不能编辑、删除或伪造持有人。

### 阶段三：个人计划、饭局、冰箱与购物

该阶段按一条“计划到做饭”主链交付，不拆成四套独立协作系统。

```text
个人周计划
-> 选择个人菜谱
-> 从某餐发起饭局
-> 邀请饭搭子或分享外部用户
-> 参与人选择我带菜
-> 本人生成购物缺口
-> 本人确认库存扣减
```

#### 实施内容

1. 周计划直接归用户，只创建实际安排的餐次。
2. 计划餐次和饭局共享固定菜单事实，避免双份可变菜单。
3. 饭局直接归发起人，参与关系归参与人。
4. 饭搭子邀请和外部分享使用同一饭局参与状态机。
5. “我带菜”只引用参与人的个人菜谱固定版本。
6. 冰箱和购物清单所有查询、写入和索引都使用用户作用域。
7. 购物建议可以来自计划、饭局、我带菜和个人冰箱缺口，但最终项目只写入本人清单。
8. 首版使用普通请求和必要的订阅消息，不引入 SSE 或实时协同基础设施。

#### 验收

- 计划转饭局不产生两份菜单。
- 外部参与人不能读取任何用户的冰箱、购物清单和完整计划。
- 成员退出饭搭子不自动取消已确认饭局参与。
- 带菜和购物只影响操作人自己的数据。
- 重复生成购物建议和库存扣减具备幂等边界。

### 阶段四：个性化、治理与旧模型清理

1. 接入主题皮肤、我的页背景图、首页背景图权限。
2. 背景图上传接入图片安全、空间计量和删除引用规则。
3. 后台增加最小菜谱举报、下架、审计和用户权益检查能力。
4. 更新 API 手册、客户端手册、OpenAPI 和接口索引。
5. 删除客户端、后台、脚本和文档中的旧字段与旧文案。
6. 将旧生命周期和 Prisma 计划标记为已被本计划替代，保留历史追溯。
7. 完成全仓类型检查、构建和核心流程验证。

头像装饰只保留规则和资源扩展点，不在没有真实资源与交互前建设业务模型。

## 五、性能要求

1. 成员关系至少覆盖 `(userId, status)`、`(diningGroupId, status)` 和唯一成员组合索引。
2. 邀请按令牌哈希、状态和有效期索引；不保存可直接使用的明文令牌。
3. 接受邀请按固定顺序锁定饭搭子和接受人额度主体，避免并发突破和死锁。
4. 首版通过索引计数解析饭搭子额度，不提前维护多份成员计数缓存。
5. 菜谱列表只读取摘要；详情一次性批量读取基础内容和覆盖，禁止逐食材、逐步骤查询。
6. 有效菜谱缓存键必须包含基础版本、个人覆盖版本和个人菜谱版本，写入后精确失效。
7. 空间账本增量写入必须与业务写入同事务，并提供离线全量重算校正命令。
8. 图片先压缩和重新编码再入对象存储，缩略图与原图引用分开管理。
9. 所有增长型列表必须分页；成员、菜谱、饭局和购物不得一次返回无限集合。

## 六、安全要求

1. 读写接口都做服务端所有权和成员关系校验，禁止依赖客户端隐藏按钮。
2. 菜谱可见只放宽读取，不放宽编辑、删除、导入身份和媒体管理权限。
3. 邀请令牌单次使用、短时有效、只存哈希；接受时重新校验双方实时额度。
4. 超额状态由服务端实时解析，旧 token、缓存和客户端状态不能绕过。
5. 图片校验真实类型、大小、尺寸和像素总数，移除 EXIF 并服务端重新编码。
6. 用户可见菜谱和背景图接入必要的文本、图片安全检查、举报和下架审计。
7. 饭局分享只暴露白名单字段，不返回内部用户主键、冰箱、购物、过敏原文或私人备注。
8. 所有高风险写入使用 `operationId`、事务和审计；并发可变对象使用版本校验。
9. 永久删除前检查固定版本和媒体引用，禁止删除仍被计划、饭局或其他用户菜谱引用的数据。
10. 会员和额度配置变更不能自动删除核心数据，也不能扩大未审核权限。

## 七、最小验证矩阵

| 纵切 | 主成功路径 | 关键失败路径 |
| --- | --- | --- |
| 饭搭子 | 邀请并加入多个关系 | 双方任一额度不足、重复接受、并发超限 |
| 降级 | 减少关系后自动恢复 | 超额时修改资料或继续邀请被拒绝 |
| 菜谱 | 导入、覆盖、图片独立化 | 越权编辑、来源删除、版本冲突 |
| 空间 | 增量计量与全量重算一致 | 超额继续上传、账本重复写入 |
| 计划饭局 | 周计划发起饭局并带菜 | 双菜单漂移、外部参与人越权 |
| 冰箱购物 | 本人缺口生成和库存扣减 | 访问他人数据、弱网重复执行 |
| 图片 | 压缩、安全检查和空间入账 | 伪造类型、超大像素、EXIF 泄露 |

每个阶段至少执行对应应用类型检查、真实 API 流程验证和 `git diff --check`。共享契约或跨端类型变化时执行完整 `pnpm type-check`。

## 八、实施顺序与提交建议

建议保持四个主题提交或四组连续提交，不按每张表、每个 DTO 或每个页面拆成大量微提交：

1. `重构饭搭子关系与个人四档权益`
2. `实现个人菜谱覆盖与空间账本`
3. `实现个人计划饭局与食材采购闭环`
4. `接入个性化内容治理并清理旧模型`

每组内部仍按“契约和 migration -> API -> 客户端/后台 -> 验证”顺序完成。上一组主链未通过，不进入下一组。

## 九、明确不顺手做

- 不重命名全部历史目录。
- 不统一重构所有页面样式。
- 不建设通用 Patch 引擎、权限中心、媒体中心或同步中心。
- 不实现价格、支付、自动续费和退款，直到商业契约确认。
- 不建设用户搜索、关注、评论、榜单和动态流。
- 不启动完整 Worker；需要清理时继续使用幂等调度命令。
- 不覆盖或删除历史 migration 和 `docs/cook/` 来源材料。

## 十、开始实施前确认

1. 同意开发环境直接删除旧空间、快照和饭搭子授权数据，不做回填。
2. 同意第一阶段新契约直接废止旧接口，不保留兼容期。
3. 确认饭搭子首版允许主理人直接解散，且只解除关系。
4. 菜谱业务流和页面行为已由 `recipe-execution.md` 重新确认；进入实现前继续冻结最小 API 和数据约束。
5. 确认图片独立化规则作为后续上传契约；当前阶段不实现图片写入。
