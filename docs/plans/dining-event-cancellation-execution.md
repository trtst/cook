# 功能执行单：饭局取消与同计划再次发起

## 1. 已确认业务流程

- 菜单确认后，详情页按当前用户冰箱重新计算采购缺口。
- 有确定采购缺口时，底部主按钮优先显示“去采购”或“查看采购清单”。
- 缺口清零且有已接受参与人时，底部显示“结束饭局”；确认后进入饭局回忆。
- 缺口清零且没有已接受参与人时，底部显示“取消饭局”。
- 取消确认文案明确：不进入回忆，原计划和菜单保留，之后还可以重新发起饭局。

## 2. 状态与权限

- 只有饭局发起人可以取消。
- 饭局已到开饭时间、已完成或已有 `ACCEPTED` 参与人时，服务端拒绝取消。
- 取消后饭局状态为 `CANCELLED`；当前 `ACTIVE / OPENED` 分享邀请改为 `EXPIRED`。
- 取消不生成回忆、不派发完成勋章、不触发做饭库存消耗，也不删除原计划、计划菜单或饭局菜单快照。
- 取消时把已取消饭局的 `mealPlanItemId` 置空，释放数据库现有的计划饭局唯一关系，使同一计划可以再次发起新的饭局。
- 已取消饭局不支持恢复；原饭局历史仍可通过已有饭局列表或详情 ID 查看。

## 3. 最小接口

`POST /dining-events/{eventId}/cancel`

- 请求：空业务体，携带数字字符串 `Idempotency-Key`。
- 返回：现有 `DiningEventSummary`，状态为 `CANCELLED`，`planItemId` 为 `null`。
- 幂等：操作类型为 `dining-event:cancel`，重复请求返回当前取消摘要。

## 4. 客户端行为

- 采购缺口、结束饭局、取消饭局按优先级互斥显示在 `meal-footer__buttons`。
- 缺口加载中或加载失败时，不提前显示结束/取消按钮。
- 取消成功后回到同一 `planItemId + planDate` 的计划详情，刷新计划事实；计划菜单仍在，并可再次点击“发起饭局”。

## 5. 验收

- 计划 `planItemId=276&planDate=2026-09-24` 有采购缺口时，底部出现“去采购/查看采购清单”，不出现“结束饭局”或“取消饭局”。
- 缺口清零、无已接受参与人时，出现“取消饭局”；确认后状态为 `CANCELLED`，当前邀请失效，回到原计划详情。
- 缺口清零、有已接受参与人时，出现“结束饭局”；确认后进入回忆。
- 已取消饭局对应的原计划仍能再次发起新饭局。
- 已到开饭时间、已完成或已有已接受参与人的饭局，取消接口返回冲突，状态和计划关系不被改变。
