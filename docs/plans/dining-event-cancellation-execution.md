# 功能执行单：取消饭局并删除对应计划

## 1. 已确认业务流程

- 菜单确认后，详情页按当前用户冰箱重新计算采购缺口。
- 有确定采购缺口时，底部主按钮优先显示“去采购”或“查看采购清单”。
- 缺口清零且有已接受参与人时，底部显示“结束饭局”；确认后进入饭局回忆。
- 缺口清零且没有已接受参与人时，底部显示“取消饭局”。
- 二次确认明确：取消会删除饭局、对应计划和菜单内容；已买食材及已记入冰箱的事实保留；删除后无法恢复。

## 2. 状态与权限

- 只有饭局发起人可以取消。
- 饭局已到开饭时间、已完成或已有 `ACCEPTED` 参与人时，服务端拒绝取消。
- 取消不生成回忆、不派发完成勋章、不触发做饭库存消耗。
- 取消在一个事务内删除饭局、对应计划及两者的内容；邀请、参与、菜单、心愿、准备记录等饭局子项随饭局删除。
- 删除饭局和计划产生的未购买采购来源；保留已购买项目及其冰箱痕迹。采购清单版本随删除更新。
- 计划轮询记录解除已确认资源关联，饭局/计划活动摘要删除；其他投票、采购清单和冰箱事实继续保留。
- 饭局封面对象在事务提交后清理；删除接口返回仅含 `id` 与 `status = CANCELLED` 的最小结果，幂等记录不保存饭局内容。
- 删除成功后客户端回到“我的饭局”列表；该饭局和计划均无法恢复或再次发起。

## 3. 最小接口

`POST /dining-events/{eventId}/cancel`

- 请求：空业务体，携带数字字符串 `Idempotency-Key`。
- 返回：`{ id, status: "CANCELLED" }`，不返回已删除的饭局内容。
- 幂等：操作类型为 `dining-event:cancel`；相同幂等键重放返回最小删除结果。资源删除后用其他幂等键请求返回不存在。

## 4. 客户端行为

- 采购缺口、结束饭局、取消饭局按优先级互斥显示在 `meal-footer__buttons`。
- 缺口加载中或加载失败时，不提前显示结束/取消按钮。
- 取消成功后回到“我的饭局”列表；饭局和对应计划均不再出现。

## 5. 验收

- 计划 `planItemId=276&planDate=2026-09-24` 有采购缺口时，底部出现“去采购/查看采购清单”，不出现“结束饭局”或“取消饭局”。
- 无已接受参与人且未到开席时间时，出现“取消饭局”；二次确认后饭局及对应计划、未购买采购来源被删除，页面回到饭局列表；已购买与冰箱事实保留。
- 缺口清零、有已接受参与人时，出现“结束饭局”；确认后进入回忆。
- 删除后的饭局和计划均不能恢复或再次发起。
- 已到开饭时间、已完成或已有已接受参与人的饭局，取消接口返回冲突，状态和计划关系不被改变。
