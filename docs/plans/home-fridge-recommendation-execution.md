# 首页按家里食材推荐优化执行单

## 目标

- “换一换”只展示按活跃家里食材匹配并去重后的菜谱。
- 页面刷新复用活跃食材和候选池缓存，菜谱增长后通过食材 ID 关联索引分批读候选。

## 本轮范围

- API/数据库：新增菜谱版本—食材关系表、历史回填、按用户的活跃食材与候选池缓存；更换首页推荐批处理逻辑。
- 小程序：保持每次最多 3 张卡；候选不足 3 道时清空菜谱卡并提供“去更新食材”入口。
- 契约文档：同步无页码读取、活跃食材规则、X 批次、随机与去重规则。

## 本轮不做

- 不改变菜谱正文版本和固定版本引用语义。
- 不新增菜谱标签优先级、最近做过优先级或匹配度排序。
- 不增加换一换频控。
- 不改菜谱详情、随机菜单或后台菜谱编辑流程。

## 业务流程与页面行为门禁

### 业务流程

- 用户目标：用家里近期仍确认“有”的食材快速看到能做的菜。
- 触发条件：首页登录状态下首次加载/重新展示推荐区，或用户点击“换一换”。重新展示只读取服务端按用户缓存；缓存有效时不重新查询食材痕迹或扫描菜谱。
- 主成功路径：从缓存读活跃食材和候选池；若池不足 9 道，按活跃食材数量和索引游标读取下一批；每批匹配结果随机打乱后去重；池有 3 道以上时返回 3 道。
- 失败 / 阻断路径：无活跃食材不查菜谱；候选读完后不足 3 道时返回空列表。
- 结束状态：显示 3 道新菜谱，或显示更新家里食材的空态与入口。
- 确认人 / 确认记录：用户在本对话确认分类范围、去重、分批阈值、空态和关联表方案。

### 页面行为

- 页面入口：首页“按家里已有食材”区域。
- 展示内容及用途：最多 3 道菜谱摘要；无完整 3 道候选时不展示零散菜谱。
- 用户操作：首页重新展示读取当前批次；“换一换”用幂等写请求从当前候选池取下一组；曾显示推荐且候选池耗尽后由服务端清空当前批次，再进入“这一轮能匹配的菜已经看完啦”空态；初次加载没有可匹配食材时显示独立提示。
- 加载 / 空态 / 失败态：加载时显示三张 skeleton；无匹配结果时提示更新家里的食材，入口跳转食材页；请求失败保留既有错误处理。
- 成功后的页面变化：整体替换为本次 3 道菜谱；池耗尽则切到更新食材空态。
- 本流程不需要的页面数据：主料标签、精确用量、单位换算、采购缺口、最近做过状态。

## 接口与数据基线

| 主事实 / 关系 | owner | 生命周期与约束 | 对应查询 |
| --- | --- | --- | --- |
| `recipe_version_ingredients` | 平台菜谱版本 | `(recipe_version_id, ingredient_id)` 唯一；两列均引用主表并级联删除 | 按活跃 `ingredient_id` 反查当前菜谱版本 |
| `home_fridge_recommendation_caches` | 当前用户 | 每用户一行；缓存当前展示批次、待展示候选 ID 与命中食材集合，池不足 9 时读取下一批；菜名用集合查重，命中食材集合按食材 ID 倒排后检查子集关系；扫描游标和去重签名 30 分钟后重建；手动确认、删除、采购入库、做饭记录等写操作仅在活跃食材集合或有效期变化时失效，最近一项活跃食材过期时重建 | 首页重复展示读同一批；换一换推进下一批 |

## 接口契约

| 方法 | 路径 | 用途 | 权限 | 状态 |
| --- | --- | --- | --- | --- |
| GET | `/home/fridge-recipes` | 读取当前展示批次；重复读取不推进候选游标；不传页码 | UserBearerAuth | 本轮实现 |
| POST | `/home/fridge-recipes` | 首页“换一换”推进到下一组；要求纯数字 `Idempotency-Key` | UserBearerAuth + Idempotency-Key | 本轮实现 |

X 取值：活跃食材 `1–14` 种为 `1500`，`15–34` 种为 `1000`，`35+` 种为 `500`。活跃食材按最新状态、7/15 天确认期和分类 ID `5001–5004` 计算。
