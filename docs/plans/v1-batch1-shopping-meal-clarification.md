# 炊火记 V1 第一批采购与餐次口径补丁

## 目的

冻结 2026-08-22 这一轮已经确认过、且后续不能再反复改口的第一批主链路口径，避免代码继续按旧的 `单一自动落点清单 / 保存后强制编辑 / 计划饭局混成一个对象` 规则推进。

## 本补丁覆盖的范围

1. `保存为私房菜`
2. 采购清单写入口径
3. 采购清单详情反向加餐次
4. 计划与饭局的对象边界
5. 饭局详情展示门禁

## 已冻结规则

### 1. 保存为私房菜

- 前台统一语义仍然是 `保存为私房菜`
- 从灵感详情进入时，保存就是保存，不再强制跳到编辑发布页
- 如需补字段，只允许保存前做最小必要选择；保存后编辑是可选动作
- 个人副本的真正生成时点是 `保存成功`

### 2. 采购清单不是单一自动落点

- V1 不采用“永远自动加入唯一一张默认清单”的口径
- 从菜谱、计划、饭局加入采购时，统一使用：
  - `选择已有采购清单`
  - `现场新建采购清单后加入`
- 多清单能力是第一批主链路的一部分，不是边缘能力

### 3. 采购清单详情可反向加餐次

- 从采购清单详情进入时，统一使用一个 `加餐次` 入口
- 这个入口在 UI 上不再拆成 `加计划 / 加饭局` 两张并列能力卡
- 进入后直接列近期餐次
- 如果餐次已经挂饭局且当前存在缺口，则按 `EVENT` 缺口写入这张清单
- 如果餐次还只是计划，则按 `PLAN` 写入这张清单
- UI 统一，底层对象和写入契约不合并

### 4. 计划和饭局不是同一个对象

- 两者共享同一顿饭的餐次上下文，但不是同一个数据对象
- `计划` 是个人安排容器
- `饭局` 是挂在这顿饭上的协作事件
- 不允许为了前台入口统一，就把计划和饭局在数据层合成一个类型
- 时间与结束判断也按对象边界处理：
  - 计划列表不再按默认 `18:30` 之类的餐次建议时间提前判定“已结束”
  - 饭局创建/改期不能写入早于当前时间的时间点

### 5. 饭局详情门禁

- `饭局回忆` 只在饭局真正结束后展示
- `采购准备` 需要直接展示缺什么清单，而不只是摘要文案
- 缺口里的菜名必须是当前食材真正对应的菜单，不是整场饭局完整菜单重复挂载

### 6. 我带菜与我想吃

- `我带菜` 和 `我想吃` 是并列能力，不互相替代
- `我带菜` 继续保持：
  - 不进入主家菜单
  - 不进入采购
  - 不进入缺口
  - 不进入库存计算
- `我想吃` 本轮只冻结存在性和并列关系，尚未进入实现
- 下一轮如果继续做饭局协作，必须单独按第二批执行单补 `我想吃` 的详细交互和数据写入

### 7. 清单默认命名

- 有明确餐次上下文时：`x月x日 · [餐次]清单`
- 无明确餐次上下文时：`x月x日 · 采购清单`
- 不再使用“饮食计划”这类命名

## 本轮已落代码结果

- 首页 `GET /api/home/next-meal` 与 `GET /api/home/fridge-recipes` 在 API 重启后已不再返回 `404`，当前本地返回 `401`，说明新路由已生效
- 饭局创建/改期补了过去时间拦截
- 计划列表结束判定收回到按当天结束，不再受默认餐次建议时刻影响
- 饭局详情补了采购缺口明细、回忆展示门禁
- 采购清单详情统一成 `加餐次` 入口，并按 `PLAN / EVENT` 分流写入
- 缺口食材下挂的菜单名改为真实对应菜单

## 暂不继续扩写的项

- `我想吃` 具体交互与接口
- 饭局回忆卡展示字段细则
- 更完整的采购联调回放记录

## 一句话结论

这一轮先把：

**保存为私房菜直接生成副本 + 采购保持多清单显式选择 + 清单侧统一加餐次入口 + 计划/饭局只统一入口不统一对象**

冻结为后续继续开发的口径。
