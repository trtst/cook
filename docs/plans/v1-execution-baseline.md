# 炊火记 V1 执行基线

## 目的

本文档是炊火记 V1 的唯一执行基线。

它只回答 3 个问题：

1. V1 做什么
2. V1 不做什么
3. V1 按什么批次推进

字段、表结构、接口参数等实现细节不在本文档展开。

## 一、V1 范围

**V1 = 个人下一顿闭环 + 饭局轻协作闭环**

| 优先级 | 模块 | 说明 |
| --- | --- | --- |
| P0 | 首页下一顿决策 | 主入口，状态驱动 |
| P0 | 菜谱主系统 | 内容基础 |
| P0 | 冰箱与采购 | 执行支撑 |
| P0 | 做饭执行 | 闭环终点 |
| P0 | 饭局轻协作 | 协作主线 |
| P1 | 营养展示 | 弱上，可降级 |
| 后端预留 | 菜品知识底座 | 不上前台独立页面 |

## 二、已冻结全局规则

### 1. 首页

- 首页主标题固定为 `今晚吃什么？`
- 首页状态由后端统一返回 `status enum + 摘要数据`
- 前端只按返回状态渲染，不做业务兜底
- 首页动作区排序延续现有逻辑，由后台配置；如配置缺失，前端按默认基线顺序兜底
- 首页状态枚举固定为：
  - `NO_ARRANGEMENT`
  - `NEED_GAP_CHECK`
  - `NEED_SHOPPING`
  - `READY_TO_COOK`
  - `COMPLETED`
- 前 4 个是首页首屏主状态，`COMPLETED` 只进入最近安排，不占首屏主位

### 2. 菜谱

- 系统菜谱所有进入个人链路的前台语义统一为 `保存为私房菜`
- 不混用 `导入 / 收藏 / 改编`
- 保存即生成个人副本，后续编辑是可选动作，不强制进入编辑发布页
- 私房菜草稿不可进入计划

### 3. 采购

- 采购保持多清单能力，不收成单一采购清单自动落点
- 从菜谱、计划、饭局加入采购时，统一为 `选择已有采购清单 / 现场新建清单后加入`
- 从采购清单详情可反向 `加餐次`，把计划或已挂饭局的当前缺口加入这张清单
- 不按来源自动拆单
- 来源元信息保留，但不前置分组
- 采购清单详情按当前清单聚合显示，不把计划和饭局合并成同一数据对象

### 4. 做饭执行

- 多菜执行优先以 `做饭助手` 为主视图
- 原始步骤只作为降级备选
- 做饭助手前台三态固定为：
  - `未生成`
  - `已生成`
  - `降级原始步骤`
- 计划与饭局只有在用户显式点击完成后才同步完成

### 5. 饭局协作

- `我带菜` 只做登记，不进入主家菜单，不进入采购，不进入缺口
- `我想吃池` 与 `我带菜` 并列存在，不互相替代
- `我想吃池` 为新最小实现，不复用旧 poll
- `我想吃池` 只支持从已有菜谱中选择，不支持自由输入
- `我想吃池` 与知识底座在 V1 解耦
- 回忆分享入口只在饭局完成后展示

### 6. 营养与知识底座

- 营养展示只上菜谱详情页
- 第一版营养数据以后台人工维护为主，不做自动计算闭环
- 知识底座只做后端能力，不做前台独立 Wiki 页
- 搜索结果继续在菜谱页内承接，不新起独立路由

## 三、模块边界

### 模块 1：首页下一顿决策

- 只回答“今晚吃什么、下一步做什么”
- 首页是状态驱动，不是入口集合
- 首屏结构固定为：
  - 下一顿状态卡
  - 2x2 动作区：默认基线顺序为 `随机一桌 / 看冰箱 / 采购清单 / 加菜谱`，实际排序沿用后台配置
  - 冰箱匹配推荐
  - 最近安排
- 不做复杂推荐流和个性化排序

### 模块 2：菜谱主系统

- 继续固定 `私房菜 / 灵感` 双 Tab
- 系统菜谱进入个人链路只有一条：`保存为私房菜`
- 主路径固定为：
  - `灵感 -> 保存为私房菜 -> 加入计划`
- 如需补分类，只允许保存前做最小选择；保存后不强制进入编辑发布页
- V1 不做独立“我的收藏”模块

### 模块 3：冰箱与采购

- 统一主链路：
  - `菜谱/计划/饭局 -> 缺口分析 -> 选择已有清单或新建清单 -> 完成购物 -> 入冰箱`
- 反向链路固定为：
  - `采购清单详情 -> 加餐次 -> 选择计划或已挂饭局的餐次 -> 写入当前清单`
- 饭局进入采购只看主家菜单缺口
- `我带菜` 不转采购项
- 已挂饭局的餐次按 `EVENT` 缺口写入；未挂饭局的计划按 `PLAN` 写入
- V1 不做饭局共享采购，不做多套购物体验

### 模块 4：做饭执行

- 入口从计划详情或饭局详情进入
- 允许列表和沉浸式两种视图
- 多菜执行优先读做饭助手
- 原始步骤只做降级
- 本餐完成由用户显式点击触发

### 模块 5：饭局轻协作

- 保留：
  - 发起
  - 邀请
  - 参与确认
  - 菜单确认
  - 我带菜
  - 完成饭局
  - 回忆分享
- 回忆分享能力在 V1 保留，但展示字段待定，后续按第二批详细设计单独确认
- `我想吃池` 按 `提议 + 附议 + 主家加入本次菜单` 落地
- `确认菜单` 是唯一正式生效动作
- 不做：
  - 聊天
  - 实时同步
  - 公开投票
  - 我来做
  - 做饭进度同步
  - 共享冰箱
  - 复杂权限

### 模块 6：营养展示

- 只上菜谱详情页
- 只读展示：
  - 热量
  - 蛋白质
  - 脂肪
  - 碳水
- 数据不足时允许按降级文案展示
- 不做营养推荐、减脂方案、AI 营养师

### 模块 7：菜品知识底座

- 只做后端能力
- V1 最小范围：
  - 别名归一
  - 同菜归一
  - 搜索承接
- 不做前台独立 Wiki 页、百科社区、复杂知识图谱

## 四、明确不做

以下能力不进入 V1 前台：

- 会员 / 订阅展示引导
- 灶火值 / 积分
- 兑换码前台引导
- 广告减免前台能力扩展
- 语音、AI 推荐、OCR
- 实时多人做饭协作
- 聊天、评论、公开社交流
- 我来做
- 复杂营养推荐
- 点菜池概念归一

## 五、批次划分

### 第一批

- 首页下一顿决策
- 菜谱主系统
- 冰箱与采购

目标：先跑通 `决定吃什么 -> 看缺什么 -> 进入采购清单`

### 第二批

- 做饭执行
- 饭局轻协作

目标：在第一批稳定后，跑通 `已安排 -> 做饭 -> 饭局完成`

### 第三批

- 营养展示
- 菜品知识底座

目标：补齐辅助信息层和后端基础能力，不反向阻塞 P0 上线

## 六、执行规则

- 正式开发只以本基线和各批次执行单为准
- 第一批稳定前，不启动第二批
- 第三批始终不能反向阻塞 P0 上线
- 每完成一块能力，都必须更新 `docs/plans/minor_change_log.md`

## 七、一句话结论

**V1 先跑通主闭环，再补执行和协作，最后补辅助层。**
