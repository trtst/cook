# 食材库存批次模型实施记录

## 已落地口径

- 食材列表按最终有效食材身份聚合，同一食材只出现一次。
- `fridge_items` 每行作为一次购买/入库批次；详情页展示当前批次，新增库存创建新批次。
- 扣减只提交食材身份、总量和单位，服务端按最早到期批次跨批次分摊；过期但有量的批次仍可使用。
- 扣减至 `0` 的批次进入历史；历史默认收起，15 天只影响展示。
- `aliases` 与 `MERGED + mergedToId` 沿用现有食材治理，不新增父子食材树。
- 购物清单库存预占与真实扣减分离；采购完成的每个入库项创建独立批次。

## 数据审计

在实施前对本地真实数据库执行只读审计，共检查 `195` 条库存记录：

- `14` 条缺少 `ingredientId`，保留为待确认状态，不按名称猜测。
- 未发现已归并食材库存。
- 存在模糊数量，保留原始文案，不参与自动扣减。
- 存在已过期但仍可用的库存，按当前规则继续保留和扣减。

因此 migration 只增加非负精确数量检查和按用户/食材/可用状态/到期时间的查询索引，不做历史数据自动迁移。

## 代码与接口

- API 新增食材级摘要、食材详情、历史批次和按总量扣减模型。
- 客户端列表消费食材摘要；详情页将 Hero 放入滚动容器，去除重复到期文案，默认折叠过期/历史批次，并提供新增与总量扣减。
- 最后一个批次扣减至 `0` 后，详情响应返回空当前库存摘要和历史入口，不复用扣减前的批次详情。
- 旧的未绑定库存通过 `/fridge-items/batch/{itemId}` 查看，保持 `identityPending`，不隐式猜测食材身份。
