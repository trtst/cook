# 菜谱营养基表映射规则确认稿

## 一、文档状态

本文用于冻结“系统食材如何映射到营养基表项”的当前规则边界。

当前阶段结论：

1. 只先确认映射规则，不导入正式营养基表数据。
2. 只先定义后续如何做，不进入当前代码实现。
3. 营养计算仍以 `recipe-data-completion-rules.md` 的字段分层和降级规则为上位约束。

## 二、文档目标

本文只解决以下问题：

1. 一个系统食材如何绑定营养基表项。
2. 什么时候可以自动映射。
3. 什么时候必须人工复核。
4. 映射结果如何存储，供后续营养分析与健康规划复用。

本文不解决：

1. 营养基表全量导入。
2. 实际表结构、迁移和脚本实现。
3. 菜谱详情页营养 UI。
4. 健康规划算法。

## 三、基本原则

### 3.1 映射只绑定系统食材

第一版营养映射只绑定系统食材，不直接绑定用户个人食材。

规则：

1. 已归并到系统食材的个人食材，按系统食材映射处理。
2. 仍为个人食材、未进入系统库的条目，不直接进入稳定营养映射主链路。
3. 个人食材后续若要参与营养分析，先通过“系统食材候选映射”降级处理，不影响当前正式映射层稳定性。

### 3.2 映射结果不进入菜谱正文

营养映射属于后台基础数据，不进入菜谱正文事实层。

规则：

1. 食材与营养基表项的绑定是后台引用关系。
2. 映射调整不得改写菜谱正文中的 `ingredientId`、数量或步骤。
3. 后续营养结果按映射关系派生，不反向覆盖正文。

### 3.3 映射先求稳定，不先求全量

第一版优先保证高频家常食材稳定可算，不追求长尾全覆盖。

## 四、映射对象

### 4.1 映射左侧对象

左侧对象固定为系统食材：

1. `ingredientId`
2. 系统食材名称
3. 分类
4. 默认单位
5. 必要别名

### 4.2 映射右侧对象

右侧对象固定为营养基表项：

1. `nutrientFoodId`
2. 来源编码
3. 标准名称
4. 营养基准口径
5. 可食部信息
6. 数据版本

### 4.3 一对一为默认规则

第一版默认采用：

1. 一个系统食材主映射到一个营养基表项。
2. 不做多映射聚合平均。
3. 不做运行时“按菜谱语境动态挑不同映射项”。

后续若出现真实需求，再单独评审“一食材多营养映射候选”的扩展。

## 五、映射优先级规则

### 5.1 精确同名同物优先

满足“名称、物种、常见形态都一致”的营养基表项优先级最高。

例如：

1. 系统食材是 `鸡胸肉`，优先映射 `鸡胸肉`，不映射 `鸡肉（代表值）`
2. 系统食材是 `三文鱼`，优先映射 `三文鱼`
3. 系统食材是 `北豆腐`，优先映射 `北豆腐`，不优先用泛化 `豆腐`

### 5.2 细分部位优先于代表值

当营养基表中同时存在细分部位和泛化代表值时：

1. 细分部位优先
2. 无细分部位时才退回代表值

例如：

1. `鸡翅` 优先 `鸡翅`
2. 没有 `鸡翅` 时才退回 `鸡肉（代表值）`

### 5.3 可食部更明确者优先

若两个候选都看似匹配，优先使用：

1. 可食部定义更明确的项
2. 与家庭烹饪实际购买/处理方式更接近的项

### 5.4 加工度更接近日常烹饪原料者优先

第一版优先映射“家庭做菜时的原始食材”，不优先映射深加工或品牌化条目。

例如：

1. `番茄` 优先原料番茄
2. `燕麦` 优先原味燕麦，不优先即食品牌冲调品

### 5.5 分类冲突时人工复核

若名称相近但类别冲突，不自动映射。

例如：

1. 干制 vs 鲜品
2. 生鲜 vs 熟制品
3. 原料 vs 调味复合品

此类必须人工复核。

## 六、自动映射与人工复核边界

### 6.1 可自动映射条件

满足以下条件时，可进入自动映射候选：

1. 系统食材名称与营养项标准名称高度一致
2. 分类一致或无明显冲突
3. 无多个同优先级候选冲突
4. 不涉及鲜/干、生/熟、原料/复合加工歧义

### 6.2 必须人工复核条件

出现以下任一情况，必须人工复核：

1. 一个系统食材对应多个高相似候选
2. 存在部位歧义
3. 存在鲜/干歧义
4. 存在生/熟歧义
5. 存在包装食品/品牌歧义
6. 可食部定义不清
7. 系统食材名称是泛称，例如 `青菜`、`鱼`、`肉片`

### 6.3 暂不映射条件

出现以下情况，暂不进入正式映射：

1. 食材本身过于模糊
2. 当前营养基表没有稳定候选
3. 需要复杂配方拆分才能计算
4. 需要品牌 SKU 级营养差异支持

此类食材后续只允许在营养结果中体现为“数据不足”。

## 七、单位与换算关系

### 7.1 映射不等于换算

食材映射只解决“它是谁”，单位换算解决“它有多少”。

映射层本身不直接承担全部单位推导。

### 7.2 第一版换算依赖

后续营养分析要想真正可算，还需同时具备：

1. 营养基表基准口径
2. 系统单位到基准口径的换算规则
3. `COMMON / PACKAGE` 标准映射表

### 7.3 常用单位与包装单位策略

对于 `个 / 瓣 / 包 / 盒 / 瓶 / 罐`：

1. 只有存在标准换算定义的食材才允许参与稳定营养计算
2. 没有标准映射时，不因为食材已映射成功就直接视为“可精算”

## 八、映射结果状态

建议后续映射结果至少区分三档状态：

1. `CONFIRMED`
2. `CANDIDATE`
3. `UNMAPPED`

语义：

1. `CONFIRMED`：已确认可用于正式营养分析
2. `CANDIDATE`：有候选但未人工确认
3. `UNMAPPED`：当前无稳定映射

## 九、建议存储字段

后续正式落库时，建议每条映射至少保留：

1. `ingredientId`
2. `nutrientFoodId`
3. `matchType`
4. `status`
5. `confidence`
6. `sourceVersion`
7. `reviewedBy`
8. `reviewedAt`
9. `notes`

## 十、后续实施步骤

后续真正开始做时，按以下顺序推进：

1. 先冻结高频系统食材清单
2. 导入营养基表原始数据到底稿层
3. 产出自动映射候选
4. 完成人工复核
5. 冻结第一版 `CONFIRMED` 映射集
6. 再接菜谱营养计算

## 十一、当前不做

当前明确不做：

1. 全量食材一次性自动映射
2. 个人食材直接进入正式营养映射主链路
3. 品牌 SKU 级映射
4. 动态按上下文切换多个营养候选项
5. 营养映射结果直接暴露给用户编辑

## 十二、待确认项

后续进入实现前，当前默认按本稿建议执行；如遇真实数据或映射冲突，再针对具体项复核：

1. 第一版是否允许少量“代表值映射”进入 `CONFIRMED`
2. `青菜 / 菜心 / 油麦菜` 这类近义但不完全同物的映射是否统一按人工复核处理
3. 个人食材何时进入营养映射正式主链路
