# 菜谱导入校对工作台规则确认稿

## 一、文档状态

本文用于冻结“菜谱导入后的人工作台如何校对和补齐”的规则边界。

当前阶段结论：

1. 只先确认工作台规则，不进入实现。
2. 工作台是导入草稿发布前的人工收口环节，不是新建菜谱主流程。
3. 工作台必须服从 `recipe-data-completion-rules.md` 中的正文事实、派生字段和缺失处理边界。

## 二、文档目标

本文只解决以下问题：

1. 导入后哪些字段允许在工作台内补齐。
2. 哪些字段允许直接改。
3. 哪些字段只能标记待确认。
4. 工作台如何判断“可发布”与“仍需修正”。

## 三、工作台定位

### 3.1 工作台是导入草稿校对层

工作台只服务以下链路：

```text
后台批量 JSON 导入 -> 待审核系统项 -> 人工校对 -> 发布为灵感系统菜谱
```

导入系统菜谱与普通用户创建私房菜是两条流程，不共用正式菜谱创建入口。

### 3.2 导入成功后的写入范围

JSON 导入成功后，只创建待审核系统项和导入草稿：

1. 保存原始 JSON、规范化内容和后台匹配结果。
2. 保存分类、标签、厨具、原始步骤和美食助理步骤等导入内容。
3. 已严格匹配的食材和单位保留引用；未匹配食材创建为 `PENDING` 系统食材，并绑定到导入草稿。
4. 导入项使用自己的工作台记录 ID；此时不创建正式 `Recipe.id`。
5. 不分配灵感归属 UID/昵称，不生成收藏数，不进入前台灵感菜谱。

### 3.3 发布成功后的写入范围

发布前通过全部门禁后，服务端才：

1. 创建正式 `Recipe` 和 `RecipeContentVersion`，自动生成菜谱 ID。
2. 写入最终系统分类。
3. 从后台维护的 100 个灵感用户池中随机选择一名用户作为菜谱归属；UID 和昵称不来自 JSON。
4. 收藏数从 `0` 开始，后续只由真实收藏行为产生。
5. 保存已确认的导入标签、厨具和美食助理快照。
6. 根据正式食材、数量和单位生成营养分析及其他 Wiki 派生结果。

营养派生结果不足时保留 `PENDING` 或 `INSUFFICIENT` 状态，不得用数值 `0` 伪装成估算结果。

### 3.4 工作台不替代正常创建流程

规则：

1. 正常用户手动创建菜谱仍走现有创建流程。
2. 导入校对工作台只处理导入结果，不扩成通用编辑器。
3. 工作台不承接未来所有菜谱编辑需求。

## 四、校对对象分层

### 4.1 可直接修正的正文事实

工作台允许直接修正以下正文事实：

1. `name`
2. `categoryId`
3. `baseServings`
4. `difficulty`
5. `duration`
6. `story`
7. `tips`
8. `ingredients`
9. `steps`
10. `sceneIds`

### 4.2 只读展示的派生结果

工作台第一版只读展示以下派生结果，不把它们直接编辑成正文事实：

1. 营养估算
2. 主蛋白推断
3. 菜品角色标签
4. 餐型标签
5. 风味标签
6. 辣度标签
7. 健康标签

### 4.3 可确认但不直接写正文的待确认项

工作台后续若要支持确认动作，也只应确认：

1. 标签接受/驳回
2. 映射接受/驳回
3. 缺失项说明

而不是把派生值伪装成用户原始输入。

## 五、第一版工作台必备能力

### 5.1 基础信息补齐

工作台第一版必须支持补齐：

1. `categoryId`
2. `baseServings`
3. `difficulty`
4. `duration`

这是当前已确认的发布必填项中，最容易在导入时缺失的部分。

### 5.2 食材逐行校对

每条导入食材行至少要支持：

1. 查看原始文本
2. 选择系统食材
3. 选择单位
4. 录入精确数量
5. 保留原始用量文本并标记待修正；不把模糊用量写入正式菜谱模型
6. 删除错误食材行
7. 新增遗漏食材行

### 5.3 步骤逐条校对

每条步骤至少要支持：

1. 查看原始文本
2. 编辑文本
3. 删除错误步骤
4. 新增遗漏步骤
5. 调整顺序

### 5.4 发布前校验

工作台必须在发布前明确提示：

1. 当前缺哪些必填字段
2. 哪些食材仍未结构化
3. 哪些结果只是估算
4. 当前是否允许发布

## 六、字段处理规则

### 6.1 名称规则

`name` 可编辑，但不允许：

1. 后台自动静默改成另一道菜名
2. 用推荐标签或原始网页标题替代用户已确认名称

### 6.2 分类与场景规则

规则：

1. 普通用户菜谱的 `categoryId`、系统导入项的 `inspirationCategoryId` 必须在发布前补齐
2. `sceneIds` 可空
3. 工作台不要求导入时强制补场景

### 6.3 人数、难度、时长规则

规则：

1. `baseServings`、`difficulty`、`duration` 允许导入时为空
2. 允许在工作台一次性补齐
3. 未补齐时不能发布

### 6.4 食材规则

规则：

1. 优先结构化为 `ingredientId + quantity + unitId`
2. 数量必须是可校验的正数，单位必须来自当前可用系统单位
3. 无法稳定精确化时，保留导入原文并标记为 `NEEDS_FIX`；原文不进入正式菜谱模型
4. 识别到“适量、少许、按需”等模糊用量时，必须改成精准数量后才能发布；不得将模糊用量写入正式菜谱模型
5. 若既无法结构化也无法确认精准数量，则标记为待修正

导入时未匹配到的食材不得直接创建为 `ACTIVE` 系统食材。后台应创建或复用一条 `PENDING` 系统食材，统一出现在“待审核食材”入口；该食材审核为 `ACTIVE` 或被归并、重新匹配前，引用它的导入项不得发布。

### 6.5 步骤规则

规则：

1. 工作台允许人工润色语句
2. 不允许后台自动补写用户未提供的关键烹饪事实
3. 步骤最少保留 1 条有效项

## 七、状态与门禁

### 7.1 工作台状态建议

建议后续区分以下状态：

1. `PENDING_PARSE`
2. `NEEDS_FIX`
3. `READY`
4. `PUBLISHING`
5. `PUBLISHED`
6. `FAILED`

### 7.2 可发布条件

工作台项只有在满足以下条件时，才允许进入发布：

1. `name` 已确认
2. `categoryId` 或 `inspirationCategoryId` 已补齐
3. `baseServings` 已补齐
4. `difficulty` 已补齐
5. `duration` 已补齐
6. 至少 1 条有效食材
7. 至少 1 条有效步骤
8. 所有食材均已匹配到 `ACTIVE` 系统食材
9. 所有用量均为正数和有效系统单位

### 7.3 不阻塞发布的项

以下情况不直接阻塞发布，但必须影响后续质量状态：

1. 部分标签未确认
2. 营养结果暂缺
3. 部分派生值低置信度
4. 美食助理尚未生成

## 八、批量与单条边界

### 8.1 第一版以单条校对为主

第一版工作台优先支持逐条校对，不追求复杂批量操作。

### 8.2 允许的轻量批量能力

后续可以允许少量轻量批量能力，例如：

1. 批量设置分类
2. 批量设置场景
3. 批量标记状态

但第一版不要求：

1. 批量改食材映射
2. 批量改步骤正文
3. 批量自动发布

## 九、与后台补全的分工

工作台与后台补全的边界：

1. 后台负责给出候选和缺失提示
2. 导入工作台负责人工确认正文事实
3. 发布时后台负责创建正式菜谱并分配灵感用户池归属
4. 发布后后台负责生成派生结果
5. 已发布用户菜谱进入后台 Wiki 治理后，运营可以补充当前正文版本的标签、营养、分析和完整度等派生结果；这不是把派生结果伪装成用户正文
6. 导入工作台第一版不直接编辑营养和健康派生真值；低置信度结果保留状态并进入后台治理

## 十、后续实施步骤

后续真正开始做时，按以下顺序推进：

1. 冻结导入草稿字段和状态机
2. 冻结工作台字段权限
3. 实现单条校对页
4. 接入发布校验
5. 再考虑批量能力

## 十一、当前不做

当前明确不做：

1. 导入工作台替代正常创建页
2. 一次性全自动直发
3. 直接在工作台里做人群健康规划
4. 在导入工作台里直接编辑营养派生真值；已发布菜谱的派生补充走后台 Wiki 治理入口
5. 批量复杂规则编排

## 十二、待确认项

后续进入实现前，当前默认按本稿建议执行；如遇真实工作台交互或权限冲突，再针对具体项复核：

1. 工作台是否允许“分类/人数/难度/时长”一键批量补齐
2. 系统菜谱后台导入与个人菜谱网页导入，是否共用同一套工作台
3. 工作台中低置信度标签是否只展示，不允许确认
