# 菜谱导入校对工作台规则确认稿

## 一、文档状态

本文用于冻结“菜谱导入后的人工作台如何校对和补齐”的规则边界。

当前阶段结论：

1. 只先确认工作台规则，不进入实现。
2. 工作台是导入草稿发布前的人工收口环节，不是新建菜谱主流程。
3. 工作台必须服从 `recipe-data-completion-rules.md` 中的正文事实、派生字段和缺失处理边界。

## 二、文档目标

本文只解决以下问题：

1. 导入后哪些字段允许在工作台内补齐。
2. 哪些字段允许直接改。
3. 哪些字段只能标记待确认。
4. 工作台如何判断“可发布”与“仍需修正”。

## 三、工作台定位

### 3.1 工作台是导入草稿校对层

工作台只服务以下链路：

```text
网页/后台导入 -> 导入草稿 -> 人工校对 -> 发布到我的或系统菜谱
```

### 3.2 工作台不替代正常创建流程

规则：

1. 正常用户手动创建菜谱仍走现有创建流程。
2. 导入校对工作台只处理导入结果，不扩成通用编辑器。
3. 工作台不承接未来所有菜谱编辑需求。

## 四、校对对象分层

### 4.1 可直接修正的正文事实

工作台允许直接修正以下正文事实：

1. `name`
2. `categoryId`
3. `baseServings`
4. `difficulty`
5. `duration`
6. `story`
7. `tips`
8. `ingredients`
9. `steps`
10. `sceneIds`

### 4.2 只读展示的派生结果

工作台第一版只读展示以下内容，不允许人工直接编辑为正文事实：

1. 营养估算
2. 主蛋白推断
3. 菜品角色标签
4. 餐型标签
5. 风味标签
6. 辣度标签
7. 健康标签

### 4.3 可确认但不直接写正文的待确认项

工作台后续若要支持确认动作，也只应确认：

1. 标签接受/驳回
2. 映射接受/驳回
3. 缺失项说明

而不是把派生值伪装成用户原始输入。

## 五、第一版工作台必备能力

### 5.1 基础信息补齐

工作台第一版必须支持补齐：

1. `categoryId`
2. `baseServings`
3. `difficulty`
4. `duration`

这是当前已确认的发布必填项中，最容易在导入时缺失的部分。

### 5.2 食材逐行校对

每条导入食材行至少要支持：

1. 查看原始文本
2. 选择系统食材
3. 选择单位
4. 录入精确数量
5. 保留模糊用量
6. 删除错误食材行
7. 新增遗漏食材行

### 5.3 步骤逐条校对

每条步骤至少要支持：

1. 查看原始文本
2. 编辑文本
3. 删除错误步骤
4. 新增遗漏步骤
5. 调整顺序

### 5.4 发布前校验

工作台必须在发布前明确提示：

1. 当前缺哪些必填字段
2. 哪些食材仍未结构化
3. 哪些结果只是估算
4. 当前是否允许发布

## 六、字段处理规则

### 6.1 名称规则

`name` 可编辑，但不允许：

1. 后台自动静默改成另一道菜名
2. 用推荐标签或原始网页标题替代用户已确认名称

### 6.2 分类与场景规则

规则：

1. `categoryId` 必须在发布前补齐
2. `sceneIds` 可空
3. 工作台不要求导入时强制补场景

### 6.3 人数、难度、时长规则

规则：

1. `baseServings`、`difficulty`、`duration` 允许导入时为空
2. 允许在工作台一次性补齐
3. 未补齐时不能发布

### 6.4 食材规则

规则：

1. 优先结构化为 `ingredientId + amount`
2. `EXACT` 优先于 `FUZZY`
3. 无法稳定精确化时，允许保留 `FUZZY`
4. 若既无法结构化也无法确认模糊用量，则标记为待修正

### 6.5 步骤规则

规则：

1. 工作台允许人工润色语句
2. 不允许后台自动补写用户未提供的关键烹饪事实
3. 步骤最少保留 1 条有效项

## 七、状态与门禁

### 7.1 工作台状态建议

建议后续区分以下状态：

1. `PENDING_PARSE`
2. `NEEDS_FIX`
3. `READY`
4. `PUBLISHING`
5. `PUBLISHED`
6. `FAILED`

### 7.2 可发布条件

工作台项只有在满足以下条件时，才允许进入发布：

1. `name` 已确认
2. `categoryId` 已补齐
3. `baseServings` 已补齐
4. `difficulty` 已补齐
5. `duration` 已补齐
6. 至少 1 条有效食材
7. 至少 1 条有效步骤

### 7.3 不阻塞发布的项

以下情况不直接阻塞发布，但必须影响后续质量状态：

1. 少量 `FUZZY` 用量
2. 部分标签未确认
3. 营养结果暂缺
4. 部分派生值低置信度

## 八、批量与单条边界

### 8.1 第一版以单条校对为主

第一版工作台优先支持逐条校对，不追求复杂批量操作。

### 8.2 允许的轻量批量能力

后续可以允许少量轻量批量能力，例如：

1. 批量设置分类
2. 批量设置场景
3. 批量标记状态

但第一版不要求：

1. 批量改食材映射
2. 批量改步骤正文
3. 批量自动发布

## 九、与后台补全的分工

工作台与后台补全的边界：

1. 后台负责给出候选和缺失提示
2. 工作台负责人工确认正文事实
3. 后台负责生成派生结果
4. 工作台第一版不直接编辑营养和健康标签

## 十、后续实施步骤

后续真正开始做时，按以下顺序推进：

1. 冻结导入草稿字段和状态机
2. 冻结工作台字段权限
3. 实现单条校对页
4. 接入发布校验
5. 再考虑批量能力

## 十一、当前不做

当前明确不做：

1. 导入工作台替代正常创建页
2. 一次性全自动直发
3. 直接在工作台里做人群健康规划
4. 工作台里直接编辑营养派生真值
5. 批量复杂规则编排

## 十二、待确认项

后续进入实现前，当前默认按本稿建议执行；如遇真实工作台交互或权限冲突，再针对具体项复核：

1. 工作台是否允许“分类/人数/难度/时长”一键批量补齐
2. 系统菜谱后台导入与个人菜谱网页导入，是否共用同一套工作台
3. 工作台中低置信度标签是否只展示，不允许确认
