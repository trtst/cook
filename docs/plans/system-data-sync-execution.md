# 后台系统数据手动同步

> 2026-10-04：按已确认需求扩展为可选择类别的线上快照导出与本地测试环境替换导入。本文件下面保留原 V1 记录作为历史基线；本轮新增契约见“快照扩展”。

## 快照扩展（已确认）

### 目标与边界

- 从线上导出一个时间点的数据快照，再导入本地测试环境；保留既有 TEST 首次初始化 ONLINE、此后只允许 ONLINE -> TEST 的方向限制。
- 导出时可选择数据类别：用户及其业务数据、勋章、菜谱分类、菜谱、食材分类、系统食材、食材营养表、单位、文章、文章栏目。营养、单位等低频数据可不选。
- 快照只覆盖已选择类别；导入后这些类别按快照完整替换目标环境对应记录，类别内仅存在于目标环境的记录清除；未选择类别保持不变。
- 菜谱与文章所引用的受管图片文件随包导出，导入后写入目标环境自己的资产存储并改写引用。用户头像等未确认媒体不纳入本次图片搬迁。
- 用户快照包含手机号、用户业务记录及关联，并包含快照账号自己的个人食材和单位；不能导出其他账号的个人食材/单位。不复制密码哈希、微信身份、认证会话或短信/风控临时记录。本地用户通过本地短信手机号授权或本地微信手机号授权匹配手机号账号登录。
- 导入预览检查未选类别的依赖：若目标环境缺少被快照引用的类别/记录，按具体类别汇总缺失数量并阻止导入；管理员补选、重新导出后再导入。已经存在于目标环境的依赖可继续使用。

### 用户流程与页面行为

1. SUPER_ADMIN 在系统数据同步页勾选导出类别；导出文件标注来源环境、导出时间、快照类别和数据/媒体清单。
2. 选择快照文件后，服务端校验格式、来源方向、文件/媒体清单、引用及依赖；页面展示每类新增、覆盖、将清理数量，以及缺失依赖和冲突。
3. 存在缺失依赖或不可安全覆盖的冲突时禁用导入，并列明类别、记录数及补选建议。
4. 管理员确认后，服务端事务替换所选数据类别；数据库失败时整体回滚并清理本轮写入的媒体对象。成功后失效导入用户的既有本地会话，页面显示替换及清理数量。

### 契约和技术决策（实施前需逐项按现行 Prisma/存储模型落实）

- 包格式升级为 `cook.data-snapshot.v2`，采用 ZIP 容器保存 manifest、数据 JSON 和去重后的图片对象；拒绝越界路径、重复路径、未知数据类别、单文件/总展开超限和清单与正文不匹配，读取压缩内容前先按 ZIP 声明大小拦截。
- 以业务类别映射白名单表集合；禁止用任意 Prisma delegate、任意 SQL 表名或客户端提交表集合。父表先写、子表先删，并显式刷新涉及自增 ID 的序列。
- 导出采用一致性数据库快照，避免多次查询跨越并发写入形成混合时点；媒体按资产存储 key 去重。
- 导入前预检外键、菜谱正文 JSON 食材/单位依赖和唯一键冲突；事务内替换数据。预览指纹绑定快照文件与目标类别当前数据，导入事务内复核，任一变化都要求重新预览。媒体写入与数据库事务需提供失败补偿；导入失败清理本次新对象，旧媒体只有确认无其他引用后才能清理。
- 任何选中类别都不得级联修改未选类别；存在未选类别引用将被清理记录时，预览报告阻断。
- 用户 ID 与手机号保持快照身份；目标已有同手机号但不同 ID 或 ID 被其他手机号占用时报告冲突，不自动重映射外键。
- 线上/测试规则及 SUPER_ADMIN、数字字符串 `Idempotency-Key` 保持服务端强制；导入请求幂等键结果必须绑定文件内容摘要和目标环境。

目标中已有手机号必须与快照 user ID 一致；同手机号不同 ID、或同 ID 绑定其他手机号都作为冲突阻止，不做自动 ID 映射。导入用户快照时清除目标用户的本地密码及微信绑定并撤销本地会话，用户之后可通过本地手机号授权登录并建立本地凭据。

若目标数据被所选类别清理、但仍被未选类别引用，预览阻止导入并指出依赖类别/记录数。所需记录若已随快照带入或目标已有则通过。

### 页面/API 草案

- 导出页展示十个类别和依赖说明；“用户及个人数据”作为单组选项；营养、单位等不默认必选。
- `GET /admin/system-data/export?categories=...` 返回 ZIP 附件；包包含 `manifest.json`、按类别组织的数据 JSON 和 `assets/<sha256>` 图片对象。
- `POST /admin/system-data/preview` 和 `/import` 接收 ZIP。预览按类别显示快照条数、目标覆盖条数、本地额外清理条数、媒体对象数，以及阻断原因；缺失依赖需显示类别、记录数和补选提示。
- 三个接口仅 SUPER_ADMIN 可用；导入要求数字字符串 `Idempotency-Key`。本功能不新增 Prisma 表、字段或 migration；升级到 `cook.data-snapshot.v2`，明确拒绝旧 v1 文件，避免将旧“包外保留”语义误用于快照替换。

### 数据类别关系与依赖

- 用户快照只包含当前用户业务所需数据表；关联表按 owner/父记录关系收集，认证/资金/运营记录不随行。用户 ID 与手机号是匹配依据，用户表中的 `password_hash / openid / unionid` 清空，`session_version` 增加；本地 `user_wechat_identities / auth_sessions / phone_change_sessions` 对所选用户重置。
- 用户的餐桌话题参与记录随用户快照复制，餐桌话题本身按测试环境现状保留；若线上参与记录引用的 topic ID 在测试环境不存在，预览按缺失依赖阻止导入。
- 系统菜谱快照包含 `recipes(is_inspiration=true)`、其被引用的 `recipe_content_versions` 与 assistant/nutrition/completeness/tag 子表；个人菜谱和其版本属于用户快照。
- 系统食材、单位、营养表严格按 owner 和 FK 拆分；营养/换算表的关联引用按食材 ID、单位 ID 和营养食品 ID 检查。
- 文章和栏目分别快照 `site_contents` 与 `site_content_channels`；文章栏目引用缺失时阻止导入。用户点赞属于用户快照。
- 依赖预览至少覆盖菜谱 -> 菜谱分类/正文版本/食材/单位、食材 -> 食材分类/单位/合并目标、营养关联 -> 食材/单位/营养食品、文章 -> 栏目、用户勋章 -> 勋章模板、餐桌话题参与记录 -> 测试环境已有话题，以及所有用户业务表 -> 用户/其父记录。
- 清理前检查未选表是否引用将删除的目标记录；有引用时保留现状并阻止整个类别替换，不能依靠数据库级联静默改写未选类别。

## 目标与确认范围

在后台使用一个统一 JSON 数据包手动导出、校验、预览和导入系统基础数据，先用于测试环境到线上，后续用于线上到测试环境。数据包格式版本固定为 `cook.system-data.v1`。

本轮包含：系统菜谱分类、系统菜谱当前正文及 Wiki/营养/质量快照、系统食材分类、系统食材、系统单位、营养食品及食材营养关联和单位换算。

明确排除：私房菜、个人食材、用户账号和其他用户私有数据；不做自动同步、增量版本历史、数据包缺失项删除和数据库级备份恢复。

## 业务流程与页面行为

- 导出：管理员从“基础数据同步”页面下载带 `schemaVersion` 和 `exportedAt` 的 JSON。
- 预览：选择不超过 10 MB 的 JSON；服务端校验格式、统计新增/匹配 ID 的记录，并提示个人数据 ID 冲突与不可变正文版本冲突。
- 导入：管理员确认预览后，服务端在一个事务中写入；任一唯一键、外键或内容冲突整体回滚。
- 覆盖规则：按 ID 新增或覆盖；数据包缺失的目标数据保留，不删除。
- 方向规则：必须配置 `SYSTEM_DATA_ENVIRONMENT=TEST|ONLINE`。线上仅允许导入测试数据一次；测试环境只接受线上数据包。
- 菜谱归属：不导出账号资料；系统菜谱写入时映射到目标环境公共内容池账号。
- 图片：图片 URL 保留原值，图片文件本身不进入 JSON 数据包。
- 权限：仅 `SUPER_ADMIN` 可访问；导入写操作使用数字字符串 `Idempotency-Key`。

## 实现边界

- API：`GET /admin/system-data/export`、`POST /admin/system-data/preview`、`POST /admin/system-data/import`。
- Admin：新增“基础数据同步”页，提供导出、选包校验、数量预览、冲突提示、确认导入和失败提示。
- 数据库：不新增表、字段、索引或 migration；导入完成后同步显式 ID 表的序列值。
- 事务：导入只写入同步包中的平台数据，不清理包外记录；不得触碰私房菜、个人食材及个人表。

## 已知限制

跨环境的图片文件没有随 JSON 移动。如果环境使用不同的图片对象存储，导入后的图片地址仍指向导出环境，需要另外迁移媒体文件。
线上部署需将 `SYSTEM_DATA_ENVIRONMENT` 配为 `ONLINE`，测试部署配为 `TEST`；未设置或值无效时同步接口拒绝操作。
