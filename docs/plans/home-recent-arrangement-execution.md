# 功能执行单：首页最近安排卡

## 目标

- 本功能要跑通的最小业务闭环：
  - 首页在存在“最近一顿、且还有下一步动作”的计划或饭局时，展示一张 `最近安排` 条件卡。
  - 用户看一眼首页，就能知道接下来这顿饭的时间、人数、菜数、缺口和下一步动作。
  - 用户点击卡片主动作后，进入统一餐次详情页继续推进，不在首页直接执行写操作。
- 对应 V1 范围：
  - `最近安排` 是首页摘要能力，不是新入口，不替代四宫格，不扩成消息流或任务中心。
  - 计划和饭局仍共用同一个餐次详情页；首页只前置“下一步做什么”的提醒。

## 本轮范围

- 小程序端：
  - `pages/home/index` 增加 `最近安排` 条件卡展示位。
  - 条件卡支持整卡跳转详情，主动作跳转到统一餐次详情页并聚焦对应区域。
  - 条件卡文案、状态和按钮统一由客户端本地映射，不把整段中文文案下放到接口。
- 后端 API：
  - 提供首页单卡摘要读取接口草案，首版只返回 `null` 或 1 条最近安排摘要。
- 后台管理：
  - 不涉及。
- 共享契约：
  - 新增首页单卡摘要读取契约草案。
  - 不改动现有 `GET /home-entries` 入口配置职责。

## 本轮不做

- 不把 `最近安排` 做成首页固定第五入口或四宫格新坑位。
- 不在首页直接执行确认菜单、出采购、开始做饭等写操作。
- 不做多卡轮播、历史安排列表、查看更多安排。
- 不在本轮冻结新的数据库表、持久化字段、索引或 migration。
- 不扩成通知中心、消息流、任务中心或通用首页工作台。

### 业务流程

- 用户目标：
  - 打开首页后，一眼知道最近这顿饭现在推进到哪一步，以及自己下一步该做什么。
- 触发条件：
  - 登录用户进入首页，且当前存在最近 `24` 小时内、或补位的 `24~36` 小时内的可推进计划/饭局。
- 主成功路径：
  - 用户进入首页 -> 首页读取最近安排摘要 -> 若存在候选则展示 1 张卡 -> 用户查看时间、人数、菜数、缺口和状态 -> 点击整卡进入详情，或点击主动作进入统一餐次详情页继续推进。
- 失败 / 阻断路径：
  - 当前没有候选安排 -> 首页不展示该卡。
  - 候选饭局/计划已取消、已彻底完成或当前用户无权读取 -> 接口返回 `null`。
  - 缺口事实当前不可靠 -> 卡片不展示具体缺口数，只保留更泛化的状态文案。
- 结束状态：
  - 首页至多展示 1 张最近安排卡；该卡只服务“看一眼就懂当前下一步”，不承担写入责任。
- 确认人 / 确认记录：
  - 2026-08-20 当前 Codex 会话内逐项确认，已确认命名、窗口、优先级、最小字段和动作方向。

### 页面行为

- 页面入口：
  - `apps/client/src/pages/home/index.vue`
- 展示内容及用途：
  - 条件卡标题：告诉用户“接下来是哪顿”。
  - 时间 / 人数 / 菜数：告诉用户这顿饭的基本规模。
  - 当前状态：告诉用户现在卡在哪一步。
  - 主动作：告诉用户现在该点什么。
- 用户操作：
  - 点击主动作：进入统一餐次详情页，并聚焦当前动作区域。
  - 点击卡片：普通进入统一餐次详情页。
- 加载 / 空态 / 失败态：
  - 加载中：首页卡位可展示轻骨架，但不阻塞其他首页内容。
  - 无候选：不展示该卡，不额外显示“暂无最近安排”空壳。
  - 接口失败：静默降级为不展示该卡，不影响首页其他区域。
- 成功后的页面变化：
  - 卡片本身不做写入态变化；真实状态变化来自用户在餐次详情页完成操作后，下次进首页或返回首页重新读取。
- 本流程不需要的页面数据：
  - 菜单明细列表
  - 投票明细
  - 冰箱明细
  - 购物清单明细
  - 实时参与人 UID
  - 带菜备注、内部备注或其他非首页必须事实

## 已确认产品结论

### 1. 命名与定位

- 首页这张卡正式命名为 `最近安排`。
- 它不是常驻首页工作台，也不是新入口；本质是统一餐次详情页的首页提醒投影。

### 2. 展示位置

- `最近安排` 放在首页四个快捷入口下方、买菜和冰箱区块上方。
- 不占 `MAIN / SIDE_TOP / SIDE_BOTTOM` 三张主卡，不占四宫格坑位。

### 3. 展示前提

- 首页最多只展示 `1` 张 `最近安排` 卡。
- 只有存在“最近一顿、且还有下一步动作”的计划或饭局时才展示。
- 没有候选时，首页不展示该卡，不补空壳。

### 4. 候选时间窗口

- 先看未来 `24` 小时内的候选安排。
- 若未来 `24` 小时内没有可展示候选，再补看未来 `24~36` 小时。
- 超过 `36` 小时不进首页该卡。

### 5. 饭局与计划优先级

- 在未来 `24` 小时窗口内，若同时存在饭局和计划候选，优先饭局。
- 在未来 `24~36` 小时窗口内，若同时存在饭局和计划候选，仍然优先饭局。
- 只有当前窗口内没有饭局候选时，才回退到计划。

### 6. 同类型候选排序

- 同类型候选先按状态优先级排序：
  - `TIME_UP_SHARE`
  - `READY_TO_COOK`
  - `PENDING_SHOPPING`
  - `PENDING_CONFIRM`
  - `EMPTY_MENU`
- 同级时按离当前时间更近排序。

### 7. 首页卡片最小信息

- `标题`
- `时间`
- `人数`
- `菜数`
- `当前状态`
- `主动作`

推荐固定结构：

1. 第一行：标题
2. 第二行：`时间 · 人数 · 菜数`
3. 第三行：当前状态
4. 底部：主动作

### 8. 首版字段口径

- 时间：显示该安排的最终开饭时间，例如 `今天 18:30`。
- 人数：
  - 饭局显示当前参与人数。
  - 个人计划首版固定显示 `1人`。
- 菜数：显示当前菜单项数。
- 缺口：
  - 若后端已有可靠缺口事实，则显示 `还差 X 样食材`。
  - 若当前没有可靠缺口事实，则不猜测，不拼装明细。

### 9. 首页状态口径

- 首页不新建持久化状态，只投影现有餐次事实和下一步动作。
- 首版固定 5 态：
  - `EMPTY_MENU`：有安排但菜单为空。
  - `PENDING_CONFIRM`：菜单已有菜，但尚未确认。
  - `PENDING_SHOPPING`：菜单已进入准备阶段，但仍有食材缺口或采购动作。
  - `READY_TO_COOK`：食材基本齐，可以开始做饭。
  - `TIME_UP_SHARE`：饭点已到、饭局已结束或进入回忆分享阶段。
- `recent-arrangement__status--head` 按 5 个状态各自的文案池随机展示，每个状态池 5 条；同一次小程序运行内，同一张卡同一状态首次出现后固定，冷启动后允许重新随机。
- `recent-arrangement__hint` 按 7 个显示分支随机展示：`EMPTY_MENU / PENDING_CONFIRM_WITH_GAP / PENDING_CONFIRM_NO_GAP / PENDING_SHOPPING_WITH_GAP / PENDING_SHOPPING_NO_GAP / READY_TO_COOK / TIME_UP_SHARE`，每个分支池 7 条；同一次小程序运行内，同一张卡同一分支首次出现后固定，`gapCount` 数字变化时只替换 `{n}`，不重新抽模板。
- `已取消` 不出现在首页卡片。

### 10. 主动作口径

- `EMPTY_MENU` -> `去加菜`
- `PENDING_CONFIRM` -> `确认菜单`
- `PENDING_SHOPPING` -> `去采购`
- `READY_TO_COOK` -> `开始做饭`
- `TIME_UP_SHARE` -> `分享回忆`
- 主动作按钮文案固定，不参与随机。

### 11. 跳转原则

- 首页不直接调用写接口。
- 首页所有动作都跳转到统一餐次详情页继续处理。
- 整张卡点击普通进入统一餐次详情页；主动作进入详情页后优先聚焦当前动作区域。

### 12. 统一餐次详情页跳转聚焦方案

- `最近安排` 不新开中间页，也不跳到四宫格场景页；统一进入现有 `pages_meal/detail/index`。
- 首页卡继续复用当前详情页已有真实入参：
  - `planItemId`
  - `planDate`
  - `eventId`（有饭局时带上，无饭局时省略）
- 在现有入参基础上，首版新增一个轻量聚焦参数：
  - `focus=menu | footer | shopping | assistant | memory`
- 该参数只服务页面进入后的视图聚焦，不表达写操作，不改变权限判断，不替代真实业务状态。
- 首页卡的动作与 `focus` 映射固定为：
  - `去加菜` -> `focus=menu`
  - `确认菜单` -> `focus=footer`
  - `去采购` -> `focus=shopping`
  - `开始做饭` -> `focus=assistant`
  - `分享回忆` -> `focus=memory`
- 详情页进入后只做最轻聚焦：
  - 滚动到对应区块
  - 高亮或短暂强调当前区块
  - 必要时自动展开对应面板
- 首版不做：
  - 自动触发写操作
  - 自动弹确认框
  - 自动生成助理
  - 自动生成采购清单
  - 自动生成回忆卡
- 若当前目标区块因真实业务状态不存在，详情页应降级为普通详情展示，不报错、不跳错页、不伪造中间状态。

## 接口契约

接口契约只能从本执行单已确认的业务流程、页面行为、权限和状态推导。首版先在本文冻结草案，待进入开发前再同步 `docs/api-contract.md`。

| 方法 | 路径 | 用途 | 权限 | 幂等 | 版本字段 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| `GET` | `/api/home/recent-arrangement` | 读取首页最近安排单卡摘要 | 当前登录用户 | 否 | 无 | 草案 |

建议返回：

```ts
interface HomeRecentArrangement {
  sourceType: "PLAN" | "EVENT";
  planItemId: UUID;
  planDate: string;
  eventId: UUID | null;
  title: string;
  scheduledAt: IsoDateTime | null;
  participantCount: number;
  menuCount: number;
  gapCount: number | null;
  status:
    | "EMPTY_MENU"
    | "PENDING_CONFIRM"
    | "PENDING_SHOPPING"
    | "READY_TO_COOK"
    | "TIME_UP_SHARE";
}
```

补充约束：

- 无候选时返回 `data: null`
- 不返回菜单明细、投票明细、冰箱明细、购物明细、参与人 UID、内部备注
- 不把按钮中文文案下放到接口，客户端本地映射
- 客户端跳转详情页时继续使用现有 `planItemId + planDate + eventId` 路由参数，并在需要时额外带 `focus`
