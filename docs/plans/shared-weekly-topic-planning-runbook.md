# 共享「每周灵感」周刊筹划操作手册

> 用途：后续由 Codex 按本文筹划共享周刊。每次运营提供目标周日日期和有效的 `Authorization: Bearer <后台token>`。默认 API base URL 为 `https://cms.trtst.com/api`；如果某次另行提供 API base URL，该次使用新地址。Codex 不自行判断或切换环境。
>
> 业务范围：只筹划平台共享周刊，不包含「餐桌话题」、个人周刊、家庭库存、个性化推荐或后台模型服务。筹划结果由 Codex 生成并通过后台预览校验；导入只创建草稿，不预约、不发布。
>
> 新版规则：每期围绕独立选题组织；不再填写旧版固定用途“推荐类别”。共享/个人表示周刊归属和访问范围，不作为每期选题类别。当前本手册只筹划共享周刊。

## 1. 每次任务的输入与默认值

运营提供：

1. 一个或多个周日日期，例如 `2026-10-18`，或连续周日列表 `2026-10-18、2026-10-25、2026-11-01`。
2. 有效的后台 Bearer token，账号必须具有 `SUPER_ADMIN` 角色。

默认规则：

- 一个周日筹划一期；多日期按给定顺序筹划，连续批次最多 12 期。
- 每个输入周日表示**以该日为首日的周日至周六**。例如 `2026-10-18` 对应 `2026-10-18` 至 `2026-10-24`。
- 默认计划发布时间是该周刊开始日周日 00:00，时区为 `Asia/Shanghai`。上例为 `2026-10-18 00:00 +08:00`。
- 日期必须是周日；批次日期必须每隔 7 天连续。日期不符合时停止生成并指出日期问题，不自行猜测修正。
- 如果输入的是日期范围，按范围内的周日逐期生成；最多 12 期。不能唯一确定周日列表时再询问运营。

日期对应关系：

| 输入周日 | 周刊周期（周日至周六） | JSON `plannedPublishAt` |
| --- | --- | --- |
| 2026-10-18 | 2026-10-18 至 2026-10-24 | 2026-10-18 00:00（上海时间） |
| 2026-10-25 | 2026-10-25 至 2026-10-31 | 2026-10-25 00:00（上海时间） |

## 2. 环境与接口

### API base URL

```text
默认 API base URL: https://cms.trtst.com/api
```

每次任务默认使用上述地址。如果运营本次明确提供了另一个 `API base URL`，则本次改用该地址和对应 token。不得从域名推断环境，也不得改用仓库配置、历史会话或猜测出的其他地址。默认读取统计、搜索候选并调用只读预览；除非本次明确要求导入，否则不创建草稿、不预约、不发布。

所有请求使用：

```http
Authorization: Bearer <本次任务提供的后台token>
X-Platform: admin-web
X-Admin-Version: <当前 Admin 版本>
X-Admin-Build: <当前 Admin build>
```

Admin API 除 token 和 `SUPER_ADMIN` 角色外，还经过客户端版本门禁。直接调用时必须带以上 Admin 请求头：`X-Platform` 固定为 `admin-web`；版本和 build 使用当前 Admin 部署的值（仓库默认值为 `0.1.0` 和 `1`，分别可由 `VITE_ADMIN_VERSION`、`VITE_ADMIN_BUILD` 覆盖）。服务端最低版本由 `ADMIN_MIN_SUPPORTED_VERSION` 和 `ADMIN_MIN_SUPPORTED_BUILD` 决定；如果当前 Admin 部署值低于服务端最低值，应停止并更新 Admin 版本信息，不要伪造更高版本绕过门禁。

错误判断按响应体的业务 `code` 和 `message`，不要只看 HTTP 状态码。API 异常过滤器可能把业务错误包装成 HTTP 200：`code: 426` 且提示“当前版本过低”表示平台/版本/build 请求头缺失或未达到服务端最低值，不是 token 失效；`code: 401` 表示 token 缺失或无效；`code: 403` 表示账号没有所需角色。

发送带 token 的请求前先检查目标 URL 和方法。若出现 `ENOTFOUND`、连接超时、TLS 错误或 `curl` 的 HTTP 状态为 `000`，表示请求没有取得 HTTP 响应，不能据此判断接口、方法或权限有问题。DNS/路由可能因 Codex 命令执行环境与运营本机不同而不同；在不改变 API base URL 的前提下，检查当前执行环境的解析与网络访问能力，并使用获准的网络执行方式重试。不要把本机解析出的私有 IP 写进 URL、绕过 TLS/Host 校验、切换环境或改用其他凭证。若当前环境仍无法访问，报告具体的解析/连接错误并停止。

服务端必须同时验证 token 和 `SUPER_ADMIN` 角色。遇到 401/403、网络目标不匹配或环境不清楚时停止，不尝试其他凭证或环境。

### 统计读取与重建

读取当前预计算统计快照：

```http
GET /admin/home-topics/statistics
```

首次使用新统计口径前，本次目标 API 必须已部署核心食材过滤逻辑，并已重建一次快照。若接口没有快照，可调用重建接口后再读取：

```http
POST /admin/home-topics/statistics/rebuild
```

菜谱库变化不频繁；已有快照时默认直接读取，不为每次选题重复重建。每次任务记录响应的 `snapshotId` 和 `generatedAt`，并将其写入 JSON 的 `statsSnapshotId` 和 `generatedAt`。

统计中的核心食材只包括匹配到 ACTIVE 系统食材分类 `5001–5004` 的食材：蔬果菌菇、肉禽蛋、水产海鲜、豆乳制品。米面杂粮、调味料、干货腌制、酒水饮料、待归类和没有食材 ID 的条目不进入核心食材/主要食材统计。现有 API 字段 `facets.allIngredients` 在业务上按“核心食材”理解；后台显示名称为“核心食材”。

### 候选菜谱搜索

复用现有周刊后台菜谱搜索，不另建搜索流程：

```http
GET /admin/home-topics/recipes
```

支持参数：

| 参数 | 用途 |
| --- | --- |
| `keyword` | 搜索菜名、故事、食材等文本 |
| `ingredient` | 按食材筛选 |
| `cuisine` | 按已确认菜系筛选 |
| `dishStyle` | 按已确认菜式/做法筛选 |
| `page` | 页码，从 1 开始 |
| `pageSize` | 每页条数，最多 100 |

搜索必须遍历 `hasNext` 分页，不能只凭第一页判断候选是否充足。结果只作为候选；最终 JSON 必须使用接口返回的 `recipeId` 和固定 `sourceVersionId`。不自行拼 ID、不编造菜谱、不将未确认标签说成已确认事实。

## 3. 选题和选菜规则

按以下优先顺序完成每期编排：

1. **公开资格**：仅使用接口当前返回的、可公开的系统灵感菜谱。
2. **主题适配**：先围绕目标周拟定一个清楚、具体、能由候选菜谱支撑的主题，再筛选菜谱；不能为凑主题硬套不相关菜。
3. **七日覆盖**：周日至周六每天至少一道菜。每天菜量可不同，不设固定菜量；一周总菜量以内容完整且不重复为准。
4. **整周变化**：检查核心食材、菜系、菜式/做法、菜品角色和难度/时长分布；避免连续多天同类菜、同种主要食材或相似做法扎堆。多个周刊组成批次时，尽量避免跨期重复菜谱。
5. **季节与普遍可做性**：按北京/上海和目标周日期推断当季特点，把时令性作为选题参考，不要求每期必须出现特定时令食材。优先选择做法清楚、普通家庭容易理解和完成的菜。
6. **理由准确**：每道菜的推荐说明要能由菜谱返回内容支持，简短说明它如何呼应主题、食材或做法。不得编造营养、安全、口味或烹饪事实。
7. **共享边界**：不考虑任何家庭的冰箱、已有食材、忌口或个人偏好；这些属于未来个人周刊逻辑。
8. **避免重复**：同一期内菜谱 ID 不得重复；同一批次跨期菜谱 ID 也不得重复。候选不足时标记该期未完成并报告缺口，不用重复菜或虚构菜补齐。

统计只提供全库分布参考，不能代替逐道候选搜索，也不能据统计数字推断某一道菜仍可公开。

## 4. JSON 结构和字段要求

输出一个可粘贴到后台的 JSON 对象，`schemaVersion` 固定为 `2`，批次包含 1 至 12 个连续周刊。JSON 中只放菜谱数据和计划内容，不放 token、Authorization header 或其他凭证。

```json
{
  "schemaVersion": 2,
  "statsSnapshotId": "统计接口返回的 snapshotId",
  "generatedAt": "统计接口返回的 generatedAt",
  "issues": [
    {
      "periodStartDate": "2026-10-18",
      "plannedPublishAt": "2026-10-18T00:00:00+08:00",
      "title": "不超过20字",
      "subTitle": null,
      "description": "不超过120字的专题描述",
      "themeRationale": "不超过500字的选题依据，仅供预览",
      "days": [
        {
          "weekday": "SUNDAY",
          "items": [
            {
              "recipeId": 10000001,
              "sourceVersionId": 10000002,
              "sortOrder": 1,
              "recommendNote": "不超过60字的菜品推荐说明"
            }
          ]
        }
      ]
    }
  ]
}
```

上例只展示 JSON 形状，示例 ID 不可直接导入。正式 JSON 必须把 `days` 补齐为七个不同的 `weekday`：`SUNDAY`、`MONDAY`、`TUESDAY`、`WEDNESDAY`、`THURSDAY`、`FRIDAY`、`SATURDAY`；每一天的 `items` 至少一道菜。`sortOrder` 从 1 开始按当天顺序递增。

字段约束：

- `periodStartDate` 必须为周期周日，格式 `YYYY-MM-DD`。
- `plannedPublishAt` 默认是该周期开始日周日 00:00（上海时间），使用带 `+08:00` 的 ISO 时间。
- `title` 1–20 字；`subTitle` 可为 `null`，非空时最多 40 字。
- `description` 为 1–120 字；`themeRationale` 为 1–500 字。
- `recipeId`、`sourceVersionId`、`sortOrder` 都是正整数；菜谱版本 ID 必须与搜索结果完全一致。
- `recommendNote` 可为 `null`，非空时最多 60 字；建议提供简短、具体、可核对的推荐理由。
- 每期最多 200 道菜；同一期及整个批次均不得重复 `recipeId`。

## 5. 预览和导入

### 默认交付

Codex 完成统计读取、候选搜索和编排后，生成 JSON，并调用预览接口检查每一期。预览只读，不写后台数据：

```http
POST /admin/home-topics/import/preview
Authorization: Bearer <本次任务提供的后台token>
Content-Type: application/json
```

预览逐期核对周期、七天覆盖、重复菜谱、已有周期冲突、统计快照 ID、菜谱当前公开状态和 `sourceVersionId`。只将全部校验通过的完整 JSON 作为“可导入草稿”交付；失败时修正可从搜索结果确认的问题后重新预览。若快照 ID 已变化，重新读取统计并基于新快照生成 JSON。

最终回复应包含：每期日期范围、主题、菜谱数量、预览结果、未解决问题，以及可复制/保存的完整 JSON。不得把“预览通过”说成“已经导入”或“已经发布”。

### 导入边界

除非本次请求明确要求导入，否则停在“预览通过并交付 JSON”。如运营明确要求导入，才调用：

```http
POST /admin/home-topics/import
Authorization: Bearer <本次任务提供的后台token>
Idempotency-Key: <数字字符串>
Content-Type: application/json
```

导入会逐期重新校验并创建 `DRAFT`。无效期或已有周期冲突的期不覆盖；其他有效期可独立导入。导入不预约、不自动发布；后续由运营在 Admin 中审稿并安排发布时间。

**发布和预约都保留草稿当前周期，预约时间本身不会重算周期：**

- 对 `DRAFT` 执行 Admin“立即发布”（`DRAFT -> PUBLISHED`）时，服务端保留当前 `periodStartDate` 并清除预约时间。
- 定时发布只设置 `scheduledPublishAt`，不根据预约时间重新分配周期。新期默认预约时间为周期开始日周日 00:00（`Asia/Shanghai`），后台允许按实际需要调整。
- 定时发布前核对编辑页显示的“周期开始日”与 JSON `periodStartDate` 一致；保存预约后再核对返回的周期、状态和版本。遇到 409 时检查目标周期是否已有其他周刊。

请求失败后如需重试导入，按接口幂等规则复用同一个 `Idempotency-Key`。

## 6. Token 和数据安全

- Token 只用于本次请求的 `Authorization` header，不回显、不写文件、不写进 JSON、日志、代码、命令输出或变更记录。
- 不把 Token 发送给外部模型服务或浏览器端；不读取数据库直连凭证。
- 所有统计、搜索、预览、导入请求都使用同一授权边界：有效 Admin Bearer token 且角色为 `SUPER_ADMIN`。
- 只操作默认 API base URL 或运营本次明确提供的覆盖地址，并使用与之匹配的 token；环境或 token 不匹配时停止，不改用其他地址或凭证。
- 接口返回 401/403、候选数据与快照不一致、服务端环境不符或网络错误时停止，报告明确错误；不换环境、不绕过权限、不猜测替代数据。

## 7. 每次任务完成检查表

- [ ] 输入日期均为周日，日期范围和批次顺序明确。
- [ ] 成功读取统计快照，记录 `snapshotId` 和 `generatedAt`；必要时重建后重新读取。
- [ ] 使用当前可公开系统灵感菜谱完成分页搜索，并保留来源 `recipeId + sourceVersionId`。
- [ ] 主题符合目标周季节背景和候选菜谱；菜单七天齐全，整周有变化。
- [ ] 同一期及整个批次没有重复菜谱 ID；推荐说明可从菜谱内容核对。
- [ ] JSON 符合 schemaVersion 2 和字段长度、枚举、日期约束。
- [ ] 后台逐期预览通过；预览状态、导入状态和发布状态没有混淆。
- [ ] 如本次要求预约发布，预约时间为目标周期开始日周日 00:00（上海时间），且预约后核对了周期、状态和版本；需要保留目标周期时未使用“立即发布”。
- [ ] Token 未写入任何文件、JSON 或最终回复。
