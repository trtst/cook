# API 与数据库设计规则

## 一、定位与适用范围

本文是下一餐项目设计前后端接口、字段、数据库表、约束、查询、缓存和迁移时必须执行的工程规则。

适用于：

- 新增或修改 API 路径、请求 DTO、响应 DTO 和错误语义。
- 新增或修改 Prisma Model、字段、枚举、索引、外键和 migration。
- Client、Admin 的请求类型、Store 持久化和接口缓存。
- 涉及权限、并发、幂等、审计、存储、上传和第三方回调的实现。

文档职责：

- 本文规定“接口和数据库应该如何设计”。
- `api-contract.md` 记录“当前具体接口是什么”。
- 领域文档规定“业务事实和业务规则是什么”。
- OpenAPI、三端本地类型和实现必须与已确认契约一致。

任何实现便利、减少请求次数或临时页面需求，都不能覆盖本文的安全、所有权、数据库约束和最小实现规则。

## 二、总原则

1. 最少字段：只接收和返回当前操作真正需要的字段。
2. 最小权限：调用方只获得当前资源和当前操作所需权限。
3. 单一事实来源：同一可变事实只能有一个权威写入 owner。
4. 可预测成本：每个接口必须有可说明的最大查询成本和响应大小。
5. 数据库兜底：唯一性、引用完整性和简单不变量必须由数据库最终保证。
6. 服务端权威：权限、额度、价格、状态机和安全结论不得交给前端计算。
7. 模型分离：数据库 Model、内部策略对象和公共 DTO 不得直接复用为同一个类型。
8. 默认不预留：没有确认需求时，不增加占位字段、通用 JSON、兼容分支或抽象中心。
9. 默认不缓存：先证明查询成本和访问频率，再设计缓存与失效规则。
10. 默认不兼容旧模型：项目未上线阶段直接切换已确认契约，不保留旧字段 fallback。

## 三、设计顺序

新增接口、字段或表之前，必须依次确认：

1. 使用场景：哪个调用方在什么流程中使用。
2. 领域 owner：字段和数据属于哪个领域、哪个主体。
3. 主事实：数据是事实、配置、计算结果、缓存还是历史快照。
4. 生命周期：如何创建、修改、失效、删除和审计。
5. 权限：谁可读、谁可写、无权时返回什么。
6. 并发：是否可能重复、覆盖、超限或乱序。
7. 查询：真实筛选、排序、分页和关联是什么。
8. 约束：哪些规则必须进入外键、唯一、Check 或事务。
9. 契约：冻结请求、响应、错误语义和最大数据量。
10. 实现：最后才确定 Controller、Service、Prisma 和前端 Store。

不能从页面字段列表或现有数据库列反推公共接口。

### 3.1 业务纵切开发门禁

业务功能必须按以下顺序推进，不得跳步：

```text
业务流程 -> 页面行为 -> 权限和状态 -> 最小接口 -> 最小数据表/约束 -> 实现 -> 真实验收
```

进入下一阶段前必须满足：

1. 业务流程：明确用户目标、触发条件、主成功路径、失败路径和结束状态。
2. 页面行为：明确入口、展示、操作、加载、空态、失败态和成功后的页面变化；页面字段清单不能直接成为接口字段清单。
3. 权限和状态：明确数据 owner、读写主体、对象状态机、无权语义、额度、并发和幂等要求。
4. 最小接口：只为上述已确认行为定义请求、响应和错误；一个字段必须能对应一个已确认用途。
5. 最小数据表/约束：只持久化不能从现有主事实可靠推导的数据，只为真实一致性和查询增加外键、唯一、Check 和索引。
6. 实现：契约和数据边界确认后才修改 DTO、OpenAPI、Service、Prisma、migration 和三端本地类型。
7. 真实验收：使用真实接口和真实状态验证成功、失败、权限、并发或幂等路径，不能以类型检查或 mock 通过代替业务验收。

以下内容都不是业务已经确认的证据：

- 仓库中已经存在的接口、字段、表、枚举或页面。
- 历史方案、旧 OpenAPI、旧 migration 或原型字段。
- 为减少请求数、方便实现或预留未来而提出的结构。

开发现有业务时，已有接口和表只能作为候选实现。只有与当前确认流程、权限、状态和最小数据需求完全一致时才可复用；否则应修改、删除或保持不接入。未确认业务流程和页面行为时，禁止新增公共接口、数据库表和 migration。

## 四、API 职责规则

### 4.1 查询接口

一个查询接口只承担一种职责：

- 列表：返回摘要和分页信息。
- 详情：返回一个对象的完整业务内容。
- 状态：返回明确状态结论。
- 用量：返回计数、额度、状态和计算时间。
- 账本：返回可追溯的分页明细。
- 配置：返回客户端确实需要的公开配置。

禁止在一个 `current`、`context`、`overview` 或页面接口中混合用户、关系、权限、用量、策略、历史和明细。

权限边界、生命周期、变化频率或缓存策略不同的数据，默认拆分接口。

### 4.2 写接口

写接口只接收完成操作所需字段。服务端可以确定的内容不得由客户端提交，包括：

- 当前用户、所有者和操作者 ID。
- 当前角色、套餐和权限结论。
- 服务端价格、额度、成员数和空间状态。
- 可由文件或主事实计算的大小、哈希和统计。
- 与本次操作无关的完整对象。

请求 DTO 使用白名单映射，禁止把请求体直接传给 ORM：

```ts
// 禁止
prisma.user.update({ data: body });

// 正确
prisma.user.update({
  data: {
    nickname: body.nickname
  }
});
```

所有可安全重试的写操作必须携带 UUID `operationId`。共享可变对象存在覆盖风险时必须提交预期 `version`。

### 4.3 响应字段

每个响应字段必须能说明用途：展示、判断、后续操作、并发控制或分页。

响应必须遵守：

1. 不直接返回 Prisma Model 或数据库查询结果。
2. 不暴露内部主键、外键、密钥、哈希、内部备注和异常堆栈。
3. 用户身份默认使用公开 `uid` 或最小摘要。
4. 列表默认不返回大文本、大 JSON、历史、账本和完整子对象。
5. 大数组必须分页，并设置服务端最大 `pageSize`。
6. 时间统一使用 ISO 8601，实时计算结果带 `calculatedAt`。
7. 空值统一使用 `null`，不混用空字符串、缺失字段和特殊数字。
8. 同一事实不同时返回旧字段、新字段和多个近义字段。
9. 内部策略解析对象不得作为客户端或后台公共 DTO。
10. 暂未开放的能力返回明确 `503`，不得返回虚假成功或半成品数据。

## 五、字段规则

每增加一个字段，必须回答：

1. 字段 owner 是谁。
2. 它是主事实、计算结果、缓存还是历史快照。
3. 是否必须持久化，能否从主事实重算。
4. 谁可以读取和修改。
5. `null` 的准确含义。
6. 创建、更新、失效和删除时机。
7. 是否包含隐私或安全信息。
8. 是否参与筛选、排序、唯一或关联。

命名必须表达语义：

- 当前事实：`usedBytes`、`validUntil`。
- 可重算缓存：`usedBytesCache`。
- 历史快照：`sourceName`、`nameAtCreated`。
- 计算时间：`calculatedAt`。
- 生命周期时间：`expiredAt`、`deletedAt`。

禁止使用边界不明的 `currentData`、`extra`、`metadata`、`statusInfo`、`config` 或 `dataJson` 承载未完成建模。

布尔字段必须表达明确事实，如 `isOwned`、`canEdit`、`hasNext`。存在三个及以上互斥状态时使用枚举，不堆叠多个布尔字段。

## 六、数据库表规则

### 6.1 表边界

一张表只表达一种主事实。实体、成员关系、邀请、授权、账本、审计、内容版本和历史快照按生命周期与约束拆分。

常规业务表只保留实际需要的：

```text
id
必要业务字段
外键
status（确实存在状态机时）
version（确实存在并发覆盖时）
createdAt
updatedAt
```

只有存在恢复、审计或法规留存需求时才增加软删除。不要习惯性增加 `deletedAt`、JSON 扩展字段或冗余统计。

### 6.2 主键与公开标识

1. 内部主键使用 UUID、ULID 或数据库整数主键。
2. 防止遍历或隐藏注册量时，不向客户端暴露连续自增主键。
3. 公开编号与数据库主键分离。
4. 手机号、用户名等可变字段不能作为主键。

### 6.3 外键、唯一和 Check

1. 真实关系必须有外键，不依靠应用代码约定引用存在。
2. 外键删除行为必须明确选择拒绝、级联或置空。
3. 核心业务事实默认不静默级联删除。
4. 并发下不允许重复的规则必须使用数据库唯一约束。
5. 简单行内不变量使用 Check 约束。
6. 跨表动态规则由事务、锁和服务端校验共同保证。

典型约束：

```sql
UNIQUE (user_id, dining_group_id)
UNIQUE (user_id, operation_id)
CHECK (used_bytes >= 0)
CHECK (ends_at IS NULL OR starts_at < ends_at)
```

禁止只通过“先查询、再插入”保证唯一性。

### 6.4 枚举与 JSON

枚举只用于稳定、有限、互斥的状态。自由标签、展示文案、管理员配置和多选属性不使用数据库枚举。

删除业务模型时同步删除无引用的枚举、字段、索引和类型，避免旧概念继续成为隐性契约。

JSON 只用于：

- 不参与筛选和关联的结构化快照。
- 不可变内容版本。
- 外部系统原始响应。
- 低频读取的扩展配置。

需要频繁筛选、排序、关联、约束或单独更新的数据必须拆成列或子表。

## 七、状态与生命周期

1. 状态字段必须有明确状态机和允许的转换。
2. 每个状态必须定义允许的读写操作。
3. 状态转换只能经过领域 Service，不能由客户端任意赋值。
4. 关键转换记录操作者、时间、原因和必要审计。
5. 能由 `expiresAt` 稳定推导的状态优先计算，不重复保存事实。
6. 只有需要冻结历史结论时才保存状态快照。
7. 软删除只用于真实恢复、审计或留存需求，否则直接删除。

## 八、安全规则

### 8.1 鉴权与对象授权

每次请求分别检查：

1. 是否登录。
2. 是否有权读取或修改这个具体对象。
3. 对象当前状态是否允许操作。
4. 是否超过服务端额度或安全限制。

查询时尽量把所有权放进数据库条件：

```ts
where: {
  id: resourceId,
  userId: currentUserId
}
```

无权得知资源是否存在时返回 `404`；已确认资源存在但无操作权限时返回 `403`。CORS 和前端隐藏按钮都不是权限边界。

### 8.2 敏感数据

响应和日志不得包含：

- 密码、密码哈希、完整 token 和一次性原始凭证。
- 支付密钥、数据库连接串和第三方密钥。
- 无必要的手机号、地址、身份信息和用户私有内容。
- SQL、数据库错误、内部异常堆栈和服务端文件路径。

密码使用经过评审的慢哈希算法；一次性 token 只保存哈希。日志必须脱敏，并限制原始请求体和超长内容。

### 8.3 输入与滥用防护

所有输入校验类型、长度、范围、格式、枚举、数组上限和空值语义。

外部 URL、回调地址和服务端抓取必须防 SSRF。上传必须校验真实文件类型、输入大小、输出大小、尺寸、内容安全和元数据清理。

登录、验证码、邀请、分享、上传和高成本查询必须根据风险配置限流。请求体、分页大小和批量条目数必须有硬上限。

## 九、事务、并发与幂等

以下操作必须使用事务：

- 同时修改多个表或对象。
- 创建、结束或调整关系。
- 扣减额度、库存或次数。
- 接受邀请、确认支付和关键状态转换。
- 同时写业务记录、审计和 Outbox。

共享可变对象使用乐观锁：

```sql
UPDATE objects
SET version = version + 1
WHERE id = ? AND version = ?;
```

未更新到记录时返回 `409`。动态上限在并发下可能突破时，必须使用行锁、唯一约束或等价数据库机制，不能只依赖事务前查询。

幂等记录必须绑定操作者和操作语义；同一 `operationId` 重试返回第一次结果，不得重复产生副作用。

## 十、性能规则

1. 列表必须分页并限制最大 `pageSize`。
2. 查询只选择响应需要的列。
3. 禁止默认加载完整关联树、大 JSON、图片内容和历史明细。
4. 禁止循环查询形成 N+1；使用批量查询、聚合或明确预加载。
5. 索引必须对应真实接口的筛选和排序，不为假设需求提前建索引。
6. 写多读少的表控制索引数量，避免放大写入成本。
7. 昂贵实时统计拆成独立用量接口，不塞进高频基础接口。
8. 精确总数成本过高且页面不需要时，只返回 `hasNext`。
9. 批量处理和数据回填必须分批，避免长事务和长时间锁表。
10. 首屏请求数应受控，但不得为了减少请求把不同领域合并成大接口。

复合索引通常按“等值过滤、范围过滤、排序字段”的实际查询顺序设计。每个新增索引都必须能指出对应接口和查询。

## 十一、缓存规则

默认不增加缓存。只有同时满足以下条件才允许增加：

1. 查询成本经过验证确实较高。
2. 请求频率经过验证确实较高。
3. 数据允许明确时间范围内的过期。
4. 缓存键包含必要的用户和权限范围。
5. 写入方和失效机制明确。
6. 缓存丢失后可以从主事实重建。

缓存不能成为权限、金额、成员关系、授权或状态判断的唯一来源。禁止缓存完整 token、跨用户未隔离数据和无法解释更新时间的全局聚合对象。

## 十二、迁移规则

1. 不修改已经执行或作为历史来源的 migration。
2. 所有变更使用新的前向 migration。
3. 大表变更采用“扩展、回填、切换、删除”。
4. 新增非空字段时先允许空或提供可证明安全的默认值。
5. 数据回填必须分批，并评估锁、事务和部署时间。
6. 删除字段前确认代码、任务、报表、索引和外部调用均无引用。
7. migration 必须说明数据风险、失败处理和恢复方式。
8. Prisma Schema、migration、数据库约束、DTO、OpenAPI 和文档必须一致。

## 十三、最小实现规则

首版只实现当前确认需求：

- 只建当前使用的表。
- 只加当前读写的字段。
- 只实现当前流程需要的接口。
- 只为真实查询建立索引。
- 只为真实并发场景增加 `version`。
- 只为真实重试场景增加幂等。
- 未开放能力明确返回 `503`，不做半套实现。
- 不提前建设通用权限中心、聚合上下文或泛化缓存层。
- 不保留旧字段 fallback、双写和兼容 DTO。
- 不用 `extraJson`、占位表或预留枚举代替需求确认。

最终判断：如果删除某个字段、接口、表、索引或抽象后，当前确认需求仍然成立，那么它现在就不应该存在。

## 十四、提交前强制检查

涉及 API、DTO、Prisma、SQL 或 migration 的改动，提交前必须逐项回答：

1. 接口是否只有一个职责。
2. 是否接收或返回了不必要字段。
3. 是否直接暴露数据库 Model 或内部策略对象。
4. 每个可变字段是否只有一个权威来源。
5. 前端是否在计算服务端权限、额度或状态结论。
6. 写接口是否存在批量赋值风险。
7. 是否校验具体对象所有权和当前状态。
8. 并发下是否可能重复、覆盖、超限或乱序。
9. 外键、唯一和 Check 是否覆盖数据库可保证的不变量。
10. 查询是否分页、限量并只选择所需字段。
11. 是否存在 N+1、无索引筛选或无界响应。
12. 每个新增索引是否对应真实查询。
13. 敏感数据是否可能进入响应、日志或缓存。
14. 是否需要事务、`operationId`、`version`、审计或 Outbox。
15. migration 是否前向、安全、可恢复且不改写历史。
16. 是否增加了未经需求证明的字段、表、状态或抽象。
17. 是否可以继续缩小差异而不破坏确认需求。

任何一项无法回答时，停止实现并回到契约、业务事实或数据库证据确认。
