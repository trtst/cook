# 工程架构

## 概述

本文定义前后端工程的默认结构边界。

目标不是把架构做复杂，而是让前端页面、组件、状态、请求，以及后端接口、服务、数据源、处理逻辑各自职责清楚，避免代码一边写一边漂移。

## 前端默认分层

### 页面层

- 目录：`pages/`、`views/`
- 职责：
  - 接收路由参数
  - 组织页面状态
  - 发起页面级请求
  - 编排主交互流程
  - 决定当前页面使用哪些组件和共享能力

页面层可以保留主流程编排，不强求做“超薄页面”。

### 组件层

- 目录：`components/`
- 职责：
  - 承载单一 UI 职责
  - 接收明确输入
  - 抛出明确事件
  - 维护组件内部局部状态

组件层不负责页面级路由组织，不负责底层请求细节，不承接跨区域业务编排。

### 状态层

- 目录：`store/`
- 职责：
  - 承载明确的共享状态
  - 管理跨页面可复用状态
  - 收口状态持久化、恢复、清理规则

不是所有状态都进入 `store`。

临时页面状态、局部 UI 状态，默认留在页面或组件内部。

### 请求层

- 目录：`apis/`
- 职责：
  - 暴露业务语义接口
  - 统一请求入口
  - 收口请求配置、鉴权、错误处理
  - 处理参数兼容、字段兜底、历史口径归一

页面不直接写底层请求细节。

### 工具层

- 目录：`utils/`
- 职责：
  - 提供稳定的纯辅助方法
  - 承载通用转换逻辑
  - 承载无页面归属的基础能力

工具层不承载页面编排，不承载共享业务决策。

## 前端推荐补充层

### 页面私有辅助层

- 目录：页面目录下的 `helpers/`、`composables/`
- 职责：
  - 拆分当前页面内部已变长但仍属于页面职责的逻辑
  - 保持页面主文件可读
  - 不过早提升为全局共享模块

优先抽页面私有 helper，再决定是否升级为共享能力。

### 布局层

- 目录：`layouts/`
- 职责：
  - 共享外层结构
  - 统一页面骨架
  - 统一头部、底部、容器级布局能力

布局层不承载具体业务流程。

## 依赖方向

### 前端依赖方向

推荐方向：

`pages -> components / store / apis / utils`

`components -> utils`

`store -> apis / utils`

`apis -> utils`

规则：

1. 页面可以依赖组件、状态、请求、工具。
2. 组件不反向依赖页面。
3. 请求层不依赖页面和组件。
4. 工具层不依赖页面、组件、状态。
5. 状态层不依赖页面组件，只依赖共享能力。

### 后端依赖方向

推荐方向：

`api/handler -> service -> datasource/repository`

`service -> processor/parser/model`

`datasource/repository -> model/schema`

规则：

1. 接口入口不直接依赖具体数据源实现。
2. 服务层负责业务编排，不负责协议包装。
3. 数据源层不反向依赖接口层。
4. 处理逻辑和解析逻辑不反向依赖接口入口。
5. 配置读取集中处理，不散落在业务流程里。

## 数据与交互流

### 前端默认流程

1. 页面接收路由参数。
2. 页面决定是否读取共享状态。
3. 页面调用 `apis/` 获取或提交数据。
4. 页面整理当前页面所需数据。
5. 页面将稳定输入传给组件。
6. 组件抛出明确事件。
7. 页面决定是否更新本地状态、共享状态或继续调用接口。

### 后端默认流程

1. 接口入口接收请求参数。
2. 参数校验层确认字段、类型和范围。
3. 服务层编排业务流程。
4. 数据源层读取或保存数据。
5. 处理层完成清洗、转换或模型处理。
6. 服务层返回稳定业务结果。
7. 接口入口统一包装返回结构。

## 前后端接口边界

1. 前端只消费稳定 API，不感知后端内部数据源。
2. 后端统一对外暴露标准化字段，不把数据库表名、文件路径或第三方字段直接泄露给前端。
3. 前端组件层不直接处理 `code`、`serverTime`，统一由请求封装层消化。
4. 后端接口入口不为某个页面临时拼装特殊协议，通用协议应先写清再实现。

## 抽离规则

### 前端抽离规则

以下情况优先留在页面内：

1. 只服务当前页面。
2. 需求还在快速变化。
3. 复用尚未真实发生。
4. 逻辑虽然长，但边界仍然明确属于页面。

以下情况可以考虑抽离：

1. 已经出现真实复用。
2. 页面文件开始出现多段相互独立职责。
3. 某块逻辑已经形成稳定输入输出。
4. 抽离后边界会更清楚，而不是更模糊。

### 后端抽离规则

以下情况优先留在服务内部或局部模块内：

1. 只服务单一业务流程。
2. 数据源切换尚未真实发生。
3. 处理逻辑还在快速变化。
4. 当前抽离只会增加层级，不会让边界更清楚。

以下情况可以考虑抽离：

1. 已经存在文件、数据库、远程接口、mock 等多种数据源。
2. 同类参数校验、返回包装或处理逻辑开始重复出现。
3. 业务处理已经形成稳定输入输出。
4. 抽离后能更清楚地区分协议层、业务层和数据层。

## 明确不做

1. 不为了“架构完整”强行加层。
2. 不新增空泛中间层，如 `manager`、`adapter`、`serviceCenter`。
3. 不把单次使用逻辑提前公共化。
4. 不把页面主流程拆碎到难以追踪。
5. 不把请求兼容逻辑散落到页面和组件里。
6. 不把读取、清洗、处理、保存、返回拼装全部塞进一个后端接口函数里。

## 一句话规则

架构的目标不是层数更多，而是职责更清楚，主流程更好找，接口更稳定，后续更好改。
