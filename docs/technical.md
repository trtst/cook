# 工程技术规则

## 目标

1. 保持实现易于理解。
2. 保持边界稳定。
3. 保持改动易于验证。
4. 让项目对下一位维护者仍然可维护。

## 技术栈

### 小程序端技术栈

- 框架：uni-app + Vue 3
- 语言：TypeScript
- 状态管理：Pinia
- 构建目标：mp-weixin
- 构建工具：Vite / HBuilderX，以实际工程配置为准
- 平台能力：业务代码不直接调用 `wx.*`，统一通过 `apps/client/src/platform/uni.ts` 适配层
- API 类型：在 `apps/client` 内按接口文件维护，以契约文档和 OpenAPI 为准
- 版本约束：以 `package.json` 和锁文件实际版本为准
- 小程序工程规则：见 `docs/uniapp.md`
- 小程序落地基线：见 `docs/uniapp-architecture.md`

### 后端技术栈

- 语言：TypeScript
- 服务框架：NestJS
- 运行时：Node.js 20+
- 数据库：PostgreSQL 15+
- ORM：Prisma 5.22.0
- 缓存与队列：Redis + BullMQ
- 异步可靠交付：PostgreSQL Outbox，V1 建表但不启动 Worker
- API 契约：OpenAPI 3.0
- 返回格式：统一 JSON 返回结构
- 契约基线：见 `docs/api-contract.md`
- API 与数据库设计规则：见 `docs/api-database-rules.md`，涉及 API、DTO、Prisma、SQL、索引、缓存或迁移时必须执行
- 配置方式：环境变量或被 git 忽略的本地配置文件
- 产品策略配置：服务端类型化配置与权益解析，规则见 `docs/configuration.md`

### 后台技术栈

- 框架：Vue 3
- UI：Element Plus
- 形态：独立 Web 应用，不与小程序共用前端资源

## 落地前必须确认

只确认当前仓库真正会影响实现方案的事项；没有涉及的内容，不需要提前确认。

常见需要确认的项：

1. `Pinia` 状态是否跨页面共享，是否需要持久化和清理规则。
2. 小程序端是否触达平台能力；触达时先确认 `apps/client/src/platform/uni.ts` 边界。
3. 后台管理是否属于本次范围，是否需要新增运营角色。
4. 接口联调方式是直连、代理还是 mock。
5. 是否有明确的测试要求。
6. 是否触达 Prisma Schema、手写 SQL 约束、迁移或历史数据。
7. 是否触达 Worker、Outbox、公共 UGC、支付、饭票、会员或合规闸门。
8. 是否触达饭搭子多关系、饭局、口味、个人空间计量、菜谱覆盖、图片独立化、技术快照或到期清理。

## 生命周期与配置技术规则

1. 饭搭子关系以 `docs/dining-group.md` 为准；饭搭子只表达关系，不承载个人数据空间。
2. 配置中心只提供 `GLOBAL / ENTITLEMENT / USER / INSTANCE / SAFETY` 输入，所有权、权限和状态机仍由代码保证。
3. 客户端不得自行计算套餐、双方饭搭子额度、图片参数和空间结论。
4. 邀请和饭局等实例创建时保存必要的解析值和策略版本，后续配置变化不追溯已创建事实。
5. 逻辑空间使用量必须可增量更新也可全量重算；结构化记录至少按 1 KB 取整，图片按压缩后大小计量。
6. 资源引用与逻辑计量分开；基础版本可物理复用，个人逻辑空间按 `configuration.md` 计量，物理文件仅在最后引用释放后删除。
7. Free 删除必须二次确认并永久删除；Plus/Pro/Ultra 回收站分别为 3/5/7 天。
8. 派生做法只允许根菜谱创建且不能再次派生，上限只来自操作者个人套餐。
9. 过期清理命令必须幂等、分批、可重试、防重复执行并保留审计。Worker 仍 Disabled 时不得声称由 Worker 自动完成。
10. 支付价格、周期和升级补差尚未冻结；订单和回调契约确认前不实现销售入口。
11. OCR、AI 和小票识别当前 Reserved，不提前添加通用抽象或占位服务。

## 数据库建模规则

本节是摘要。字段、表、约束、安全、性能、缓存、事务和迁移的完整强制规则见 `docs/api-database-rules.md`。

1. 同一可变业务事实只能有一个写入 owner。
2. 其他表只能保存外键、不可变历史快照，或有明确一致性机制的缓存摘要。
3. 不为了展示方便复制当前值，避免一次修改需要同步多张表。
4. 表边界按生命周期、权限、唯一约束、更新频率、增长方式和审计要求划分。
5. 主表只放实体本体字段；成员、邀请、快照、账本、日志、版本和明细等独立生命周期数据必须拆表。
6. 金额、权限、成员状态、空间归属、权益授权和存储超额等高风险事实必须以主事实表为准，不能以缓存字段为准。
7. 允许冗余时必须说明冗余类型：历史快照、性能缓存或统计摘要，并说明是否需要随主事实更新。
8. 可无限增长的数据必须分页、归档或保留拆分空间，不塞进主表 JSON。
9. 历史快照字段必须从命名上表达快照语义，例如 `sourceName`、`nameSnapshot` 或 `displayNameAtCreated`。
10. 缓存摘要字段必须有可重算来源，关键权限、金额和状态判断不得只依赖缓存摘要。

## 接口协议规则

详细设计规则见 `docs/api-database-rules.md`，当前契约基线见 `docs/api-contract.md`。本节只保留全局摘要。

1. 前后端接口统一返回 JSON。
2. 所有接口固定使用 `code`、`message`、`data`、`serverTime` 顶层字段。
3. 成功时 `code` 固定为 `0`，失败时使用明确业务错误码。
4. 业务数据只放在 `data` 字段，不返回裸数组、裸对象或 `ok: true`。
5. HTTP 状态码保持语义化，但前端业务判断优先使用返回体里的 `code`。
6. 用户侧接口默认不返回数据库内部主键，例如 `User.id`、成员 relation 主键或主理人用户主键。
7. 用户侧需要标识用户时，统一返回 `uid` 或最小用户摘要；需要标识空间时，保留真实业务对象 id，例如 `diningGroupId`。
8. 只有服务端内部关联、后台运营或数据库约束真正需要时，才允许继续使用内部主键。

推荐结构：

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "serverTime": "2026-05-21 12:00:00"
}
```

## 直接开工或先确认规则

以下情况可直接开始：

1. 目标明确。
2. 范围较小。
3. 不涉及核心流程重排。
4. 验收方式容易检查。

以下情况需要先确认：

1. 页面结构发生明显变化。
2. 共享状态归属发生变化。
3. API 协议发生变化。
4. 路由或权限行为发生变化。
5. 任务开始扩展成重构工作。

## 目录边界

### 前端目录边界

- `pages/`
  - 页面级编排与页面本地状态接线
- `components/`
  - 输入输出明确的可复用 UI 片段
- `store/`
  - 仅存放长生命周期共享状态
- `apis/`
  - 面向领域的请求入口
- `utils/`
  - 仅存放稳定的纯辅助方法
- `config/`
  - 仅存放静态配置、常量与元数据

### 后端目录边界

- `api/`、`handlers/`、`controllers/`
  - 只做参数解析、调用服务、包装统一返回结构
- `services/`
  - 业务编排与业务规则
- `datasources/`、`repositories/`
  - 数据读取、保存与数据源切换
- `models/`、`schemas/`
  - 数据结构、输入输出定义
- `processors/`、`parsers/`
  - 清洗、转换、解析与处理逻辑
- `config/`
  - 配置读取与环境切换，不写死密钥

推荐补充目录：

- `layouts/`
  - 共享页面框架与外层结构
- `types/`
  - 跨模块复用的数据类型定义
- `composables/`
  - 可复用的组合式逻辑，前提是边界已经稳定

## 扁平化规则

前端页面、后端接口、后台页面和包目录都默认扁平化。

1. 目录层级默认不超过 3 层，路由和接口默认不超过 2 个业务语义层级。
2. 不把数据库关系、菜单树、权限树或领域模型完整搬进路径。
3. 小程序路由按入口页命名，优先 `pages_recipe/detail`，不要 `pages/dining-group/recipe/version/detail`。
4. 后端接口按稳定资源命名，优先 `GET /recipes/{recipeId}`、`POST /meal-plans`，不要多层父资源嵌套。
5. 后台路由按运营动作命名，优先 `/admin/recipes`、`/admin/imports`，不要 `/admin/content/recipe/import/review/list`。
6. NestJS 模块保持一级领域模块，复杂流程放 service、repo、DTO 和事务边界，不继续拆深层模块目录。
7. 主题目录保持 `src/themes/{skinId}`，不再增加 `skins/`、`templates/`、`variants/` 等中间层。
8. 如果超过默认层级，必须在代码注释或文档中说明原因。

## 命名规则

1. 代码标识符使用简短驼峰命名。
2. 名称最多 3 个单词，优先表达业务含义或结果角色。
3. 禁止使用 `normalized`、`formatted`、`processed` 这类只描述加工过程的命名。
4. 禁止使用 `manager`、`serviceAdapter`、`handlerCenter`、`commonBaseX` 这类边界模糊或无实际语义的抽象名词。
5. 变量名描述“它现在是什么”，函数名描述“它要做什么”。
6. 推荐 `searchKey`、`dishName`、`currentDish`、`buildMeal`、`resolveQuota`、`createPlan` 这类短名称。
7. 如果短命名不足以让开发理解，通过注释说明职责、边界或特殊原因，不要把完整解释塞进变量名。

## 组件规则

1. 组件应聚焦一个清晰的 UI 职责。
2. 不要悄悄把页面编排逻辑下沉到叶子组件。
3. 组件接口保持显式。
4. 先复用已有组件模式，再考虑新增模式。

## 状态规则

1. 页面本地 UI 状态默认留在本地。
2. 跨页面的持久状态可以移动到 `store/`。
3. 没有充分理由时，不要把临时状态提升到共享范围。
4. 持久化状态应遵循统一的命名和清理规则。

## 请求规则

1. 请求应统一经过共享 API 层。
2. 页面不应直接承载底层请求代码。
3. 通用错误处理应集中管理。
4. 鉴权与重试逻辑不应散落在各个页面。
5. 请求实例、拦截器、超时、错误码映射需在落到具体仓库时统一约定。

## 后端服务规则

1. 接口入口只做参数解析、调用服务、包装统一返回结构。
2. 不在接口入口里直接写复杂 SQL、直接读写业务文件、直接调用第三方服务或拼装复杂业务结果。
3. 数据读取、业务处理、结果保存要分层，不混在同一个函数里。
4. 数据源必须通过统一接口抽象，不在业务代码里到处判断“当前是文件还是数据库”。
5. 文件读取只作为一种数据源实现，不直接写在接口入口。
6. 参数校验失败、资源不存在、服务异常都返回明确错误码，不暴露原始 traceback、SQL、密钥或内部细节。
7. 密钥、数据库地址、远程服务地址必须来自环境变量或本地忽略配置。
8. 长任务或模型任务要记录阶段状态，状态查询接口只查状态，不触发实际计算。
9. Service 是业务规则、权限检查和事务边界 owner。
10. Controller 不承载权限判断、跨对象状态变更或复杂结果拼装。
11. 前端传入的角色、套餐、权限、成员数、空间状态和 `canXxx` 只能作为展示上下文，后端写操作必须重新解析和校验。
12. 跨对象状态变化必须事务化，例如加入饭搭子、退出或移除、菜谱图片独立化、权益升级和空间超额状态变化。
13. 高风险操作必须审计，包括支付、权益、成员关系、删除、导入、导出和公开内容治理。
14. 读接口也必须做权限过滤，不能只在写接口做权限校验。

## 参数校验规则

1. 每个接口都要明确必填字段、字段类型、枚举范围、数值范围、字符串长度和是否允许空值。
2. 参数校验失败统一返回明确错误码和可读错误信息。
3. 不允许把框架原始异常、traceback、数据库错误详情直接暴露给调用方。
4. 前端只消费稳定错误结构，不解析后端原始异常文本。

## 文件与数据源规则

1. 如果支持本地文件读取，只允许读取指定数据目录下的文件。
2. 不允许前端或调用方传入任意绝对路径。
3. 文件路径必须做规范化和目录逃逸检查。
4. 文件格式要明确，并有对应解析方法。
5. 业务服务只依赖统一数据源接口，不直接关心具体是文件、数据库、远程接口还是 mock。

## 配置与密钥规则

1. 密钥、数据库地址、远程服务地址必须来自环境变量或被 git 忽略的本地配置文件。
2. 示例配置只放 `.env.example` 或等效模板，不放真实密钥。
3. 代码里不写死生产地址、账号、密码、Token。
4. 配置读取要有清楚的默认值、缺失提示和失败处理。
5. 前端不保存任何后端密钥。

## 日志规则

1. 后端日志至少记录请求路径、请求耗时、业务错误码和异常摘要。
2. 不记录完整密钥、用户敏感信息、大段原始数据或超长模型输入输出。
3. 长任务日志应带阶段状态，便于排查和追踪。

## 性能规则

1. 入口轻、详情准、列表分页、图片受控、写操作事务化。
2. 不用减少接口数量替代性能设计；重点是减少无效数据、重复请求和无索引查询。
3. 列表接口必须分页，默认不返回大字段、明细、历史、账本或完整子对象。
4. 常用筛选字段、外键、状态字段和时间排序字段必须考虑索引。
5. 图片上传必须有输入大小、输出大小、宽高和质量限制。
6. 存储计量必须可增量更新，也必须可全量重算。
7. 缓存只用于性能，不作为权限、金额、成员关系或权益判断的唯一依据。
8. 首屏接口数量和数据量要受控，但不能为了首屏把无关模块合并进一个接口。
9. 复杂统计、账本和历史记录优先按需读取；确需摘要时，摘要要有明确 owner 和刷新机制。
10. 慢查询优化优先从查询边界、索引、分页和返回字段入手，不用提前增加泛化缓存层。

## 风格规则

1. 共享主题值应来自同一处定义。
2. 主题变量已存在时，避免在页面文件里硬编码颜色。
3. 使用清晰的间距与排版体系。
4. 关键布局行为不要依赖隐藏的框架默认值。
5. Sass 变量、mixin 与重置样式的入口文件需在落到具体仓库时统一。

## 个人工程风格

以下内容用于表达当前默认的实现倾向，优先级低于项目真实需求，但高于个人临时发挥。

1. 优先写清职责和边界，再开始拆页面、拆组件、拆状态。
2. 优先直接、稳定、可维护的实现，不为了“高级感”增加抽象层。
3. 页面可以承担主流程编排，但不要把边界搞乱。
4. 抽象建立在真实复用之上，不为未来假设提前设计。
5. 共享能力统一收口，不把请求、主题、鉴权、错误处理散落到各处。
6. 文档、目录和实现口径保持一致，不接受“文档一套、代码一套”。
7. 默认追求够用、稳定、好维护，不追求炫技式实现。

## 默认代码风格

在 Vue + TypeScript 项目里，默认采用以下写法：

1. Vue 单文件组件优先使用 `script setup`。
2. 新增代码默认使用 TypeScript 类型，不随意引入 `any`。
3. 页面文件负责路由参数、页面状态、请求组织和主交互流程。
4. 组件只做清晰单一的 UI 职责，不承接页面级编排、路由拼装或接口拼装。
5. 共享状态才进入 `Pinia`，临时页面状态默认留在页面本地。
6. `store` 保持显式，允许 `setXxx`、`updateXxx`、`resetXxx` 这类直接 action。
7. 页面不直接写底层请求，统一通过 `apis/` 暴露业务语义接口。
8. 已确认的契约迁移和历史口径适配优先收口在请求层或边界层；不得用多字段 fallback 隐藏未知契约。
9. 先把本地问题做清楚，再决定要不要抽 helper 或 `composable`。
10. 只有真实复用或职责明显混杂时，才抽共享逻辑。
11. 模板层保持清晰，复杂判断和数据整理下沉到脚本层。
12. 注释主要解释职责、边界、放置原因和兼容原因。
13. 每次提交前至少保证构建可过，且主路径已做手动验证。

## 不推荐写法

1. 为了复用而复用。
2. 单次使用逻辑提前抽成公共层。
3. 把所有状态都塞进 `Pinia`。
4. 页面里散写底层请求细节。
5. 模板里堆大段业务判断。
6. 引入没有明确职责边界的抽象层。

## 注释规则

以下情况应添加注释：

1. 文件职责
2. 重要共享数据
3. 有副作用的方法
4. 复杂代码块或边界处理

不要添加只是重复显而易见语法的注释。

## 验证规则

每次前端改动都应验证：
