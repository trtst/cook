# 厨房知识文章未读标识设计

## 背景与目标

“我的”页的厨房知识栏目入口目前没有未读圆点，文章列表标题也没有 `NEW` 标识。现有文章阅读写入只累计平台总阅读数，不保存用户对单篇文章的已读状态。

本设计只增加文章未读提示：最近 7 天发布且当前登录用户未读的文章，在列表标题后显示字体图标 `e6a6`；若某栏目至少有一篇这样的文章，“我的”页该栏目入口显示圆点。

## 已确认的产品规则

1. 以文章 `publishedAt` 为准，按服务端当前时刻向前滚动 7×24 小时计算有效窗口。
2. 窗口内，当前用户未打开文章详情的文章显示 `NEW`；成功打开详情后记录为已读并隐藏标识。
3. 最近 7 天内发布的存量文章在功能上线时也参与判断；更早的文章默认视为已读。
4. 文章发布满 7 天后自动退出未读判断，无论此前是否打开过详情，都不再显示 `NEW`、不计入栏目圆点，也不再查询个人已读状态。
5. 栏目圆点表示该栏目至少有一篇窗口内未读文章，不显示数量。
6. “我的”页在进入或从文章页面返回时刷新三个栏目的状态；列表页在返回时刷新当前栏目状态。不开启轮询或定时任务。
7. 未登录用户没有个人已读状态，不显示 `NEW` 或栏目未读圆点。现有文章浏览和列表访问行为保持不变。

## 页面行为

### “我的”页

- 登录用户进入页面时请求三个受控栏目 `KITCHEN / COOK / FOOD` 的未读摘要。
- 每个栏目只根据 `hasUnread` 显示或隐藏现有知识入口旁的圆点。
- 从文章详情返回后，利用页面 `onShow` 再次请求摘要；若用户读完栏目内最近 7 天的文章，圆点消失。
- 请求失败时保留页面内最近一次成功的栏目状态；首次请求失败且没有成功状态时不显示圆点。下一次 `onShow` 可再次刷新。

### 文章列表

- 继续使用现有 `channelCode` 路由和文章排序。
- 每条文章摘要增加稳定的布尔值 `isUnread`；登录用户仅当文章在 7 天窗口内且没有已读记录时为 `true`，未登录请求固定为 `false`。
- `isUnread` 为 `true` 时，在文章标题后渲染 `e6a6` 字体图标和 `NEW` 标识。
- 返回列表页时重新加载当前页，更新刚读过的文章状态。
- 匿名浏览收到 `isUnread: false`，不显示未读提示。

### 文章详情

- 文章详情成功加载后，现有阅读写入流程继续累计总阅读数，同时为当前登录用户在有效 7 天窗口内的文章记录已读。
- 超出 7 天窗口的文章不创建新的已读记录，因为其未读状态不再参与产品判断。
- 阅读总数和用户已读状态应在同一事务中写入；读状态使用用户与文章唯一关系，重复进入详情不会重复创建读状态。

## 数据与接口

### 已读事实

- 新增用户文章已读关系，归属为 `USER × ARTICLE`，至少保存 `userId / contentId / readAt`。
- `(userId, contentId)` 唯一；用户或文章删除时级联清理。
- 已读事实只在读状态查询的 7 天过滤条件内有效。过期记录不再查询或影响界面；本期不增加定时清理任务。

### 接口契约

1. 文章列表 `GET /site-contents/articles`：列表摘要增加稳定布尔值 `isUnread`，详情响应不增加该字段。匿名请求固定返回 `false`；登录请求仅计算本次分页内、`publishedAt >= requestNow - 7 days` 的文章，并批量读取当前用户对这些文章的已读关系；不得逐文章发查询。
2. 栏目摘要新增登录接口 `GET /site-contents/articles/unread-summary`：一次返回三个栏目各自的 `hasUnread`，不返回数量。后端对每个固定栏目用 `EXISTS` 类查询，筛选 `ARTICLE + PUBLISHED + publishedAt >= requestNow - 7 days + 当前用户没有已读关系`，每个栏目最多取一条命中记录。每个请求只计算一次 `requestNow`，避免同一响应在窗口边界上口径不一致；静态摘要路由需先于 `:articleId` 动态路由注册。
3. 文章详情现有 `POST /site-contents/articles/{articleId}/view`：保留 `Idempotency-Key` 和阅读计数语义；在同一事务中，对于窗口内文章写入已读关系。该接口只允许当前已登录用户写入。

### 查询成本与索引

- 列表接口已限制 `pageSize`，单次最多 50 条；已读状态按本页文章 ID 批量查询。
- 栏目摘要固定三个栏目，每栏只做有结果即停止的存在性查询，不加载文章正文或未读明细。
- 新已读表建立用户/文章唯一索引，供列表批量匹配和栏目反连接使用。文章窗口筛选应结合 `channelId / type / status / publishedAt` 选择有证据的索引；实现前按 API 与数据库规则核对现有索引是否足够，避免重复索引。
- 不新增缓存、通知消息、轮询、后台任务或过期清理 Worker。

## 权限与失败行为

- 未读摘要要求 `UserBearerAuth`；未登录不查询个人状态。
- 文章列表和详情仍维持现有公开读取行为；登录列表才返回个人 `isUnread` 值。
- 文章已下架或不存在时，现有文章写入权限校验继续拒绝阅读写入。
- 若阅读写入失败，服务端不伪造已读事实；下一次列表/栏目刷新仍可能显示未读，用户可重新进入详情触发后续写入。

## 验收

1. 发布 7 天窗口内的新文章，未读用户在标题后看到 `NEW`，所属栏目在“我的”页显示圆点。
2. 打开文章详情并成功写入阅读后，返回列表时该文章 `NEW` 消失；同栏目无其他未读文章时，返回“我的”页后圆点消失。
3. 同栏目仍有其他未读文章时，读完其中一篇后栏目圆点继续显示。
4. 文章超过 7 天时，不显示 `NEW`，不参与栏目圆点和个人已读查询。
5. 功能上线前 7 天内发布的文章按普通窗口规则参与判断；超过窗口的历史文章不显示未读提示。
6. 未登录浏览文章时不出现个人未读提示；阅读总数行为保持原样。
7. 不存在定时任务、轮询或按文章逐条查询的 N+1 行为。

## 实施范围

- API/Prisma：已读关系、前向 migration、列表摘要状态、栏目摘要接口、阅读事务和 OpenAPI。
- Client：文章摘要本地类型、知识列表 `NEW` 图标、“我的”页栏目圆点、页面 `onShow` 刷新与状态用例。
- Admin、文章发布流程、通知中心和其余栏目不在范围内。
