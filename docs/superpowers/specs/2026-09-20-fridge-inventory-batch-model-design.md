# 食材库存批次模型优化设计

## 状态

设计已根据用户确认形成，等待用户复核后进入实施计划。本文只冻结业务语义、页面行为和数据边界，不直接替代 API、Prisma migration 或客户端实现。

## 背景与目标

当前食材首页把每条 `FridgeItem` 直接渲染成一张卡片，食材详情页把单条库存、库存指标、预占、编辑、补货、扣减和采购入口混在一起。现有库存记录已经包含数量、单位、到期时间和采购来源等字段，但页面和接口仍以“单条食材库存”理解它，无法表达同一食材的多次购买批次。

本次目标是把食材库存调整为：

1. 食材列表代表“我的库存里有哪些食材”，同一食材只显示一次。
2. 食材详情页展示该食材的多个购买/入库批次。
3. 新增库存形成新批次，不能覆盖旧批次。
4. 做菜、采购完成等业务流程，以及详情页手动操作，都可以新增或扣减库存。
5. 用户只输入总数量，服务端自动按最早到期批次分摊扣减。
6. 过期是提醒状态，不等于不可用；过期但仍有数量的批次仍可扣减。
7. 扣减超过当前可用库存时整次失败，不产生负库存。
8. 过期和已用完的批次在详情页收起，历史记录仍可查询，不因 15 天规则删除。

## 非目标

本次不实现：

- 生产日期、开封状态、仓储位置、批次时间线或仓储级成本核算。
- 用户手动选择扣减批次。
- 新增通用的主食材/从属食材树或 `parentIngredientId`。
- 通过名称相似、拼音或 AI 自动合并食材。
- 因到期自动删除批次、禁止使用批次或修改 `available`。
- 为库存另建一份可编辑的总量缓存表。
- 把购物清单中的库存预占直接当成真实扣减。
- 本轮顺带重构通用权限中心、图片系统或其他食材治理页面。

## 核心领域语义

### 食材身份、别名和归并

食材身份沿用现有系统模型：

- `Ingredient` 是正式食材身份。
- `aliases` 是同一条食材记录上的识别别名，例如“土豆”的别名是“马铃薯”；别名命中后使用同一个 `ingredientId`。
- `MERGED + mergedToId` 是后台明确执行的食材归并，不是通用父子树。后续新写入和读取按现有归并规则解析到最终有效主食材。
- 不新增库存专用的主食材/从属食材关系。

库存批次必须绑定食材身份。新批次不接受只靠名称的隐式库存归并；历史 `ingredientId` 缺失或关系无效的数据必须先审计和人工确认，不能按名称猜测。

### 批次事实

现有 `FridgeItem` 存储结构已接近批次事实。本轮第一实现选择复用 `fridge_items` 表，把每一行的领域语义明确为“一次购买或一次入库形成的库存批次”，不新增平行的 `fridge_batches` 表。

一个批次至少包含：

- 用户 owner；
- 最终有效的食材身份；
- 精确数量和系统单位；
- 可选到期时间；
- 入库/创建时间，由服务端记录；
- 采购清单来源（如有）；
- 备注（如有）；
- 当前剩余数量和批次生命周期状态。

新增批次的用户输入保持最小：数量、单位、可选到期日。入库时间和来源由系统自动记录。生产日期、开封状态不进入本轮批次主事实。

### 生命周期与到期状态分离

批次生命周期和到期提醒是两个正交维度：

```text
生命周期：有剩余库存 -> 扣减至 0 -> 历史
到期状态：未到期 / 临期 / 已过期
```

规则：

1. `expireAt` 只派生出提醒状态，不自动把批次标记为不可用。
2. 过期但仍有剩余数量的批次仍属于当前库存，可以被扣减。
3. 扣减至 0 的批次进入历史批次。
4. 15 天只用于前台折叠和重点展示，不改变批次生命周期，不删除数据。
5. 过期批次进入“已过期库存”折叠区域；仍有数量时不能放进仅表示已结束的历史集合。

### 数量和单位

1. 相同食材、相同单位的批次可以汇总展示。
2. 不同单位只有在服务端存在明确、可靠的可比关系时才允许换算。
3. 没有可靠换算关系时，列表显示多段数量，不强行相加，例如“500 克 + 2 个”。
4. 自动扣减只处理服务端可比较的数量和单位；无法比较时返回明确的“数量待确认”业务结果，不猜测换算。
5. 旧数据中的模糊数量保留历史事实；新的库存新增和扣减使用精确数量与系统单位。

## 业务流程

### 新增库存

触发来源包括购买完成入库、详情页补货、详情页手动新增和其他已确认的入库流程。

流程：

1. 调用方提交最终食材身份、数量、单位和可选到期日。
2. 服务端解析别名/归并身份并校验 owner、单位和数量。
3. 服务端创建一条新的 `FridgeItem` 批次，不修改已有批次。
4. 返回最新的食材汇总和新增批次信息。

### 扣减库存

调用方只提交食材身份、总扣减数量、单位和幂等键，不提交批次选择。

服务端在一个事务内：

1. 解析最终有效食材身份。
2. 查询该用户该食材仍有剩余数量的可扣减批次。
3. 按最早到期优先排序；无到期日的批次排在有到期日之后；同一到期日按入库时间和稳定 ID 排序。
4. 已过期批次仍参加排序和扣减，不因过期被跳过。
5. 计算所有可比较批次是否足够覆盖本次扣减。
6. 数量不足或单位不可比较时，整次事务失败，不修改任何批次。
7. 数量足够时，跨批次扣减并更新各批次剩余量；扣减至 0 的批次进入历史。
8. 写入幂等结果和必要审计后提交。

做菜、明确消耗、详情页手动扣减等入口共用同一套库存扣减服务，不在各页面复制批次分配逻辑。

采购清单中的“用库存”仍保持当前预占语义：预占可以申请、撤销和结算，但不能直接等同于批次实际扣减。只有既有业务流程明确完成消耗时，才调用真实扣减。

### 扣减失败

以下情况必须整次失败并保持原库存不变：

- 扣减数量超过可比较的剩余库存；
- 食材身份不存在、已归并关系无效或不属于当前用户可用范围；
- 数量和单位无法可靠比较；
- 批次并发版本已变化；
- 幂等键重用但请求内容不同。

## 汇总读取模型

库存列表不再直接把 `FridgeItem` 行当成食材卡片。服务端按当前用户和最终有效食材身份聚合批次，返回食材级摘要：

- 食材身份和展示名称；
- 分类和图片摘要；
- 按单位分组的当前剩余数量；
- 最近到期批次的到期状态；
- 当前批次数量；
- 已过期但仍有库存的批次数量；
- 必要的库存状态文本。

总量是读取时从批次事实计算出的结果，不单独保存可被页面修改的汇总库存。

食材详情返回：

- 同一份食材级汇总；
- 当前批次列表；
- 已过期但仍有库存的折叠批次列表；
- 已用完等历史批次的分页查询入口；
- 新增库存和总量扣减所需的最小操作状态。

具体公共路径和 DTO 在实施阶段必须与当前 `api-contract.md`、真实调用链和 OpenAPI 一起冻结，不能从页面字段直接反推接口。

## 页面行为

### 食材列表

1. 以最终有效食材身份为 key，一个食材只出现一次。
2. 展示食材名称、汇总库存和最近到期提醒。
3. 同食材多个批次不再生成多张卡片。
4. 有过期但仍有库存时，保留该食材卡片并显示风险状态。
5. 点击进入食材详情，参数使用食材身份而不是某一条批次 ID。
6. 列表的主要任务是查看库存和到期，不把批次管理动作铺在卡片上。

### 食材详情

1. `detail-hero` 和摘要卡放进同一个 `scroll-view`，随内容滚动。
2. 顶部导航仍可固定并随滚动改变透明度，但不固定详情 Hero。
3. `summary-card__description` 不再重复 warning badge 的到期文案；到期提醒只保留一个醒目表达。
4. 首屏优先展示总库存和到期提醒。
5. 当前批次按到期优先展示；过期但有库存的批次自动收起到“已过期库存”。
6. 已用完批次进入“历史批次”，默认收起，点击后查询全部记录。
7. 详情页主要操作为“新增库存”和“扣减库存”，扣减输入总量，不出现批次选择器。
8. 现有采购入口如仍属于业务闭环，保留为次要入口，不把它和批次管理混成第三套库存操作。

## API、数据库和迁移边界

### API 方向

实施阶段至少需要分离以下读取职责：

1. 食材级库存汇总列表。
2. 单个食材的当前批次与历史批次详情。
3. 新增一个库存批次。
4. 按食材总量扣减并返回批次分摊结果。

新增和扣减均需要数字字符串幂等键。扣减事务需要保护候选批次的版本，保证并发扣减不会产生负库存或重复扣减。

### 数据库方向

1. 复用 `fridge_items` 作为批次事实，不新建重复的汇总表。
2. 保留现有采购来源字段，新增字段只在真实业务需要时加入。
3. 补充用户、食材、可用状态、到期时间和排序所需的可预测成本索引。
4. 维持 `available` 与消耗完成事实的一致性；过期不能单独把 `available` 改为 false。
5. 对数量非负、版本正数、食材身份有效等简单不变量增加数据库兜底。
6. migration 前只读审计 `ingredientId` 为空、食材已归并、数量模糊和异常生命周期记录。
7. 对无法安全解析的旧数据停止自动归并并输出待处理 ID，不能按名称猜测。

### 迁移策略

1. 现有每条 `FridgeItem` 保留为一个初始批次，不删除现有记录。
2. 当前存在的同食材多行由新的汇总读取统一展示，不做无证据的数量合并。
3. 已消耗记录继续作为历史批次读取。
4. 旧详情页的批次 ID 深链需要通过批次反查食材身份后进入新的食材详情，避免历史链接失效。
5. 未绑定食材身份的旧记录必须先完成明确映射或进入待确认状态，再决定是否收紧新写入约束。
6. 不因本次 UI 折叠而删除过期或历史数据。

## 验收与测试

### API/服务端

1. 同一食材新增两次后，列表只返回一个食材摘要，详情返回两个批次。
2. 别名命中同一个 `ingredientId` 时，不产生第二个库存汇总。
3. 已归并食材新增和查询时解析到最终有效食材。
4. 新增批次不会覆盖旧批次，采购来源和到期日分别保留。
5. 扣减按最早到期批次分摊，可跨多个批次。
6. 已过期但仍有数量的批次可以被扣减。
7. 扣减超过库存、单位不可比较、并发版本冲突时整次回滚。
8. 幂等重试不重复新增或扣减，复用幂等键提交不同请求时返回冲突。
9. 扣减至 0 的批次进入历史；过期但有库存的批次不进入已结束历史。
10. 15 天只影响展示查询，不删除历史数据。

### 客户端

1. 食材列表同一食材只渲染一个卡片。
2. 多批次汇总数量和多单位展示符合服务端结果。
3. 详情 Hero 位于滚动内容内，导航固定层仍能正确渐变。
4. `summary-card__description` 不再和 `badge--warning` 重复到期文案。
5. 详情页新增和扣减都提交食材总量，不出现批次选择。
6. 过期库存默认折叠但仍可展开和扣减。
7. 历史批次默认收起，展开后可分页查询。
8. 登录、空态、加载、接口失败和扣减失败状态不丢失当前页面上下文。

### 真实验收

至少使用真实 API 验证：

1. 同一食材连续两次购买入库。
2. 列表聚合和详情批次展示。
3. 详情手动新增库存。
4. 跨批次扣减和过期批次扣减。
5. 超量扣减回滚。
6. 历史批次折叠、展开和 15 天展示边界。
7. 做菜/采购等现有入口调用统一库存增减语义。

4. 实现后端汇总读取、新增批次和跨批次扣减。

6. 改造食材列表和详情页，包含 Hero 滚动、重复到期文案和批次折叠。
7. 串行执行 API、Client、真实接口和页面验收。

## 范围自检

- 本设计只服务于“食材列表去重、批次详情、库存新增/扣减、到期提醒”这一条主线。
- 没有新增后台食材父子树；别名和现有归并机制继续各司其职。
- 没有把截图中的生产日期、开封状态、时间线和复杂编辑操作带入本轮。
- 没有新增可编辑的库存总量副本；批次是唯一库存事实。
- 任何无法从现有食材身份、单位或批次事实安全推导的数据，实施前必须停在审计结果上，不做名称猜测。
