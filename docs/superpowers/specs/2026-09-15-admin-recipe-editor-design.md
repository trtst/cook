# 后台菜谱统一编辑器与导入图片资产设计

## 目标

后台“菜谱导入条目”和“系统菜谱详情”使用同一套编辑界面、字段校验和图片操作。导入条目在发布前是唯一编辑入口；发布后由系统菜谱详情承接唯一编辑权。已保存的导入图片可在重新进入条目后继续显示并参与发布；普通步骤和美食助理步骤均支持上传、替换、删除与显示。

## 已确认边界

1. 导入条目处于 `PENDING_PARSE`、`NEEDS_FIX`、`READY` 或 `FAILED` 时可编辑；`PUBLISHED` 时导入页只显示发布结果和“打开系统菜谱”，不再提供保存或发布操作。
2. 已发布系统菜谱只在 `/recipes/:recipeId` 编辑。每次保存继续创建新的 `RecipeContentVersion`，不原地改变旧版本。
3. 导入页和系统菜谱详情页共享 `RecipeEditor`，包含分类、正文、工具、业务标签、食材及其分类、普通步骤及图片提示词、封面、普通步骤图、美食助理步骤及其图片提示词。导入页面可额外提供“选择导入原图”，它只是图片输入来源，不是第二套编辑能力。
4. 候选标签中仅 `MEAL_TYPE` 允许多个不同值，例如 `MEAL_TYPE=LUNCH` 与 `MEAL_TYPE=DINNER`；其他标签代码每种状态最多一条。任意固定版本内，每个 `tagCode` 最多一条 `CONFIRMED` 标签；相同 `tagCode + tagValue` 不得重复。
5. 自动推导的标签保持候选，不能因为显示缺口自动升级为已确认。`10002216` 的五个候选标签须由管理员在编辑器中明确确认。
6. 转换工具输出单道菜时使用 `recipe.import.v1`；输出多道菜时使用一个 `recipe.import.batch.v1` JSON，其中的 `recipes[]` 每项都是完整的单菜谱 `recipe + wiki` 输入。一个批次 JSON 内的 N 道菜谱必须拆为 N 个独立导入条目。
7. 上传入口接受多个 `.json` 和 `.zip` 文件混选。ZIP 只承载 JSON 文件；其中每个单菜或批次 JSON 继续按上述规则展开。ZIP 内图片、可执行文件和非 JSON 文件不属于本次导入格式。

## 当前根因

导入页把上传接口返回的 `tempKey` 写入 `recipeBodyJson`，但预览只保存在浏览器 `URL.createObjectURL()`。重新进入页面后没有可读取临时对象的受保护接口，因而头图或步骤图不会显示。发布时再由服务端读取该对象；对象不存在时才会抛出“图片上传状态已失效，请重新上传”。

普通步骤已有 `imageTempKey`，美食助理步骤只有远程 `imageUrl`。因此本地上传的助手步骤图既无法保存，也无法在导入发布中固化。系统菜谱详情虽然另有封面和普通步骤上传逻辑，但没有复用导入页的编辑模型，也没有编辑助手步骤和业务标签的写入契约。

## 编辑器模型和页面责任

`apps/admin/src/components/RecipeEditor.vue` 只接收和编辑一个显式 `RecipeEditorDraft`，不发起保存或发布请求。页面容器负责加载详情、把本地 API 类型映射为草稿、处理并发版本和调用对应写接口。

草稿中的每张图片统一为：

```ts
type RecipeEditorImage = {
  imageUrl: string | null;
  imageTempKey: string | null;
};
```

封面、普通步骤和助手步骤都使用该模型。导入普通步骤可另外携带已有的 `imageKey`，用于引用导入 JSON 的原始图片；系统菜谱不接受该字段。编辑器通过同一个上传、受保护临时预览、正式 URL 预览和删除路径处理三类图片。

业务标签草稿包含 `tagCode`、`tagValue` 和 `status`。管理员保存的标签使用 `OPS` 来源和锁定状态；自动标签仍由版本生成逻辑创建，不进入管理员写请求。编辑器显示标签状态，并在提交前提示重复的已确认代码；服务端和数据库仍是最终约束。

美食助理草稿包含顺序、阶段、动作、标题、说明、时长和上述图片模型。编辑后按当前版本创建 `OPS` 助手快照；未编辑的系统菜谱仍沿用既有自动候选生成行为。

原始步骤与美食助理步骤均增加 `imagePrompt: string | null`。导入 JSON、导入条目保存与管理员创建/编辑要求非空中文提示词，长度上限为 1000，且同一菜谱内同类步骤的提示词不得重复。现有历史版本和自动生成的助手快照可返回 `null`，共享编辑器显示“待补全”；管理员一旦保存该步骤，必须显式填写，服务端不会依据正文猜造提示词。提示词是用于后续受控图片生成的版本内容，不在本次实现生成图片服务或自动触发生成。

食材行增加 `categoryCode`。导入 JSON 只接受八个可选系统分类代码：`PRODUCE`、`MEAT_POULTRY_EGG`、`SEAFOOD`、`SOY_DAIRY`、`GRAINS_STAPLES`、`SEASONING`、`DRIED_PRESERVED`、`BEVERAGE_ALCOHOL`；禁止写内部分类 ID 或 `UNCLASSIFIED`。若导入名称已严格匹配系统食材，服务端校验其实际分类与 `categoryCode` 一致；未匹配食材创建为 `PENDING` 系统食材时使用该分类。系统菜谱编辑页显示所选系统食材的权威分类，分类随食材选择自动变化，不能通过菜谱编辑修改食材主数据。

## 图片资产生命周期

新增 `AdminRecipeTempImage` 作为后台上传临时对象的唯一生命周期记录：`tempKey`、上传管理员、场景、关联导入条目、过期时间、创建和更新时间。它不向普通用户或公开静态路径暴露。

1. `POST /admin/recipe-images` 写入对象和临时记录。未保存到导入条目的图片在 24 小时后不可读取、不可消费，并由受控清理删除。
2. 导入页保存时，服务端校验封面、普通步骤和助手步骤所引用的临时图都存在、场景匹配且未过期，然后绑定到该导入条目。绑定后的对象是“导入暂存资产”，在条目发布、删除、替换或明确清空前保留，不再按 24 小时自动失效。
3. `GET /admin/recipe-images/temp/:tempKey` 仅允许 `SUPER_ADMIN` 读取仍有效的临时或导入暂存资产。后台前端使用带 Bearer token 的 `fetch` 读取 Blob，再创建本地预览 URL；不把 token 放进图片 URL，也不提供临时公网地址。
4. 发布导入条目时，所有被引用的导入暂存资产先复制为正式图片，发布事务成功后删除暂存对象和记录。发布失败时保留已绑定资产，管理员修正后可以重试。
5. 替换、删除图片或删除导入任务时，服务端在提交后删除不再引用的导入暂存对象；失败记录审计事件。系统菜谱保存时的临时图仍在本次 `POST/PUT /admin/recipes` 内直接消费并固化。

这一区分满足“重新进入仍能预览”和原有 24 小时未保存临时图清理要求，不把未发布图片暴露为公开资源。

## API、数据与迁移

`POST /admin/recipe-images` 的返回保持 `tempKey + 图片元信息`。增加受保护临时图读取接口。导入条目和系统菜谱编辑请求统一允许普通与助手步骤携带 `imageTempKey + imagePrompt`；系统菜谱请求增加管理员标签和助手步骤输入，并在当前新建的固定版本中写入对应 `OPS` 标签和助手快照。正文版本的 `stepsJson` 与助手快照 JSON 持久化各自的 `imagePrompt`，后台详情返回它们供共享编辑器显示和编辑。

服务端写入规则：

1. 先校验图片引用、标签和助手步骤，再写新版本或更新导入条目。
2. 导入更新在同一事务内更新条目、绑定新资产、解除被替换的资产，并记录审计；对象删除放在事务成功后执行。
3. 系统菜谱更新在同一事务内创建版本、写标签、固化所有普通/助手图片、写助手快照并切换 `currentVersionId`。
4. 所有现有 `Idempotency-Key`、`expectedVersion`、`SUPER_ADMIN` 校验和审计规则保持有效。

### JSON 与 ZIP 导入格式

单菜格式保持现有包络，避免已生成的单菜文件失效：

```json
{
  "schemaVersion": "recipe.import.v1",
  "recipe": {},
  "wiki": {}
}
```

多菜输出使用新包络，而不是让 `recipe.import.v1` 顶层变成不带语义的数组：

```json
{
  "schemaVersion": "recipe.import.batch.v1",
  "recipes": [
    { "recipe": {}, "wiki": {} }
  ]
}
```

每个 `recipes[]` 元素按单菜规则独立校验、记录来源路径和序号，并创建一个 `RecipeImportItem`。一个元素格式错误仅使该条目为 `FAILED` 或 `NEEDS_FIX`，不会回滚同一文件或同一 ZIP 内其余条目。最终菜谱仍必须由管理员逐条发布，导入动作不直接创建正式 `Recipe`。

ZIP 解压必须限制压缩包数量、解压后 JSON 文件数量、单文件体积、总解压体积和目录层级；拒绝绝对路径、`..` 路径、符号链接和所有非 JSON 条目。来源路径写为 `archive.zip/entry.json#序号`，以便在工作台定位原始条目。现有单次最多 100 条 JSON 的限制改为“最多 100 个展开后的菜谱条目”，单文件 JSON 保持 10 MB，展开后的 JSON 总量保持 20 MB；ZIP 文件本体和每个 ZIP 内条目也在读取前校验该上限。

新增前向 migration：

1. 创建临时图片生命周期表及其导入条目外键和到期查询索引。
2. 对每个旧版本中同一 `tagCode` 的多条 `CONFIRMED` 标签，按 `isLocked DESC`、来源优先级 `OPS > USER > AI > AUTO`、`updatedAt DESC`、`id DESC` 保留一条，其余改为 `CANDIDATE`。
3. 创建部分唯一索引：同一 `recipe_version_id + tag_code` 只允许一条 `status = CONFIRMED`。保留已有的 `recipeVersionId + tagCode + tagValue + source` 唯一约束。

迁移只调整版本级标签事实，不改变正文、菜谱 ID、当前版本指向或历史图片。迁移前先输出冲突版本和保留行，迁移后用同一查询验证没有重复已确认代码。

## 失败表现

上传、受保护预览、保存和发布都将错误定位到对应封面、普通步骤或助手步骤的 `el-form-item`。若未保存图片已过期，页面在该图片位置显示红框和“图片已失效，请重新上传”；已绑定导入资产不因离开页面而失效。并发保存返回既有 `409`，页面重新加载详情而不尝试合并两份草稿。

## 测试与验收

1. 先为共享草稿映射、图片提示词、食材分类、候选/已确认标签约束和助手图片 `imageTempKey` 写失败测试。
2. 后端覆盖：单菜 JSON、批次 JSON、ZIP 内单菜/批次 JSON、非法 ZIP 条目与展开上限；图片提示词和食材分类的严格校验、匹配分类冲突、待审食材分类落位；暂存上传、鉴权 Blob 读取、24 小时未绑定失效、导入保存后重新读取、替换/删除清理、导入发布把封面/普通/助手图固化、发布失败保留已绑定资产、系统菜谱保存三类图片、标签唯一迁移和请求校验。
3. 后台覆盖：两个页面均使用 `RecipeEditor`；普通步骤和助手步骤均显示并可编辑图片提示词，食材显示权威分类；发布后的导入页无编辑控件；重新加载导入条目仍请求临时 Blob；所有图片位置和服务器字段错误都显示红框。
4. 运行 API/Admin 定向测试与 type-check，并用本地 `3100` API 实际跑通导入上传、保存、刷新、发布和系统菜谱重新编辑。若浏览器自动化仍不可用，明确列为待人工验收，而不以静态检查替代。

## 非目标

不修改小程序菜谱图片能力，不改变个人菜谱编辑流，不自动确认候选标签，不改变 AI 生成策略，不把导入条目重构为正式菜谱草稿，也不新增通用文件管理中心。
