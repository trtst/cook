# 食材筛选导出与图片批量上传设计

## 状态

- 业务范围：已由用户确认。
- 本设计：食材图片处理、筛选导出和批量图片上传范围均已确认。
- 实现：已完成，静态检查结果以执行单和变更日志为准；真实后台浏览器及 OSS/CDN 验收未执行。

## 目标

在后台系统食材页，根据当前筛选结果批量导出 `id:name` JSON；支持按文件名中的食材 ID 批量上传图片，并把上传后生成的 URL 保存到食材的 `imageUrl` 字段。现有单张图片上传也写入同一字段。

这次只交付系统食材能力。菜谱后续可复用文件选择、ID 匹配、逐项上传与结果汇总流程，本次不改菜谱业务。

## 确认的范围

- 导出包含当前状态筛选结果，状态筛选支持 `PENDING / ACTIVE / DISABLED / MERGED / ALL`。
- “没有图片地址”开关按 `imageUrl IS NULL` 筛选；导出遵循当前状态、分类、关键词、结构化属性和图片地址筛选。
- 导出 JSON 为对象映射，键是食材 ID，值是食材名称，例如：

  ```json
  {
    "10000001": "番茄",
    "10000002": "鸡蛋"
  }
  ```

- 食材页 header 删除“批量导入”入口及页面内对应实现，替换为“批量导出”。独立“食材导入”菜单及其 API、页面和导入流程保留。
- 图片从本地多选，使用文件名主体匹配食材 ID；通过当前存储配置上传。上传成功后，返回的 URL 写入对应系统食材 `imageUrl`。
- 修复/调整现有单张图片上传，使其也写入 `imageUrl`。
- 本次不兼容或回填旧图片；原有 `imageUpdatedAt` 推导地址不作为 `imageUrl` 的 fallback。
- 食材图片必须严格 `1:1`；非正方图拒绝上传。
- 单张上传原图最大 `2 MB`、任一边最大 `1125` 像素；批量上传原图最大 `4 MB`、任一边最大 `3750` 像素；超过对应上限逐项失败且不会上传。
- 任一原始边小于 `60` 像素时拒绝上传。`60x60` 到 `100x100`（含边界）保持像素尺寸；大于 `100x100` 时等比例缩至 `100x100`。
- 单张上传在浏览器 Canvas 中编码为 JPG，quality `0.8`；批量上传编码为 JPG，quality `1`，再上传并保存处理后的对象。
- 持久化的 `imageUrl` 附带 OSS 固定缩放参数，读取时返回 `60x60` 图片。OSS 中实际对象保持 `60x60` 至 `100x100`，访问结果为 `60x60`。
- 共用 Canvas 转换方法按业务传入目标尺寸、quality 和可选源裁切区域。本次只接入食材；后续菜谱封面可使用 `800x600 JPG / 0.8`，本次不改菜谱流程。
- 图片操作继续限定为现有超级管理员权限及系统食材记录。

## 用户流程与页面行为

### 导出

1. 管理员打开系统食材页，选择状态、分类、关键词和现有结构化属性筛选。
2. 可打开“没有图片地址”筛选。
3. 点击 header 的“批量导出”。
4. 页面导出匹配当前全部筛选结果的 JSON 文件；不只导出当前分页。
5. 空结果时提示没有可导出的食材，不生成空文件。

### 批量上传

1. 管理员选择一批本地图片。
2. 页面去掉扩展名读取文件名 ID，并预检重复 ID、非法 ID、当前系统食材不存在或状态不符合服务端校验、非图片、比例错误、尺寸不足和超限文件。
3. 每张有效图片上传至现有存储；服务端持久化生成的 URL 到该食材 `imageUrl`。
4. 每个文件独立成功或失败；部分失败不回滚已成功图片，结束时汇总成功、失败和原因。
5. 成功后刷新列表；当前筛选保留。若启用了“没有图片地址”，已补图条目从结果中消失。

### 单张上传

沿用现有裁剪交互；读取原图宽高后要求裁剪结果严格为正方形，按食材尺寸规则确定输出尺寸，再通过共用 Canvas 方法导出 JPG。服务端存储成功后同时更新 `imageUrl`；接口返回的食材摘要使用数据库保存的 URL。

## 技术设计建议

### 导出与筛选

- Admin 列表查询新增 `imageStatus` 图片地址筛选条件，只允许 `ALL / MISSING`，`MISSING` 对应 `imageUrl IS NULL`。
- 导出沿用同一筛选语义，跨页收集全部结果后由后台页面生成 JSON 下载；不创建第二套过滤规则。
- 沿用分页读取以限制单次响应。导出过程按服务端 `hasNext` 读取每页，保持筛选条件不变。

### 图片字段与上传

- `Ingredient.imageUrl` 是系统食材图片 URL 的唯一持久化事实；缺图为 `null`。
- 上传仍由 API 通过现有存储服务接收文件；服务端生成并返回 URL，在同一写流程将 URL 与食材版本更新、幂等记录和审计一起提交。
- 批量操作不限制文件数，按文件顺序逐张调用单图写接口，复用其比例、尺寸、JPG、权限、版本冲突、存储替换及审计语义；每个文件使用独立幂等键和当前食材版本。批量结果按每页 50 项显示。
- 文件名主体必须是数字系统食材 ID。非匹配项、重复 ID 和无效图片在页面预检或 API 校验中给出逐项失败结果。
- 单图写入允许替换既有图片，和现有编辑行为一致。
- `imageUrl` 指向当前存储对象并附带 OSS `image/resize,m_fixed,w_60,h_60` 缩放参数，将生成值持久化。旧记录保持 `null`，不从 `imageUpdatedAt` 推导、不批量回填。
- 公开系统食材摘要、后台列表、冰箱/购物展示和菜谱食材引用统一读取 `imageUrl`；不保留旧 URL 生成 fallback。公开静态图片读取仍由现有存储路径提供，并依据 `imageUrl` 是否为空判断图片是否已登记。

### 后续复用边界

- 当前图片处理阶段先抽出通用 Canvas 编码方法并接入食材单张上传。
- 筛选导出和食材批量图片上传在当前阶段完成；菜谱图片流程仍留待单独确认。
- 图片 URL 持久化和权限校验仍属于食材领域。
- 菜谱后续复用 Canvas 编码方法时，由菜谱流程传入 `800x600` 和 quality `0.8`；仍需另行确认菜谱固定版本/图片角色的字段、权限和事务边界。

## 失败与边界

- 不存在或非系统食材：该文件失败并说明 ID 未匹配。
- 文件名不是纯数字 ID、同一批重复 ID、格式/尺寸/大小不符：该文件不上传，列入失败明细。
- 单个对象上传失败、版本冲突或 URL 写入失败：仅该项失败；其他文件继续。
- 存储成功而数据库更新失败时，API 按现有单图替换逻辑回滚对象替换；若回滚失败，记录服务端错误并向后台返回失败，不报告为成功。
- 全部失败时保留页面与筛选状态，显示失败汇总；部分成功时刷新列表并保留筛选状态。

## 已落地的实现约定

- `Ingredient.imageUrl` 为 nullable 字符串，缺图语义为 `null`；对应 Prisma migration 已应用到当前本地数据库。
- 后台列表使用 `imageStatus=ALL/MISSING`；`MISSING` 对应 `imageUrl IS NULL`。
- 上传文件名主体必须是数字食材 ID，同一批次内重复 ID 会逐项失败；批量处理按文件顺序串行执行，每张图复用单图上传接口。
- OSS 图片处理参数附加到持久化 URL；未配置静态域名时使用 API 相对地址，真实 OSS/CDN 的处理结果尚未验收。

## 不做

- 不实现菜谱批量导入图片。
- 不改独立食材 JSON 导入菜单和链路。
- 不回填旧图片 URL，不新增旧字段兼容或 fallback。
- 不增加 ZIP 上传、任意远程 URL 导入或通用媒体管理。
- 不兼容旧 PNG 对象 URL；旧记录不回填，也不从 `imageUpdatedAt` 恢复展示地址。
