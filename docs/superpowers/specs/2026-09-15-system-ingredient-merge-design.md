# 系统食材归并设计

## 状态

本设计已确认并完成本地实现与 migration；真实后台执行 `长茄子 → 茄子`、再次导入验证和生产库审计/迁移仍是独立验收门禁。示例口径为：`长茄子 → 茄子`，其中“茄子”是唯一可继续使用的主食材，“长茄子”保留为归并项，后续精确名称导入自动指向“茄子”。

后台统一使用“主食材 / 归并项”表述，不使用“辅助食材”，避免与菜谱中的主料、辅料概念混淆。

## 目标

1. 允许管理员把一条既有系统食材软归并到另一条启用中的系统食材。
2. 保留来源名称作为可追溯的归并项，使后续 JSON 导入仍能识别该名称并得到主食材 ID。
3. 把仍可变、仍直接使用来源食材 ID 的业务数据切换到目标食材。
4. 保持已发布菜谱固定正文和历史审核、营养事实不可变，不用批量回写伪造历史。
5. 复用现有 `Ingredient.status=MERGED` 和 `mergedToId`，不新增候选表或通用别名表。

## 非目标

首版不包含：

- 模糊匹配、拼音匹配或 AI 相似食材判断。
- 批量合并、自动推荐合并目标、解除归并或恢复为独立食材。
- 把来源食材的分类、默认单位、图片、结构化属性、营养映射或换算覆盖到目标食材。
- 自动合并购物清单中数量、单位或备注相近的两行。
- 改写已发布 `RecipeContentVersion`、已发布导入项或其他历史快照。
- 把现有 `aliases` 扩展成独立实体、通用同义词管理或新的别名表。

## 领域语义

### 主食材

主食材是 `ownerId=null` 且 `status=ACTIVE` 的系统食材。它是新建、编辑、导入发布、推荐、购物和冰箱等后续业务使用的正式身份。

### 归并项

归并项是 `ownerId=null`、`status=MERGED` 且 `mergedToId` 指向主食材的原系统食材记录。归并项保留自己的 ID、名称和历史字段，仅承担名称识别、历史追溯和跳转到主食材的职责，不再进入前台食材选择器，也不能成为新正式引用。

来源记录本身就是归并项，不把“长茄子”复制进目标食材的 `aliases`。现有 `aliases` 继续作为轻量识别辅助字段，本次不改变其生命周期和唯一性规则。

### 一层归并

正式关系始终只有一层：

```text
长茄子(MERGED) ──> 茄子(ACTIVE)
紫长茄(MERGED) ──> 茄子(ACTIVE)
```

目标必须直接是 `ACTIVE` 系统食材，不能指向另一条 `MERGED` 记录。若来源在归并前已有归并项，事务将这些归并项一起改指向新目标，不能形成 `A → B → C` 链或循环。

## 后台业务流程

### 入口和列表

1. “系统食材”列表状态筛选增加“已归并”，并允许 `GET /admin/ingredients` 返回 `MERGED` 记录。
2. `ACTIVE` 和 `DISABLED` 系统食材提供“合并”操作；`PENDING` 继续走“待审核食材”的现有审核归并流程。
3. `MERGED` 行显示“归并至：目标名称（目标 ID）”，只提供查看，不提供编辑、上下架、删除或解除归并。
4. “待归类”仍是隐藏系统分类，不是归并状态。分类筛选和状态筛选继续独立，不把 `MERGED` 混成“待审核”或“待归类”。
5. 系统食材分类治理数量包含 `ACTIVE / DISABLED / MERGED`；隐藏“待归类”分类额外包含 `PENDING`，保证“全部”和分类数量不会因软归并而丢失来源记录。

### 合并交互

1. 管理员从来源行点击“合并”。
2. 弹窗明确展示来源名称、状态和 ID，并通过远程搜索选择目标。
3. 目标候选只返回其他 `ACTIVE` 系统食材；当前来源、个人食材、`PENDING`、`DISABLED` 和 `MERGED` 均不可选。
4. 确认区提示：该操作不能在首版后台撤销；来源会成为归并项；目标自身资料不会被来源覆盖；历史已发布菜谱不会改写。
5. 成功后刷新当前列表和状态数量。若当前筛选不包含 `MERGED`，来源从当前结果中移除；在“已归并”中可继续查到来源和目标关系。

## 状态机

本能力只新增以下系统食材转换：

```text
ACTIVE   ──merge──> MERGED
DISABLED ──merge──> MERGED
```

规则如下：

1. 来源和目标都必须是系统食材，即 `ownerId=null`。
2. 来源只允许 `ACTIVE` 或 `DISABLED`；目标只允许 `ACTIVE`。
3. 来源和目标不能相同。
4. `PENDING` 不调用本接口；仍由现有待审核归并动作处理。
5. `MERGED` 首版不能编辑、上架、下架、删除、再次合并或解除归并。
6. 合并后来源保留原名称、分类、默认单位、图片和结构化属性作为治理历史，但这些字段不再参与正式选择或覆盖目标。
7. 仍被 `MERGED` 归并项指向的 `ACTIVE` 主食材不能直接下架；若需停用，应把该主食材继续归并到另一条 `ACTIVE` 主食材，并将已有归并项统一改指最终目标。

## API 契约

新增后台写接口：

```http
POST /admin/ingredients/{sourceIngredientId}/merge
Idempotency-Key: 纯数字字符串
Content-Type: application/json

{
  "expectedVersion": 3,
  "targetIngredientId": 10000001
}
```

成功响应的业务数据固定为：

```json
{
  "sourceIngredientId": 10000024,
  "targetIngredientId": 10000001,
  "mergedAt": "2026-09-15T12:00:00.000Z"
}
```

接口规则：

1. 仅 `SUPER_ADMIN` 可调用。
2. `sourceIngredientId`、`targetIngredientId` 使用现有正整数资源 ID 校验。
3. `expectedVersion` 对来源执行乐观锁；来源版本或状态已变化时返回冲突，不静默覆盖。
4. 同一管理员、同一操作语义和同一 `Idempotency-Key` 的重试返回首次结果，不重复迁移引用或写审计。
5. 同一幂等键改用其他来源或目标时返回幂等冲突。
6. 来源或目标不存在时返回资源不存在；不是系统食材、来源状态不允许、目标不是 `ACTIVE`、来源等于目标或会形成非法关系时返回明确业务错误。
7. 错误响应沿用项目统一 JSON envelope 和现有错误常量体系；实施阶段不得为相同语义另造重复错误码。

`GET /admin/ingredients` 同步扩展：

- `status` 查询支持 `MERGED`。
- 摘要状态类型支持 `MERGED`。
- `MERGED` 摘要额外返回最小目标信息 `mergedTo: { id, name }`；其他状态返回 `mergedTo=null`。
- 列表继续分页，不返回目标完整对象、历史引用数量或大 JSON。

## 数据库约束和迁移

现有 `Ingredient` 已具备 `status`、`mergedToId`、`mergedTo / mergedFrom` 和 `version`，本次不新增业务表。通过新的前向 migration 增加以下行内 Check：

1. `status = 'MERGED'` 时 `merged_to_id IS NOT NULL`。
2. `status <> 'MERGED'` 时 `merged_to_id IS NULL`。
3. `merged_to_id <> id`。

跨行规则无法由简单 Check 保证，必须由合并事务校验：目标是另一条 `ownerId=null AND status=ACTIVE` 的食材；所有写入后的归并关系保持一层且无循环。

迁移前必须只读审计：

- `MERGED` 但目标为空的记录。
- 非 `MERGED` 但目标非空的记录。
- 自引用、目标不存在、目标不是启用中系统食材的记录。
- 多层链和循环。

发现异常时 migration 失败并输出可核对的食材 ID，不静默修复或删除历史。已有 migration 不修改。

## 合并事务

一次合并在单个数据库事务内完成，顺序和边界如下：

1. 读取并锁定或等价条件保护来源、目标及当前直接指向来源的归并项。
2. 校验管理员权限、来源 `expectedVersion`、双方系统身份、双方状态、非自合并和一层关系。
3. 将所有当前 `mergedToId=sourceId` 的系统归并项改指向目标，保证归并仍为一层。
4. 将来源改为 `MERGED`、`mergedToId=targetId`，并递增来源 `version`。
5. 把仍可变的冰箱项和购物项 `ingredientId` 从来源切换到目标；名称、数量、单位、备注、购买状态等快照字段保持原值，不自动合并行。
6. 扫描并改写所有未发布 JSON 导入草稿中引用来源或其旧归并项的食材：同步写入目标 ID、目标当前名称和目标当前分类，并重算条目错误、状态和所属任务统计。
7. 写管理员审计，至少记录操作者、来源 ID、目标 ID、来源合并前状态、被改指向的归并项数量、更新的可变引用数量和操作时间。
8. 写入幂等结果并提交。任一步失败时整体回滚，不出现“来源已归并但草稿仍指向旧 ID”的部分成功。

目标食材的分类、默认单位、图片、`proteinType`、`isStaple`、`isSpicyIngredient`、`aliases`、营养映射和单位换算在事务中均不修改。

## 引用处理边界

### 立即切换到目标的可变引用

- `FridgeItem.ingredientId`
- `ShoppingItem.ingredientId`
- 未发布 `RecipeImportItem.recipeBodyJson` 中的真实食材引用，以及对应名称、分类、校验结果、条目状态和任务统计

切换冰箱和购物引用时保留原有名称、数量、单位和备注快照。若同一清单因此出现两行都指向目标食材，首版仍保留两行，避免擅自换算单位或合并用户备注。

### 保持不变的历史事实

- 已发布 `RecipeContentVersion.ingredientsJson`
- 已发布导入项及其固定内容
- 食材推荐和纠错审核记录
- 来源食材的营养映射与单位营养换算
- 其他记录来源名称、分类或食材版本的历史快照

这些记录继续保留当时事实。读取历史版本时仍展示其冻结内容，不能因为当前主食材变化而伪造过去正文。

### 后续派生时解析到主食材

当历史固定版本继续产生新的可变业务数据时，服务端先按食材 ID 解析当前身份：

```text
ACTIVE -> 使用自身
MERGED -> 使用 mergedTo 指向的 ACTIVE 主食材
PENDING / DISABLED / 无效关系 -> 按当前业务规则阻断，不猜测替代项
```

适用场景包括从历史菜谱创建新的编辑草稿、生成新的购物项、复制到新的可变清单或其他会创建正式新引用的流程。解析只改变新数据使用的 ID，不回写来源固定版本。

## JSON 导入匹配

精确名称匹配优先级调整为：

```text
ACTIVE > MERGED（解析到 ACTIVE 目标） > PENDING > DISABLED
```

1. 命中 `ACTIVE`：直接引用该食材。
2. 命中 `MERGED`：验证其目标仍是 `ACTIVE` 系统食材，然后写入目标 ID、目标名称和目标分类；导入草稿不保存归并项 ID。
3. 命中 `PENDING`：保留待审核引用，条目不可发布。
4. 命中 `DISABLED`：保留已下架引用，条目不可发布，不自动恢复或另建同名 `PENDING`。
5. 完全未命中：沿用现有规则创建或复用 `PENDING` 系统食材。

这里只做现有名称标准化后的精确 `searchKey` 匹配。归并项的名称承担识别作用，不启用模糊匹配，也不把 JSON 的分类建议用于覆盖目标分类。

## 并发、成本和安全

1. 合并是低频后台治理写操作，不新增缓存、Outbox 或异步 Worker。
2. 合并入口只处理一个来源和一个目标，不提供无界批量 ID。
3. 未发布导入草稿可能跨任务，实施前必须核对真实数量和单事务成本；若当前数据量不能安全放入一个事务，应先提出分批且可恢复的新设计，不能在本设计下静默改为最终一致。
4. 列表目标搜索沿用分页和最大 `pageSize`，只选择目标候选所需字段。
5. 两个管理员并发操作同一来源时，只有满足 `expectedVersion` 和允许状态的一次成功；另一次返回冲突。
6. 两个来源同时合并到同一目标允许分别成功；目标资料不被更新，因此不产生目标字段覆盖。

## 测试与验收

### 数据库和服务端

1. migration 审计和 Check 覆盖三项行内不变量，自引用和脏关系会阻断迁移。
2. 合并接口覆盖 `ACTIVE → ACTIVE`、`DISABLED → ACTIVE`、来源已有归并项重指向、版本冲突、重复幂等、自合并、个人食材、`PENDING` 来源、非 `ACTIVE` 目标和并发竞争。
3. 事务回滚测试证明任一引用更新或审计失败时，来源状态和全部引用均不发生部分提交。
4. 冰箱、购物测试确认只切换 ID，名称、数量、单位、备注和行数不变。
5. 未发布导入测试确认来源及旧归并项引用统一切到目标，并同步名称、分类、错误、条目状态和任务统计；已发布条目不改。
6. 导入名称匹配覆盖 `ACTIVE > MERGED > PENDING > DISABLED`，命中归并项时最终保存目标 ID。
7. 从历史固定版本创建新草稿或购物项时覆盖 `MERGED → ACTIVE` 解析；固定版本 JSON 断言保持原值。

### 后台

1. 状态筛选可查看“已归并”，行内展示唯一目标。
2. 只有 `ACTIVE / DISABLED` 行出现“合并”，目标候选只含其他 `ACTIVE` 系统食材。
3. 确认提示完整，成功后列表和数量刷新，冲突和业务错误不会显示虚假成功。
4. `MERGED` 行不能编辑、上下架、删除、再次合并或解除归并。

### 最小验证门禁

实施阶段至少执行：数据库迁移前审计、Prisma validate/generate、API 和 Admin 定向测试、API/Admin type-check、OpenAPI 校验、API/Admin build、`git diff --check`，并通过真实后台浏览器完成一次“长茄子 → 茄子”合并和一次再次导入“长茄子”的端到端验收。生产 migration、生产数据审计和发布后真实导入仍是独立上线门禁。

## 预计变更面

实施计划需要细化但不得超出以下边界：

- `apps/api/prisma/schema.prisma` 和一个新的前向 migration。
- Admin 合并 DTO、Controller、Service、OpenAPI 和聚焦测试。
- 系统食材归并解析、JSON 导入匹配、未发布导入回写、冰箱和购物引用迁移的服务测试。
- `apps/admin/src/apis/ingredient.ts`、`apps/admin/src/pages/IngredientItemsPage.vue` 及定向测试。
- `docs/ingredient.md`、`docs/api-contract.md`、独立实施计划和中央变更日志。

不在本次顺带重构大型 Service、拆分通用管理中心或调整前台食材选择器视觉。
