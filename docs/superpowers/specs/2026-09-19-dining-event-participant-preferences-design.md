# 饭局参与人偏好与备注设计

## 目标

让饭局成员能一次性提交最多 3 道“我带菜”和最多 3 道“我想吃”，并通过“我的备注”提交本次饭局的饮食说明。成员只看到参与饭局所需的信息，不看到主家的采购清单和食材准备区域。

## 已确认的业务规则

1. “我带菜”和“我想吃”分别最多 3 道，两个上限独立计算；每次打开菜谱 Sheet 可以多选后一次提交。
2. 带菜引用参与人自己的固定菜谱版本；同一参与人对同一饭局的带菜是完整替换，不保留旧的单道带菜列。
3. 想吃沿用饭局想吃池：一次提交最多 3 道，已存在的提议只增加当前用户的支持，不重复创建支持记录。
4. 成员可以填写本次饭局专属备注；备注属于参与人和饭局关系，不修改公共饭局提醒，也不修改个人口味。
5. “我的备注”Sheet 顶部固定多行输入框，下方按个人口味分类展示可多选标签。标签来源于 `GET /api/users/me/taste-profile` 的四个数组字段：过敏、严格忌口、不喜欢食材、口味偏好；个人口味里的“备注”保持普通多行文本，不作为快捷标签来源。
6. 点击口味标签只把选中文案追加到本次备注输入框，去重并以中文分号分隔；提交后只保存饭局参与人备注。
7. 主家继续使用公共“饭局提醒”；主家参与人管理中能查看参与人的饭局备注。其他成员只能看饭局公开信息和参与人备注，不获得采购或食材缺口数据。

## 数据与接口

### 持久化

- `DiningEventParticipant.note` 保存参与人本次饭局备注，最大 255 字符，可为空。
- 新增 `DiningEventParticipantBringRecipe` 关系表，一行表示一位参与人带的一道固定菜谱版本；唯一约束为 `(participantId, recipeVersionId)`，`recipeId` 允许因菜谱实体删除而为空，查询按创建顺序返回。
- 旧 `bringRecipeId` / `bringVersionId` 列直接迁移为关系表数据后删除，不保留兼容字段。

### 请求

- `POST /api/dining-events/{eventId}/wishes`：`{ recipeIds: UUID[] }`，数组 1–3 项、唯一。
- `POST /api/dining-events/{eventId}/bring`：`{ recipeIds: UUID[] }`，数组 1–3 项、唯一，完整替换当前参与人的带菜。
- `POST /api/dining-events/{eventId}/my-note`：`{ note: string | null }`，仅当前饭局成员可写，空文本保存为 `null`。

### 响应

- 参与人摘要返回 `bringRecipes: Array<{ recipeId, recipeVersionId, title }>` 和 `note`；不再返回单值带菜字段。
- 成员读取饭局详情时，`shoppingListId`、`shoppingListName`、`shoppingListStatus` 返回 `null`；成员客户端不渲染采购/食材准备区域。主家仍按现有字段读取自己的采购事实。

## 页面行为

1. 带菜和想吃的菜谱 Sheet 的选择状态支持多选，达到 3 道时未选项不可继续加入，并显示剩余数量。
2. “我带菜”按钮和“我想吃”按钮显示当前已选数量；重新打开 Sheet 时回显当前已提交集合。
3. 成员的饭局详情显示“我的备注”区域；主家显示“饭局提醒”区域。
4. 成员点击“添加备注/编辑备注”打开上滑 Sheet：备注输入框始终位于标签分类上方；口味数据加载中、失败、空态均有明确反馈；标签可多选，已选标签高亮。
5. 主家参与人管理的成员行显示该成员备注摘要，空备注不显示占位内容。
6. 成员不显示“食材准备”区域、缺口预览、采购清单入口和底部“去采购/查看采购清单”动作。

## 权限与失败路径

- 服务端重新校验饭局状态、成员状态和菜谱 owner；主家不能把自己的菜放进成员的带菜/想吃池。
- 数组超过 3 项、重复 ID、空数组或菜谱不属于当前用户时返回业务错误，不产生部分写入。
- 成员备注只允许当前参与人写；主家公共提醒接口权限不变。
- 所有写入使用现有数字字符串 `Idempotency-Key`；同一请求重试返回第一次结果。

## 验证范围

- API：请求 DTO 数组约束、带菜完整替换、想吃最多 3 道、成员备注权限/幂等、成员最小响应。
- Client：Sheet 多选上限、口味标签回填、成员隐藏采购区与底部采购动作、主家备注入口保持。
- 静态类型检查和 mp-weixin 构建；真实微信/设备展示仍需人工验收。
