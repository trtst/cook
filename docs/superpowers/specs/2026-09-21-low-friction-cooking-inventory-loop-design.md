# 低摩擦做饭库存闭环设计

## 状态

2026-09-21 已由用户确认并补充低摩擦交互收口，作为实现基线。本文只描述当前确认的业务行为，不替代 `docs/api-database-rules.md` 的接口、数据库和迁移门禁。

## 目标

把库存维护从“采购时逐项记账”改成“做饭时由系统顺带更新”，让用户主要围绕下一顿饭做决定；精确数量仍可主动补充，但不阻塞正常做饭、采购和推荐。

核心原则：

> 用户只决定“做不做、买没买到、有没有例外”；数量、缺口、入库和消耗沿着固定菜谱来源由系统推导。

## 非目标

1. 不建设仓储级库存、成本核算或全局精准库存模式。
2. 不把计划结束、饭局结束或采购完成解释为实际消耗。
3. 不对“适量”调味料做虚假的数量换算。
4. 不按食材名称猜测未绑定的库存身份。
5. 不覆盖用户手动添加的购物项；自动来源项独立维护。
6. 不并行建设第二套库存写入系统；采购自动入库和做饭自动消耗都复用现有库存批次事实与写入边界。
7. 冰箱属于用户本人，不建设餐厅或饭局共享冰箱；饭局只分配菜谱责任，不改变库存归属。

## 一、统一领域语义

### 菜谱、计划、清单和冰箱

- 菜谱固定版本提供计划用量和菜谱来源。
- 计划/饭局记录时间、人数、菜单和责任人，不直接扣库存。
- 购物清单记录待购买任务；自动写入项必须保留菜谱、计划或饭局来源。
- 冰箱记录当前可用线索；精确库存可计算，粗略库存只表达存在或状态。
- “做饭完成”是唯一自动消耗库存的正式事件。

计划、饭局、购物清单和做饭消耗必须引用确认时的固定菜谱版本，不能用后来修改的菜谱重算历史餐次。

### 冰箱归属和并发

- 缺口计算只读取当前用户自己的冰箱。
- 饭局做饭完成只处理当前用户负责的菜和当前用户自己的冰箱。
- 饭局未指定责任人或当前用户没有负责菜时，只有用户明确确认“标记整桌完成”后，才允许用当前用户自己的冰箱处理整桌用量；不影响其他参与者。
- 不同用户不会扣减同一份冰箱库存；同一用户的并发做饭事件通过数据库事务和 `FridgeItem.version` 防止重复扣减。
- 餐厅共享冰箱属于后续独立能力，必须重新设计归属、权限、共享清单、并发和迁移，不纳入本闭环。

### 库存精度状态

服务端区分以下状态，客户端使用简短文案：

| 服务端语义 | 前台文案 | 是否参与精确扣减 |
| --- | --- | --- |
| 精确数量和可比较单位 | 当前有 `N 单位` | 是 |
| 存在记录但数量未知 | 可能有，数量未记录 | 否 |
| 用户粗略标记 | 快用完 | 否 |
| 已无可用库存 | 已用完 | 否 |
| 无库存记录 | 缺少 | 否 |

用户手动输入明确数量和单位后，仍然属于精确库存，可以继续自动扣减。只有“快用完”“用完”“清空数量但保留食材”或单位无法比较时才降级为粗略状态。

### 菜谱用量

- 精确菜谱用量按当前餐次人数换算。
- `适量` 仅保留为逐项提示，不参与精确扣减和精确合并。
- 同一顿饭内相同最终有效食材、相同单位的精确用量先合并，再执行一次扣减。
- 合并结果保留来源菜名和菜谱版本，供结果摘要和审计使用。

### 菜谱整体状态

菜谱详情不展示复杂的多项状态组合，只展示一道菜的综合结论，优先级为：

```text
MISSING > SHORTAGE > UNKNOWN > READY
```

对应文案为：`缺少 X 样`、`还差 X 样`、`可能有，数量未记录`、`现在就能做`。

## 二、菜谱详情和缺口

菜谱详情展示当前用户范围内的缺口状态：

- 精确库存明确足够：`现在就能做`。
- 精确库存明确不足：`还差 X`。
- 只有粗略库存：`可能有，数量未记录`，不得静默判定为足够或确定缺少。
- 没有库存记录：`缺少 X`。

点击“补齐食材”时，服务端按固定菜谱版本、当前人数和当前库存重算缺口：

1. 确定缺少或确定不足的项自动写入当前有效采购清单。
2. 粗略库存项保留为“待确认”，不静默过滤，也不自动写成确定购买项。
3. 没有有效采购清单时才自动创建默认清单；有清单时不再让用户选择目标清单。
4. 自动写入项必须有稳定来源键，可重复请求而不产生重复未完成项。
5. 用户撤销自动写入时，只撤销本次来源项，不删除手动项或其他来源项。

计划或饭局菜单确认后，按同一规则自动补充关联采购清单。菜单变更只更新原来源项，不覆盖手动采购内容。

`UNKNOWN` 只在用户主动查看时进入确认流程。缺口页将其显示为可展开列表，每项可以选择“够用”“不够，加入采购”或“暂不处理”，底部提供“全部确认”以批量应用同一种处理方式；不确认不会阻止做饭，也不会自动加入确定缺口。

购物清单的事实按来源保留，展示层按“食材 + 单位”合并。同一食材来自多个计划或饭局时默认只显示一行合计数量，展开后可以查看每个来源；删除某个来源后，展示数量重新计算。

## 三、采购完成和自动记入冰箱

采购清单继续支持逐项“已购”和例外处理；所有项目均已购时，主按钮直接执行“全部买到，完成采购”，不再进入独立入库确认页。部分项目未购时，完成动作直接结束已购项，未购项保留为待购买状态，并在结果页显示已完成和未购数量，不追加确认步骤。

点击“完成采购”后，服务端在同一事务内：

1. 只处理已购项，未购项保留采购事实。
2. 为已购项创建个人冰箱批次或存在记录。
3. 默认只写“有库存”语义；数量、精确单位和到期时间均可为空。
4. 不默认生成七天到期时间。
5. 保留 `sourceShoppingListId`、`sourceShoppingItemId` 和来源快照。
6. 重试使用同一个幂等键返回同一结果。

采购完成页不再提供“是否入库”选择。自动记入冰箱后的即时结果提供“撤销记入”操作；服务端只接受完成后 5 分钟内且没有后续修改的撤销请求，前端离开结果页后隐藏入口，之后改用冰箱详情页手动修正。

## 四、做饭完成和自动消耗

做饭模式在最后一步提供“这顿做完了”。该动作提交一个唯一的做饭完成事件，不能由计划关闭或饭局结束隐式触发。

服务端处理步骤：

1. 读取当前餐次固定菜谱版本、人数、责任人和用户本人冰箱；只处理当前用户负责的菜和当前用户自己的冰箱。
2. 合并同一顿饭中相同食材且单位一致的精确用量。
3. `SEASONING + FUZZY` 行跳过精确扣减。
4. 精确库存按 FEFO 顺序跨批次分摊扣减；库存不足时扣除可用部分，剩余缺口进入异常摘要，不虚构扣减结果；数量未知的库存不参与精确扣减。
5. 粗略库存记录“本次用过、余量未知”，不伪造剩余数量。
6. 单位不一致、数量不足或无可靠库存时，该项进入异常摘要，不阻塞其他可处理项。
7. 同一做饭完成事件重复提交时返回原结果，不得重复扣减；用户可以在餐次完成后 48 小时内从历史餐次补录，补录使用提交时的当前库存状态，不回溯历史库存；当前库存不足时按可用数量扣减，剩余缺口进入异常摘要。

结果摘要显示“已按菜谱用量估算”，不得使用“精确扣减”文案。根据结果动态显示已更新数量、数量未知、库存不足和适量跳过的条数。自动消耗结果在当前结果页提供一次撤销；服务端保存完整的跨批次扣减记录，只有完成后 5 分钟内且所有相关批次都没有后续修改时才允许整体反向恢复，否则整个撤销被拒绝，不能覆盖用户之后的手动修正。

没有计划来源但从菜谱详情直接做饭时，使用当前固定菜谱版本和当前人数建立同样的做饭完成事件。多人饭局只处理当前用户负责的菜和当前用户自己的冰箱；饭局未指定责任人或当前用户没有负责任何菜时，页面提示“当前没有你负责的菜，是否标记整桌完成”，由用户明确确认后只处理当前用户自己的冰箱，不影响其他参与者。

## 五、异常和手动修正

正常路径不弹窗。以下情况仅在结果摘要中显示例外：

- 数量未知；
- 单位无法比较；
- 精确库存不足；
- 用户只做了部分份量；
- 某道菜临时没有使用某项食材。

异常操作只提供：

- `按有库存处理`：保留粗略存在状态，不参与精确计算；
- `标记快用完`；
- `暂不处理`。

冰箱详情页提供精准入口：补充数量、补充到期时间、精准调整消耗。输入明确数量后恢复精确参与；粗略标记不会要求用户补数字。

## 六、来源、幂等和撤销

- 自动购物项以来源键去重，来源项和手动项分离。
- 自动购物项被用户删除后保留已移除事实；复用现有购物项的 `status = DELETED`、`removedByUserId` 和 `removedAt` 作为来源墓碑，后续同步遇到相同来源键时不重新加入，不新增独立来源表或 `removedByUser` 字段。
- 购物清单提供“已移除来源”列表，用户可以手动恢复某个来源；恢复后该来源的自动写入重新生效。
- 来源事实分开保存，展示层可以按食材和单位合并，不因展示合并而丢失来源。
- 做饭完成以做饭事件键幂等，菜谱来源、人数和合并行写入结果快照。
- 撤销只允许当前完成结果页发起，并且服务端必须同时检查 5 分钟时间窗和该自动事件尚未被后续手动操作覆盖。
- 采购自动记入冰箱和做饭自动消耗均使用客户端生成的数字字符串 `operationId` 作为 `Idempotency-Key`；服务端按 `userId + operationType + operationId + requestHash` 作用域幂等，`requestHash` 包含餐次、固定菜谱版本、责任人等业务上下文，不把多个业务字段拼接成非数字幂等键。
- 撤销批次版本检查使用自动操作完成后保存的 `FridgeItem.version`；手动补充数量、标记快用完、再次扣减或其他更新导致版本变化时，整体撤销被拒绝。
- 事务失败时，不允许只完成一部分来源变更后返回成功；可独立处理的食材异常应记录为结果摘要而不是让整顿饭失败。
- 历史餐次补录只影响当前用户自己的冰箱，不改变计划或饭局状态，不通知其他饭局成员。

## 七、验收重点

1. 菜谱详情按 `MISSING > SHORTAGE > UNKNOWN > READY` 显示一个综合状态，数量未知不阻止做饭。
2. 自动清单项可重复写入而不重复，撤销不影响手动项。
3. 完成采购直接写入有库存记录，不再进入入库确认页；数量和到期时间为空合法，全部已购时支持一键完成。
4. 相同食材多菜合并后只扣一次，`适量`不扣，来源可回看。
5. 粗略库存不阻止做饭或推荐，精确库存按 FEFO 扣减。
6. 重复点击做完不会重复扣减，5 分钟内且无后续修改可撤销，离开页面后前端隐藏撤销入口。
7. 计划/饭局结束不触发消耗，做饭完成才触发消耗。
8. 采购预占仍是预占，不被误当成真实扣减。
9. 同一食材来自多个来源时展示合并、事实分开；用户移除自动项后不会被再次写回。
10. 用户忘记当天确认时，可以在 48 小时内从历史餐次补录；补录使用提交时的当前库存，不触发饭局状态和成员通知。
11. 跨三个批次的扣减必须保存三条反向分配记录；任一批次发生后续修改时，整体撤销失败。
12. 用户级冰箱下，两个参与者同时完成各自负责的菜时分别处理各自冰箱，不产生共享库存竞态。
