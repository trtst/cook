# 工程决策文档

## 结论

- 使用这套文档时，应先明确前后端技术栈与接口边界。
- 当前工作应优先保证可维护性与快速验证。
- 即使是新需求，也必须先写清交付边界，再进入实现。
- 除非明确重新打开边界，否则范围应保持收敛。
- 当前以菜谱、饭局、购物清单协作和个人会员规则为准；菜谱以 `recipe.md` 为准，食材与单位以 `ingredient.md` 为准，会员与空间以 `configuration.md` 为准。

## 已确认产品决策

1. 菜谱、冰箱、计划和饭局归个人；购物清单默认归个人创建者，但允许按单张清单共享协作。
2. 当前协作主链路收口为饭局邀请、参与、带菜与餐后回忆分享，不再保留独立饭搭子关系入口。
3. 任何协作变化都不得冻结、切换、合并、迁移或复制个人数据。
4. 菜谱不设置可见权限；能访问用户或菜谱入口即可查看，但只能编辑自己的菜谱。
5. 导入菜谱使用固定基础版本加个人字段级覆盖；来源更新不自动改变已导入内容。
6. 首次新增、替换或加工菜谱图片时，暂按当前方案转为个人独立版本；仅删除图片不触发。
7. 系统不自动判断菜谱是否因修改变成另一道菜，只有新建、再次导入或另存为新做法才增加数量。
8. 冰箱完全个人化，不共享、不共同编辑；购物清单不扩成共享空间，但允许按单张清单通过链接邀请协作，且不使用食材认领。
9. 计划采用稀疏周计划；具体多人用餐由饭局承接，可从计划中的一餐发起。
10. 饭局可分享给外部用户；计划、饭局和“我带菜”可使用本人持有的“我的”菜谱或只读收藏，不能使用草稿。
11. 只销售个人 Free、Plus、Pro、Ultra，不销售共享空间或成员席位。
12. 当前不建设通用权限中心；协作权限只在具体饭局或清单动作里按事实校验。
14. “我的口味”属于用户本人，过敏和忌口安全能力永久免费。
15. 当前不实现小票、OCR、AI 和冰箱物品图片，不为其提前占位。
16. 会员到期不删除核心数据；空间超额允许清理、导出和续费。
17. 会员开通、升级和续费只能直接付费，饭票或积分不得购买、抵扣或混合支付会员。
18. 活动、成就和勋章保持非货币属性，不提高共同点菜权重或安全权限。
19. 菜谱主页面固定为“私房菜 / 灵感”；“私房菜”按单选个人分类管理，私房菜页面是默认主菜单。
20. 灵感系统菜谱只读；改编或从灵感加入计划时保存为私房菜，已有来源私房菜直接复用，不重复创建。
21. 个人发布只进入“私房菜”；推荐到灵感必须提交固定版本并经过人工审核，未修改的灵感菜谱不能重复推荐。
22. 灵感支持一人一票的点赞和按持有人去重的收藏量，不开放评论、关注、用户搜索、点赞用户列表或排行榜。
23. 系统与个人食材使用统一分类体系；分类不上传图片，个人食材不配置单项图片，系统食材可由后台后期补传 `50x50` 小图；个人食材和单位立即本人可用，明确推荐后才进入后台审核。

## 文档范围

包含：

- 前后端核心结构
- 共享工程规则
- 技术栈确认
- 启动基线
- 交付边界写法
- 接口协议约束
- 验证与评审流程

不包含：

- 未确认的业务扩展
- 临时实验记录
- 已不再指导实现的历史设计讨论
- 用“后续再说”替代的隐性需求

## 为什么需求也要写边界

边界不是为改造场景准备的，而是为避免需求持续漂移准备的。

如果不写边界，最常见的问题是：

1. 开发过程中顺手加需求。
2. 验收时口径临时变化。
3. 登录、权限、埋点、适配、数据源、持久化这类附属能力默认被算进范围。
4. 首版应先占位还是一次做全，团队内部没有统一判断。
5. 前后端各自理解的接口口径不一致。

## 最小边界模板

在落到具体需求前，至少要写清以下内容：

1. 当前要做哪些页面或模块。
2. 当前明确不做什么。
3. 是否包含登录、权限、埋点、国际化、暗黑模式、响应式适配。
4. 后端是否包含持久化、任务处理、数据源切换、文件读取或第三方接口接入。
5. 首版交付标准是什么。
6. 哪些内容允许先占位，哪些必须一次做完整。
7. 哪些接口、数据结构、状态码或交互细节仍待确认。

## 关键边界

1. 不要顺手扩张范围。
2. 不要把临时说明当成长期规则。
3. 不要混用当前规则与归档材料。
4. 未先澄清受影响边界前，不要做架构调整。
5. 未写清是否属于当前范围前，不要默认接入附属能力。
6. 未写清接口协议前，不要前后端各自先写一版。
7. `docs/cook/` 中的 Schema/SQL 是来源材料，冲突时不能覆盖当前权威文档。
8. 产品规则已确认不等于当前代码已实现；API、DTO、数据库必须按当前契约逐项评审。

## 商业化评估规则

每个新功能都必须记录免费基础、付费增量、权益作用域、额度类型、到期行为、数据保留、配置来源和合规影响。“永久免费”和“不商业化”是合法结论。

过敏安全、基础菜谱、冰箱、计划、购物、基础饭局参与和退出不得变成付费墙。基础勋章获得不作为付费墙，未实现的权益不得出现在会员销售页面。

## 交付边界

这套主文档只需足够支撑以下事项：

- 开发
- 评审
- 验证
- 联调
- 交接

落到具体仓库或需求时，建议在这里补齐一句明确表述：

- 当前交付：`<页面 / 模块 / 功能范围>`
- 当前不交付：`<明确排除项>`
- 接口边界：`<统一返回结构 / 状态码 / 数据源方式 / 持久化范围>`

## 一句话总结

保持工程文档精简、权威，并提前写清技术栈、接口边界、启动基线和交付范围。
