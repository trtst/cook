# 工程决策文档

## 结论

- 使用这套文档时，应先明确前后端技术栈与接口边界。
- 当前工作应优先保证可维护性与快速验证。
- 即使是新需求，也必须先写清交付边界，再进入实现。
- 除非明确重新打开边界，否则范围应保持收敛。
- 饭搭子生命周期以 `dining-group.md` 为准，会员与空间以 `configuration.md` 为准。

## 已确认产品决策

1. 注册自动创建单人饭搭子，单人与多人共用一套空间逻辑。
2. V1 每人只有一个活跃长期饭搭子，不做普通切换和多家庭协作。
3. 长期加入冻结原空间，主动迁入；退出恢复原空间，并通过限时快照选择带回。
4. 菜谱广场没有收藏，只有浏览和收录；收录后支持独立修改。
5. 饭局承接临时来客，不开放冰箱、购物、完整计划和完整菜谱库。
6. “我的口味”属于用户本人，过敏和忌口安全能力永久免费。
7. 当前只开放 Free/Plus；Pro 与多家庭协作一起后置。
8. 当前不实现小票、OCR、AI 和冰箱物品图片，不为其提前占位。
9. 会员到期不删除核心数据；超额立即只读，允许清理、导出、退出和续费。
10. 个人 Plus、饭搭子 Plus 的开通、升级和续费只能直接付费，饭票或积分不得购买、抵扣或混合支付会员。
11. Plus 个性推荐是持续权益，只增强本人推荐响应，不改变安全过滤、饭搭子投票或全局推荐权重。
12. V1 不做通用饭票或积分钱包；活动与成就改为非货币留存层，围绕真实用餐闭环和饭局完成沉淀勋章。
13. 勋章不提现、不兑换、不抵扣会员、不转赠；获得资格由服务端真实业务状态判定，客户端和后台不得伪造完成次数。
14. Free 用户可获得基础勋章；Plus 只增加展示、历史、统计、纪念卡等沉淀权益，不提高共同点菜或投票权重。

## 文档范围

包含：

- 前后端核心结构
- 共享工程规则
- 技术栈确认
- 启动基线
- 交付边界写法
- 接口协议约束
- 验证与评审流程

不包含：

- 未确认的业务扩展
- 临时实验记录
- 已不再指导实现的历史设计讨论
- 用“后续再说”替代的隐性需求

## 为什么需求也要写边界

边界不是为改造场景准备的，而是为避免需求持续漂移准备的。

如果不写边界，最常见的问题是：

1. 开发过程中顺手加需求。
2. 验收时口径临时变化。
3. 登录、权限、埋点、适配、数据源、持久化这类附属能力默认被算进范围。
4. 首版应先占位还是一次做全，团队内部没有统一判断。
5. 前后端各自理解的接口口径不一致。

## 最小边界模板

在落到具体需求前，至少要写清以下内容：

1. 当前要做哪些页面或模块。
2. 当前明确不做什么。
3. 是否包含登录、权限、埋点、国际化、暗黑模式、响应式适配。
4. 后端是否包含持久化、任务处理、数据源切换、文件读取或第三方接口接入。
5. 首版交付标准是什么。
6. 哪些内容允许先占位，哪些必须一次做完整。
7. 哪些接口、数据结构、状态码或交互细节仍待确认。

## 关键边界

1. 不要顺手扩张范围。
2. 不要把临时说明当成长期规则。
3. 不要混用当前规则与归档材料。
4. 未先澄清受影响边界前，不要做架构调整。
5. 未写清是否属于当前范围前，不要默认接入附属能力。
6. 未写清接口协议前，不要前后端各自先写一版。
7. `docs/cook/` 中的 Schema/SQL 是来源材料，冲突时不能覆盖当前权威文档。
8. 产品规则已确认不等于当前代码已实现；API、DTO、数据库必须按当前契约逐项评审。

## 商业化评估规则

每个新功能都必须记录免费基础、付费增量、权益作用域、额度类型、到期行为、数据保留、配置来源和合规影响。“永久免费”和“不商业化”是合法结论。

过敏安全、基础菜谱/冰箱/计划/购物、基础饭局参与、退出与菜谱带回不得变成付费墙。基础勋章获得不作为付费墙，未实现的权益不得出现在会员销售页面。

## 交付边界

这套主文档只需足够支撑以下事项：

- 开发
- 评审
- 验证
- 联调
- 交接

落到具体仓库或需求时，建议在这里补齐一句明确表述：

- 当前交付：`<页面 / 模块 / 功能范围>`
- 当前不交付：`<明确排除项>`
- 接口边界：`<统一返回结构 / 状态码 / 数据源方式 / 持久化范围>`

## 一句话总结

保持工程文档精简、权威，并提前写清技术栈、接口边界、启动基线和交付范围。
