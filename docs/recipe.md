# 菜谱产品、版本与流转规则

## 文档定位

本文是菜谱信息架构、录入、收藏、导入、推荐、版本和固定引用的当前产品权威文档。食材与单位规则见 `ingredient.md`，额度与空间计量见 `configuration.md`，计划和饭局引用规则见 `dining-group.md`。

本文只确认产品行为和数据语义，不冻结 API 字段、DTO、表、索引或迁移。现有候选实现与本文冲突时，必须先回到 `plans/recipe-execution.md` 完成契约设计和评审。

## 一、菜谱主页面

菜谱主页面顶部固定为 `我的 / 灵感 / 合集`，与微信胶囊齐平：

1. `我的`：本人可编辑的菜谱，按个人自定义分类组织。
2. `灵感`：平台系统菜谱和审核通过的用户推荐菜谱，按平台分类组织。
3. `合集`：本人收藏的固定版本，按个人自定义场景组织。

搜索框用于搜索菜谱和食材，并随页面正常滚动。分类区域 Sticky 在 Header 下方，菜谱列表在分类区域下方滚动；各 Tab 的具体检索范围在 API 契约阶段确认，不由客户端猜测。

登录门禁：

1. 未登录用户进入菜谱主页面时默认展示“灵感”，可以浏览灵感列表和详情。
2. 未登录用户进入“我的”或“合集”时触发登录。
3. 点赞、收藏、升级为“我的”和推荐到灵感都必须登录，未登录操作时触发登录。
4. 匿名可读不表示可以绕过内容状态；只有审核通过且当前允许曝光的灵感固定版本可以匿名读取。

### 我的

1. 默认分类为“全部”，其他个人分类可横向滑动。
2. 每道“我的”菜谱必须且只能选择一个个人分类。
3. 管理入口支持个人分类排序和分类内菜谱排序。

### 灵感

1. 默认分类为“全部”，其他平台分类可横向滑动。
2. 左侧“全部”和右侧筛选图标固定，中间平台分类横向滑动。
3. 点击筛选后，筛选抽屉从右向左滑入。
4. 首版筛选包括推荐/最新、难度和时长；时长与录入页一致，使用 `15分钟内 / 15~30分钟 / 30~60分钟 / 1小时以上` 四档；抽屉内选择是临时状态，点击“应用”后才生效。

### 合集

1. 默认场景为“全部”，其他个人场景可横向滑动。
2. 一道菜谱可以加入 `0～N` 个个人场景；场景不是菜系分类。
3. 同一道菜谱加入多个场景仍只是一条收藏，不重复占额度。
4. 管理入口支持个人场景排序，并维护一套跨场景复用的全局收藏顺序。

## 二、列表和滚动交互

菜谱列表使用两列等高竖卡：

1. 封面比例固定为 `4:3`。
2. 菜谱名称最多展示两行。
3. 信息行左侧展示“难度 · 时长”，右侧展示分类。
4. 灵感卡片增加点赞量和收藏量，收藏操作位于图片右上角。
5. 用户推荐来源的“由某某整理”只在详情页展示，卡片不展示。

页面右下角提供浮动管理图标，但只在“我的”和“合集”出现。页面滚动时图标向右滑出隐藏，停止滚动后向左滑回显示。

## 三、分类与场景

分类和场景是两套不同的个人管理数据：

1. 分类用于管理“我的”菜谱，一道菜谱只能属于一个分类，发布时必选。
2. 场景用于组织合集和个人使用情境，一道菜谱可选多个，也可以不选。
3. 添加或编辑菜谱时，分类和场景都使用可换行的 Tag 选择，不使用持续增长的纵向列表。
4. 个人分类、个人场景与平台分类彼此独立，不互相自动映射。
5. 推荐到灵感时选择的是建议平台分类，后台审核人员可以调整。

## 四、菜谱内容与录入

菜谱内容包括：封面、名称、故事、个人分类、个人场景、基准人数、难度、总时长、食材与用量、制作步骤和小贴士。

基础录入区按以下顺序展示：

1. 上传封面。
2. 菜谱名称。
3. 这道菜的故事。
4. 个人分类。
5. 个人场景。
6. 食材与用量。
7. 制作步骤。

高级设置包括基准人数、难度、总时长和小贴士。高级设置默认收起，点击后打开约占页面高度 `90%` 的上滑弹窗。弹窗顶部左侧为关闭，中间为标题，右侧为保存；关闭直接丢弃本次临时修改，只有点击保存才写回录入页。

总时长不使用自由分钟输入，统一使用固定四档：

1. `15分钟内`。
2. `15~30分钟`。
3. `30~60分钟`。
4. `1小时以上`。

录入页底部提供“预览、存草稿、发布”。发布只进入“我的”，不等于进入灵感。

### 发布校验

发布时必须具备：

1. 菜谱名称。
2. 一个个人分类。
3. `1～20` 人份的基准人数。
4. 至少一个食材及其有效用量。
5. 至少一个有效制作步骤。

封面、故事、个人场景、难度、总时长和小贴士均为选填。

### 草稿

1. 新建菜谱的草稿计入菜谱数量和个人空间。
2. 已有菜谱的编辑草稿不额外占菜谱数量，但新增结构化内容和正式图片计入个人空间。
3. 草稿不能用于计划、饭局、合集或推荐到灵感。
4. 草稿入口放在管理功能中的草稿箱，不混入已发布列表。

## 五、食材与用量

食材必须从系统食材库或本人食材库选择；食材和单位的建立、审核与换算规则见 `ingredient.md`。

菜谱用量支持两种表达：

1. 精确数量加单位。
2. `适量 / 少许 / 按需` 等模糊用量。

基准人数换算只处理精确数量。模糊用量不是单位，不参与数学换算。

## 六、制作步骤与图片

每个制作步骤是一组 `0/1 张图片 + 0/1 段文字`，支持纯图片、纯文本和图文组合，但图片和文字不能同时为空。

步骤录入规则：

1. 每组可添加、替换或删除图片，并输入一段文字。
2. 点击“添加新步骤”后追加一组。
3. 步骤区右侧支持批量上传，选择几张图片就按选择顺序追加几个纯图片步骤。
4. 步骤组支持拖动排序和删除。
5. 封面固定为 `4:3`，步骤图片保留原比例。
6. 步骤图片可以直接设为封面；复用同一正式文件时不重复计入空间。

图片上传先进入临时区。服务端必须校验真实类型、尺寸、体积和像素总数，移除 EXIF 并重新编码。临时图片保留 24 小时且不计个人空间；存草稿或发布时才正式绑定，并按处理后的最终文件大小计费。

当前代码尚未开放菜谱图片写入。现阶段候选 API 不接受图片写入字段；在新的图片契约、对象存储和安全验收完成前，不得把以上产品规则误报为已实现能力。

## 七、固定版本与个人修改

菜谱正文使用不可变的固定内容版本。饭局、计划、分享、收藏、导入和推荐审核提交都必须引用固定版本，不能引用会被后续编辑改变的实时正文。

来源菜谱产生新版本时，不自动改变已经收藏、导入、加入计划、加入饭局、分享或提交审核的版本。

从来源菜谱建立可编辑的“我的”菜谱时，使用：

```text
个人有效菜谱 = 固定基础版本 + 个人覆盖修改
```

普通文字修改保存结构化字段覆盖；读取时由服务端合并为完整有效菜谱。个人分类、场景、排序、做过次数和显示别名属于个人管理数据，不改变来源基础版本。

首次新增、替换或加工来源图片时，菜谱转为个人独立版本；只隐藏来源图片不触发独立化。独立化后仍只占一个菜谱名额，新增、替换或加工后的图片计入个人空间。

覆盖数据过多时，服务端可以将有效正文压缩为完整技术快照以改善读取性能，但不能改变用户可见身份、菜谱数量或已经固定的计划和饭局版本。

## 八、收藏、升级与重复处理

收藏是保存到“合集”的只读固定版本：

1. 收藏计入个人菜谱数量和个人空间。
2. 收藏可直接用于计划和饭局，但不能直接编辑正文。
3. 收藏不自动跟随来源更新。
4. 收藏升级为“我的”时必须选择一个个人分类，保留个人场景，不重复占菜谱数量。
5. 重复收藏同一来源固定版本时打开已有入口，不新建第二条收藏。
6. 只读收藏可以直接取消；升级为“我的”后按普通删除和回收站规则处理。

已修改的导入菜谱可以执行“再次导入原版”，明确新增一份新的个人菜谱并额外占用数量和空间。未修改的相同来源再次导入时打开已有入口；内容相似但来源不同只提示，不自动合并。

系统不根据修改字符数、食材比例或名称变化自动判断“变成另一道菜”。只有用户明确新建、再次导入或另存为新做法时，才增加菜谱数量。派生做法只能由根菜谱创建，不能再次派生。

## 九、推荐到灵感

本人创建或已形成个人改编的菜谱详情可以发起“推荐到灵感”：

1. 本人创建的菜谱可直接推荐。
2. 从灵感升级为“我的”并完成编辑后，可以按“推荐我的改编做法”提交。
3. 未修改的灵感菜谱不能重复推荐。
4. 提交时选择建议平台分类，后台审核人员可以调整。
5. 提交的是当时固定版本；后续编辑个人菜谱不直接改变审核版本。
6. 推荐状态包括未推荐、审核中、驳回、已收录和已撤回。
7. 审核中可以撤回；驳回后可以修改并重新提交。
8. 已收录内容更新时走新一轮审核，旧审核版本在新版本通过前继续展示。
9. 删除个人菜谱不自动删除已收录的平台版本；用户可单独撤回推荐。

审核通过的用户推荐菜谱只在详情页显示 `由某某整理`。该标识不跳转用户主页，使用审核通过时的昵称快照；没有可用昵称时显示“由一位炊友整理”。产品不展示“原创作者”，也不以推荐标识判断版权归属。

推荐到灵感属于受控内容投稿，不扩展为用户动态流。首版不开放评论、关注、用户搜索、点赞用户列表或排行榜。

## 十、点赞、收藏量与排序

1. 点赞不占菜谱数量或个人空间，同一用户对同一灵感菜谱最多一个有效点赞。
2. 收藏量按当前持有该来源菜谱的用户去重，不按场景数或重复入口累加。
3. 灵感推荐排序综合平台质量、点赞、收藏、新内容扶持和时间衰减。
4. 收藏意愿高于轻量点赞，因此收藏权重应高于点赞，但具体权重本轮不冻结。
5. “最新”按首次审核通过时间排序，内容更新通过新审核后不重新置顶。

## 十一、来源删除与技术保留

来源用户删除菜谱时，其个人入口按本人套餐规则删除。只要固定版本仍被收藏、其他用户菜谱、计划、饭局、分享或已收录灵感引用，该版本就继续作为不可变技术数据保留。

技术保留不表示恢复来源用户的可见菜谱，也不授予任何人编辑来源的权限。引用全部释放后，技术版本才可以进入幂等清理。

因违规、安全或合规要求必须强制下架时，服务端可以阻止继续曝光，并按合规策略处理依赖引用；普通删除规则不能覆盖安全处置。

## 十二、空间、安全与性能

1. 固定基础版本在物理层可以只保存一次，但每个持有人的逻辑空间按 `configuration.md` 计量。
2. 服务端必须能从业务数据全量重算逻辑使用量，不能只依赖容易漂移的累计计数。
3. 菜谱列表只返回摘要，正文和覆盖合并按详情或批量菜单需要读取。
4. 基础版本、覆盖、点赞和收藏统计不得造成列表 N+1 查询。
5. 合并结果和统计结果可以缓存，但写入后必须精确失效。
6. 对其他用户可见的图片和文本必须经过必要的内容安全流程。
7. 菜谱编辑、独立化、收藏升级、派生、推荐提交和删除必须在后续契约中设计事务、版本校验和幂等边界。
