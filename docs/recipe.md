# 菜谱数据、导入与版本规则

## 文档定位

本文是个人菜谱归属、可见性、基础版本、覆盖修改、图片独立化、派生做法和固定引用的当前产品权威文档。额度与空间计量见 `configuration.md`。

## 一、归属与可见性

菜谱归当前持有人。用户只能编辑和删除自己的菜谱，不能直接修改其他用户的菜谱。

菜谱不设置公开、私密、仅饭搭子可见或成员白名单：

1. 能进入用户或菜谱入口，就能查看其菜谱。
2. 当前通过饭搭子菜谱和分享入口发现其他用户菜谱。
3. 首版菜谱广场和搜索只覆盖“我的个人菜谱 + 系统菜谱”，搜索字段仅菜名和食材，不包含其他用户菜谱。
4. 查看不计入查看人的菜谱数量和空间。
5. 导入后才形成查看人的个人菜谱。

首版不做用户搜索、关注、评论和榜单；其他用户菜谱仍只通过已存在的饭搭子菜谱或分享入口进入。

不设置可见权限不代表没有内容治理。违规、侵权、敏感信息和安全风险仍可由平台限制曝光或下架。

产品不判断原创归属，不展示“原创作者”，使用“某某的菜谱”或“由某某整理”等中性表达。

## 二、基础版本

菜谱正文使用不可变的固定内容版本。正文至少包括菜名、食材、用量、步骤、份量、时间和图片引用。

饭局、计划、分享和导入必须引用固定版本，不能直接引用会被后续编辑改变的实时正文。

来源菜谱产生新版本时，不自动改变已经导入、加入计划、加入饭局或分享出去的版本。

## 三、导入模型

导入其他用户或系统菜谱时，先创建属于当前用户的轻量菜谱入口：

```text
个人有效菜谱 = 固定基础版本 + 个人覆盖修改
```

未修改时：

1. 计入个人菜谱数量。
2. 继续引用导入时的固定基础版本。
3. 不复制完整正文和来源图片。
4. 同一来源版本重复导入时打开已有入口。
5. 来源更新可以提示存在新版本，但不自动更新。

来源信息默认不在前端展示，不用于原创、权限或自动同步判断。

## 四、字段级覆盖修改

普通文本修改不复制整份菜谱，而是保存结构化字段级覆盖：

1. 修改食材用量：保存该食材的新用量。
2. 修改步骤：保存修改后的完整步骤文本，不保存字符差异补丁。
3. 新增食材或步骤：保存新增项。
4. 删除基础项：保存删除标记。
5. 调整顺序：保存个人排序。
6. 修改份量、时间或菜名：保存对应字段的新值。

即使只修改一个字符，也只新增对应字段覆盖。读取时由服务端合并基础版本和覆盖数据，返回完整有效菜谱。

个人备注、分类、标签、排序、做过次数、最近做饭时间和显示别名属于个人管理数据，不改变基础版本。

覆盖数据过多时，服务端可以将有效正文压缩为完整技术快照以改善读取性能。该操作不改变用户可见身份、不新增菜谱数量，也不能改变饭局和计划已经固定的版本。

## 五、图片独立化，暂按当前方案

本节是后续图片上传能力的产品契约，当前尚未实现图片上传、删除、替换或加工。现阶段 `POST /recipes` 和 `PUT /recipes/{recipeId}` 的请求正文不接受 `images`；提交该字段返回 `400`。已有系统图片和历史图片仅可读取，文本编辑由服务端保留原图片。未来图片大小、类型和尺寸必须来自服务端接收并重新编码后的文件事实，不接受客户端声明。

首次新增、替换或加工图片时，菜谱转为个人独立版本：

```text
基础版本 + 已有覆盖修改 + 个人图片 = 个人独立版本
```

| 图片操作 | 是否转为个人独立版本 |
| --- | --- |
| 新增图片 | 是 |
| 替换图片 | 是 |
| 裁剪、滤镜、标注后保存 | 是 |
| 只删除基础图片 | 否，只保存隐藏标记 |
| 删除全部基础图片但不上传 | 否，只保存隐藏标记 |
| 删除后重新上传 | 是 |

转为个人独立版本后：

1. 仍然只占一个菜谱名额。
2. 当时的有效结构化正文固化为个人版本。
3. 来源降为内部弱记录，不再用于更新提示。
4. 未替换的基础图片可以继续复用。
5. 新增、替换或加工后的图片计入个人空间。

该规则当前允许后续调整，但在新契约确认前不得由客户端自行判断。

## 六、再次导入与重复提示

重复判断不能用来认定原创，也不能阻止用户创建不同做法。

1. 未修改的轻量入口再次导入同一固定版本时，打开已有菜谱。
2. 已产生覆盖修改或已经独立化时，可以提示“曾经导入过”。
3. 用户仍可选择再次导入原版本，形成新的个人菜谱入口。
4. 内容相似但来源不同只提示，不自动合并。
5. 删除个人菜谱后，对应个人导入关系和覆盖数据一起删除。

## 七、新建、编辑与派生

以下行为必须区分：

| 行为 | 结果 |
| --- | --- |
| 普通编辑 | 仍是当前菜谱，更新覆盖或个人独立版本 |
| 新建菜谱 | 创建无基础引用的个人菜谱 |
| 另存为新做法 | 创建新的派生菜谱，占用派生额度 |
| 再次导入 | 创建新的个人菜谱入口 |

系统不根据修改字符数、食材比例或名称变化自动判断“变成另一道菜”。只有用户明确新建、再次导入或另存为新做法时，才增加菜谱数量。

派生做法只能由根菜谱创建，不能再次派生。套餐额度和删除规则见 `configuration.md`。

## 八、来源删除与技术保留

来源用户删除菜谱时，其可见入口按本人套餐规则删除。只要固定基础版本仍被其他用户菜谱、计划、饭局或分享引用，该版本就继续作为不可变技术数据保留。

技术保留不表示恢复来源用户的可见菜谱，也不授予任何人编辑来源的权限。引用全部释放后，技术版本才可以进入幂等清理。

因违规、安全或合规要求必须强制下架时，服务端可以阻止继续曝光，并按合规策略处理依赖引用；普通删除规则不能覆盖安全处置。

## 九、空间与物理存储

物理存储与个人逻辑空间分开计算：

1. 固定基础版本在物理层只保存一次。
2. 每个持有人的逻辑空间计算基础结构化数据和个人覆盖数据。
3. 来源图片可以物理复用，不重复计入个人图片空间。
4. 个人新增、替换或加工后的图片按压缩后大小计入本人空间。
5. 技术快照只在有固定业务引用时保留。

服务端必须能从业务数据全量重算逻辑使用量，不能只依赖容易漂移的累计计数。

## 十、安全与性能

1. 菜谱列表只返回摘要，正文和覆盖合并按详情或批量菜单需要读取。
2. 基础版本和覆盖读取必须避免逐条查询，列表不得产生 N+1。
3. 合并结果可以按基础版本、覆盖版本和个人菜谱版本缓存，但写入后必须精确失效。
4. 图片上传必须校验类型、尺寸、体积、像素总数，移除 EXIF 并重新编码。
5. 对其他用户可见的图片和文本必须经过必要的内容安全流程。
6. 菜谱编辑、独立化、派生和删除必须使用事务、版本校验和幂等边界。
