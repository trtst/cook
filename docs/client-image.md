# 客户端图片能力约定

## 目的

本文只约束 `apps/client` 当前已经落地的图片选择、裁剪、本地预览、延迟上传和本地清理规则。

它解决的是工程一致性问题，不重新定义菜谱、用户资料或会员图片权益。

## 当前范围

当前已落地的能力：

1. 菜谱封面图单图选择与裁剪。
2. 菜谱步骤图单图与批量选择、逐张裁剪。
3. 裁剪完成后的本地预览。
4. 保存草稿或发布前的延迟上传。
5. 持久本地文件的 best-effort 清理。

当前明确不做：

1. 头像上传业务接入。
2. 即选即传。
3. 通用多媒体管理器。
4. 页面外直接调用 `uni.uploadFile`、`uni.saveFile`、`uni.removeSavedFile`。

## 分层

当前图片能力只允许分成 3 层：

1. 平台层：`apps/client/src/platform/uni.ts`
   - 只封装 uni / 小程序媒体能力。
   - 包含 `chooseMedia`、`getImageInfo`、`saveFile`、`removeSavedFile`、canvas 导出。
2. 流程层：`apps/client/src/utils/image-crop.ts` 与 `apps/client/src/composables/useImageCropFlow.ts`
   - 只维护裁剪协议、裁剪预设、裁剪会话和页面间回填流程。
   - 不承载业务字段名，不直接发上传请求。
3. UI 层：`apps/client/src/pages_recipe/components/ImageField.vue`
   - 只负责单图空态、预览、更换、删除交互。
   - 不知道菜谱、头像、饭局等业务概念。

页面负责：

1. 当前图片属于哪个业务字段。
2. 何时允许选择、删除、保存。
3. 保存时调用哪个上传接口。
4. 上传成功后如何把结果写回页面状态。

## 统一流程

单图或多图都遵守同一条主流程：

`选择图片 -> 入裁剪队列 -> 裁剪页导出 -> saveFile 持久化 -> 页面本地预览 -> 保存时上传 -> 上传成功后释放本地文件`

约束：

1. 选择图片后不立即上传。
2. 页面内优先展示本地文件路径。
3. 只有在“保存草稿 / 提交 / 发布”等真正写请求时，才把本地文件上传到后台。
4. 上传成功后清空页面里的本地路径，并尝试删除旧的持久本地文件。

## 裁剪策略

裁剪差异只允许通过预设表达，不允许页面散写任意参数。

当前预设：

1. `recipeCover`
   - `fixed`
   - `4:3`
   - 导出 `1200 x 900`
2. `recipeStep`
   - `free`
   - 不固定比例
   - 最长边限制 `1280`
3. `profileAvatar`
   - `fixed`
   - `1:1`
   - 导出 `720 x 720`
   - 目前只保留预设，不接业务入口

后续新增图片场景时，先判断能否复用既有预设；不能复用时再新增预设，不在页面内直接拼参数。

## 本地文件规则

图片临时文件与持久文件要分开看：

1. 选择器和 canvas 初始返回的通常是 `tmp` 文件。
2. 裁剪完成后必须尽快 `saveFile`，再把持久路径回填页面。
3. 页面状态里长期持有的应该是 `savedFilePath`，不是 `tmp` 路径。
4. 删除图片、替换图片、上传成功后，都要 best-effort 调用 `removeSavedFile` 清理旧本地文件。

注意：

1. 清理失败不能阻断主流程。
2. 页面不能假设 `getImageInfo` 一定返回可直接用于上传的桥接 URL。
3. 页面不能把开发者工具里的 `http://127.0.0.1:xxxx/tmp/...` 当成权威本地路径。

## 上传时机与节省策略

当前统一采用延迟上传，原因不是“实现简单”，而是为了控制：

1. 流量：避免用户反复裁剪、反复替换时每次都真实上传。
2. 存储：避免未保存内容提前占用后台空间。
3. 安全：避免临时选择但最终取消的图片提前进入后台。
4. 一致性：只让真正提交的内容进入草稿或正式记录。

因此默认规则是：

1. 本地预览可以多次替换。
2. 只有页面发生真实保存写入时才上传。
3. 没有保存成功的本地图片，不应写入业务正式记录。

## 安全与滥用约束

当前图片能力必须遵守这些约束：

1. 上传场景白名单由业务 API 定义，页面不能自由拼 scene。
2. 裁剪输出尺寸和质量走预设，不让页面随意放大原图导出。
3. 真机上传时禁止把 `127.0.0.1/localhost` 当目标接口地址。
4. 调试日志不进入正式链路。
5. 不因为“复用”而做一个跨业务字段、跨接口、跨权限的大上传中心。

## 组件使用约定

`ImageField` 当前是 `pages_recipe` 私有单图组件，只适合单图。

适用：

1. 菜谱封面图。
2. 菜谱单个步骤图卡片。
3. 后续头像这类单图场景。

不适用：

1. 多图网格管理。
2. 页面级上传编排。
3. 需要知道上传接口、鉴权、scene 或 slotKey 的逻辑。

如果后续出现“多图列表也需要统一 UI”，优先新增 `ImageListField`，不要继续把单图组件堆条件做大。

## 后续头像接入方式

头像上传业务重新放开后，按下面顺序接入：

1. 复用 `profileAvatar` 裁剪预设。
2. 复用 `useImageCropFlow`。
3. 复用 `ImageField` 单图 UI。
4. 在“我的”页或资料编辑页补业务写接口和保存入口。

在头像业务未确认前，不要提前补：

1. 头像上传按钮。
2. 头像保存接口调用。
3. 头像即时上传。
4. 通用用户资料图片管理中心。

## 一句话规则

图片能力的复用顺序必须是：

`先统一协议和流程，再统一单图 UI，最后才接新的业务场景`
