# 饭搭子关系与协作规则（已下线，保留历史资料）

## 文档定位

本文件自 2026-08-19 起只保留为历史产品边界资料，不再作为当前前台、后台或 API 的现行权威文档。当前协作主链路以饭局、购物清单分享及现行 API 契约为准；菜谱内容、收藏与导入规则见 `recipe.md`，食材与单位规则见 `ingredient.md`，会员和空间数值见 `configuration.md`。

以下内容反映的是饭搭子功能下线前的历史规则，保留用于追溯旧数据、旧迁移和历史执行单，不再作为新增实现依据。

## 一、核心模型

饭搭子是长期协作关系，不是共享空间。

每个用户始终独立拥有自己的菜谱、冰箱、用餐计划、饭局和口味资料。购物清单默认由创建者拥有，但允许按单张清单邀请协作者共同维护。加入或退出饭搭子只改变成员关系，不冻结、切换、合并、迁移或复制个人数据。

当前规则：

1. 每个用户最多创建一个自己主理的饭搭子。
2. 用户可以在个人会员额度内加入其他饭搭子。
3. 自己创建的饭搭子计入“可加入饭搭子数”。
4. 饭搭子不单独售卖会员、空间或成员席位。
5. 首版不支持主理人转让；主理人可直接解散自己主理的饭搭子，且只解除关系。
6. 新用户默认不自动创建饭搭子；只有用户在饭搭子页显式开启后，才创建自己主理的第一个饭搭子。

## 二、数据归属

| 数据 | 归属 | 协作边界 |
| --- | --- | --- |
| 菜谱 | 当前持有人 | 可查看、导入，不能直接编辑别人的菜谱 |
| 冰箱 | 用户本人 | 不共享、不共同编辑 |
| 购物清单 | 清单创建者 | 可按单张清单共享协作，不形成共享空间 |
| 用餐计划 | 创建人 | 默认个人使用，可从其中一餐发起饭局 |
| 饭局 | 发起人 | 参与人只访问本次饭局必要信息 |
| 口味、过敏、忌口 | 用户本人 | 参加饭局时按次提交必要快照 |

成员加入前后的个人数据保持不变。退出或被移除后也不生成迁出快照，不存在“原空间恢复”或“数据带回”。

## 三、饭搭子成员关系

饭搭子包含一名主理人和若干成员。首版固定权限为：

| 身份 | 默认权限 |
| --- | --- |
| 主理人 | 修改饭搭子名称与简介、邀请、移除成员、查看成员列表、解散饭搭子 |
| 成员 | 查看成员列表和成员菜谱、接受饭局邀请、主动退出 |
| 所有人 | 只能编辑自己的个人业务数据 |

后续可以增加饭搭子级协作权限，例如允许某成员邀请新人、管理成员或发起全员饭局。该能力属于协作权限，不属于会员权益；首版不提前建设通用权限系统。

饭搭子主页主图当前按个人会员权益开放：

1. 只有 `OWNER` 可以上传或替换。
2. 当前只对 `Pro / Ultra` 开放。
3. 主图计入主理人的个人空间，不属于共享资产。
4. 普通成员可以查看当前主图、聚合数据和动态，但不能修改主图、名称、简介，也不能看到解散入口。

## 四、邀请与加入额度

创建邀请时校验主理人的“可邀请人数”。接受邀请时再次校验：

1. 邀请仍然有效且未被消费。
2. 目标饭搭子的有效受邀成员数未超过主理人当前套餐额度。
3. 接受人的有效饭搭子关系数未超过本人当前套餐额度。
4. 接受人不是目标饭搭子的有效成员。
5. 写入具备幂等、并发锁和审计，不能并发突破额度。

具体额度见 `configuration.md`。接受邀请不触碰接受人的菜谱、冰箱、计划或购物清单归属。

## 五、退出与移除

成员可以主动退出，主理人可以移除成员。操作只结束成员关系，并保留必要的历史参与事实。

退出或移除后：

1. 用户的个人数据不变。
2. 用户不再通过该饭搭子获得成员快捷入口。
3. 已参加或已完成的饭局记录继续保留在“我的饭局”。
4. 已公开可见或已被导入的菜谱不因成员关系结束而删除。
5. 未结束的饭局参与关系按饭局规则处理，不因退出饭搭子自动取消。

主理人解散饭搭子时，按结束全部成员关系处理；不冻结、不迁移、不恢复任何个人数据，也不回填旧空间或快照。

## 六、会员降级与超额受限

会员到期或配置降低后，服务端立即按当前个人套餐重新计算邀请人数和加入数量。

任一维度超额时，相关用户或饭搭子进入 `OVER_MEMBER_LIMIT` 语义的超额受限状态。该状态不删除成员，也不自动选择保留对象。

超额期间允许：

1. 查看饭搭子、成员和成员菜谱。
2. 主动退出饭搭子。
3. 主理人移除成员。
4. 查看历史饭局和已有参与记录。

超额期间禁止：

1. 创建或接受新的饭搭子邀请。
2. 修改饭搭子名称、简介和主页主图等资料。
3. 修改成员协作权限。
4. 通过饭搭子入口一键邀请成员参加饭局。

个人菜谱、冰箱、计划、饭局和购物清单不因饭搭子超额而整体锁定。数量降到当前套餐额度后，饭搭子操作自动恢复。

## 七、用餐计划

用餐计划暂按稀疏周计划设计，服务用户安排实际准备做饭的餐次，不要求每天填写或形成连续打卡。

首版规则：

1. 默认展示本周，仅创建实际需要安排的日期和餐次。
2. 每餐可以选择一道或多道本人持有的“我的”菜谱或只读收藏；草稿不能进入计划。
3. 可以根据未来餐次生成个人购物建议。
4. 可以复制上周计划。
5. 不实现营养目标、复杂周期计划、月计划和每日打卡。
6. 计划默认属于个人，不直接承载长期成员权限。
7. 计划是“我这周这顿吃什么”的个人排餐容器；饭局是“这顿和谁一起吃”的多人事件。两者仍是不同对象，但前端可收敛到同一个“餐次详情页”：计划信息作为基础层，饭局信息作为该餐次上的增强层。
8. 每场饭局都必须归属一个明确餐次：日期加早餐、午餐或晚餐。
9. 直接创建饭局时，默认同步到我的计划；该餐次没有计划项则自动创建，有计划项则挂到原计划项上。
10. 同一用户在同一日期、同一餐次下，最多只允许一场未取消且未结束的有效饭局。
11. 创建或修改饭局时，服务端和页面都要做同餐次占用校验与实际时间冲突提示，避免用户出现“分身乏术”的重复安排。
12. 若计划餐次已有菜谱，创建饭局时默认带入对应固定版本作为候选菜；饭局确认最终菜单后，计划页优先展示饭局最终菜单摘要，不再维护第二份可漂移菜单。

用户可以从计划中的某一餐发起饭局。计划餐次和饭局引用同一份固定菜单事实，不复制维护两份可漂移的菜单。

## 八、饭局

饭局是一场具体的多人用餐，包含时间、地点、发起人、参与人、固定菜单和带菜情况。

饭局可以直接创建，也可以从计划中的某一餐发起。发起人可以：

1. 直接邀请饭搭子成员。
2. 通过分享邀请外部用户。
3. 查看接受、拒绝和取消参加状态。
4. 管理本次饭局菜单和参与人。
5. 先从本人持有的“我的”菜谱或只读收藏中设置 N 道候选菜，并配置每位参与人最多可选择 X 道；草稿不能成为候选菜。
6. 根据参与者选择结果确认最终菜单，并为每道最终菜指定责任人。

“我的饭局”显示本人创建和本人参与的饭局。外部参与人不会因此成为饭搭子成员，也不会获得任何人的冰箱、购物清单或完整计划访问权。

成员选择规则：

1. 参与者的选菜只表达偏好，不直接改写最终菜单。
2. 同一道候选菜可以被多人选择，发起人可查看选择人数和明细。
3. 最终菜单只能由发起人确认；确认后进入锁定态，再修改时必须同步重算后续缺口和购物建议。
4. 参与者接受邀请后可在候选菜范围内选择；拒绝或未接受时不进入正式选菜流程。

## 九、我带菜

参与人通过“我带菜”从本人持有的“我的”菜谱或只读收藏中选择一道菜。

1. 不认领具体食材。
2. 不共享个人冰箱库存。
3. 不展示个人采购明细。
4. 其他参与人只看到谁准备带什么菜。
5. “我带菜”属于责任分配：只对该参与者本人负责的菜生效，不把整场饭局默认变成发起者独自采购。
6. 系统可以根据该菜谱和本人冰箱生成个人缺口。
7. 做完后由本人决定是否扣减个人库存。

计划、饭局和“我带菜”都引用选择时的固定菜谱版本。来源菜谱或个人菜谱后续修改，不自动改写已经确认的餐次和购物事实。

## 十、冰箱与购物清单

冰箱始终归个人，不允许饭搭子成员查看、拿取或共同编辑。

购物清单采用“清单头 + 清单项”的模型。清单默认由创建者拥有，不因加入饭搭子而整体合并；共享只发生在单张清单层，不形成长期共享空间。个人购物项目可以来自：

1. 手动创建。
2. 菜谱固定版本加入。
3. 周计划生成。
4. 饭局菜单生成。
5. “我带菜”生成。
6. 个人冰箱缺口生成。

共享购物清单规则：

1. 首版角色只分 `创建者` 和 `协作者`，不建设管理员和通用权限中心。
2. 创建者可改名、分享链接、分享给饭搭子成员、移除成员、完成、作废、恢复、删除和复制清单。
3. 协作者可勾选采购完成、取消完成、添加食材、删除食材、从菜谱加入、退出协作和复制清单。
4. 协作者复制共享清单时，复制结果是自己的新个人清单，默认不继承原协作成员。
5. 共享链接要求登录后加入；支持分享给饭搭子成员，但不把整组成员默认整包写入同一张清单。

饭局、计划和购物清单联动规则：

1. 计划、饭局和购物清单都必须保留来源链，至少能回溯到菜谱固定版本；购物清单项可继续补充 `planItem`、`diningEvent` 等来源引用。
2. 正式购物清单只在饭局最终菜单确认后生成或补充；确认前最多只做个人预估缺口。
3. 哪道菜进入谁的购物清单，取决于该道菜的责任人，而不是谁发起了饭局。
4. 发起者负责的菜进入发起者创建或选择的购物清单。
5. 参与者通过“我带菜”负责的菜，只进入该参与者本人创建或加入的购物清单。
6. 不把全场已确认菜单默认整包写入发起者单人清单；若需多人共同采购，必须显式使用共享清单。

完成清单与入库规则：

1. 购物清单状态分为 `采购中`、`已完成`、`已作废`。
2. 采购进度按食材项数计算，不按重量或金额计算。
3. 点击“完成清单”时必须先进入入库确认流程，而不是直接整单自动入库。
4. 默认只带入“已勾选采购完成”的食材项进入入库确认。
5. 入库确认只处理 `是否入库`、`数量` 和 `到期时间`；不要求生产日期。
6. 到期时间默认 `7 天`，支持快捷值、单项修改和同食材批量设置。
7. 只有被确认入库的食材项才进入个人冰箱；未入库项保留采购完成事实，但不写入库存。

首版共享购物清单不要求实时协同，不依赖 SSE 或 WebSocket。普通接口、操作后刷新、页面重进刷新、下拉刷新和轻轮询即可覆盖当前协作。

## 十一、口味与安全

口味、过敏和忌口属于用户本人，不属于饭搭子，也不计入饭搭子额度。

参加饭局时，用户可以提交本次必要快照。过敏和严格忌口能力永久免费；原始资料不得向无关参与人暴露。共享菜单的安全判断必须使用服务端固定事实，不能由客户端自行放宽。

## 十二、当前不做

首版不实现共享冰箱、食材认领、聊天、成员实时协同编辑、主理人转让、饭搭子空间会员和通用细粒度权限中心。
