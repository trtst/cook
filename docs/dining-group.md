# 饭搭子生命周期与数据规则

## 文档定位

本文是饭搭子、原空间、迁入迁出、饭局和“我的口味”的当前产品权威文档。

当本文与 `docs/cook/`、旧 Prisma v0.1、旧 SQL 或早期多饭搭子方案冲突时，以本文为当前产品规则；历史材料只用于追溯，不能直接指导新实现。会员、空间和配置数值见 `configuration.md`。

## 一、统一空间模型

用户注册后自动获得一个单人饭搭子。单人与多人只使用一种 `DiningGroup` 模型：

```text
单人饭搭子：主理人自己
多人饭搭子：主理人 + 长期成员
```

主理人邀请成员后，原 `groupId` 不变，空间原地从单人变为多人；菜谱、冰箱、计划和购物清单不复制。成员访问同一个饭搭子空间，仅权限不同。

V1 规则：

1. 每人只有一个活跃长期饭搭子。
2. 不提供普通饭搭子切换器。
3. 个人 Plus 不增加可加入饭搭子数量。
4. 多家庭、护工、多户膳食和多饭搭子切换与 Pro 一起保留为未来能力。
5. V1 不支持主理人转让；主理人不能直接退出形成无主空间。

## 二、长期加入与原空间

受邀人接受长期邀请后：

```text
原单人饭搭子 -> FROZEN 原空间
目标饭搭子   -> 当前唯一活跃空间
```

原空间不删除、不继续日常维护、不计入目标饭搭子额度，并作为待迁入资料保留。加入时不自动合并或同步，用户主动选择迁入。

### 菜谱迁入

1. 支持单个和批量选择。
2. 完全重复跳过；同菜不同做法作为变体保留；疑似相似只提示。
3. 迁入遵守目标饭搭子的菜谱数量和空间上限。
4. 超出部分继续留在冻结原空间。
5. 原空间迁入不消耗未来 OCR、AI 或普通批量识别额度。

### 冰箱迁入

冰箱表示真实物品，不能整体复制。只允许迁入用户确认真实带入新家庭的物品；新记录先标记“待确认”，数量不明确时不自动扣减原库存。

### 计划迁入

历史计划和原参与关系不迁入。本人创建但尚未发布的草稿可以复制为新草稿。

### 购物迁入

只迁入尚未购买、仍然需要、归属本人且由本人主动选择的项目。

## 三、数据归属

| 数据 | 归属 |
| --- | --- |
| 菜谱及菜谱图片 | 当前饭搭子 |
| 冰箱库存 | 当前饭搭子 |
| 用餐计划 | 当前饭搭子 |
| 购物清单 | 当前饭搭子 |
| 计划参与关系 | 参与人本人 |
| 饭局参与记录 | 参与人本人 |
| 口味、忌口、过敏 | 用户本人 |

成员加入期间创建的菜谱留在饭搭子中，但成员退出时可以按本文规则复制回原空间。

## 四、菜谱广场与收录

当前不设置“收藏”。用户可以无限浏览和临时跟做公开菜谱；未收录时不占菜谱数量和个人空间。

```text
浏览公开菜谱 -> 收录到当前饭搭子 -> 形成可编辑菜谱
```

收录规则：

1. 固定收录时的不可变内容版本，并保留来源。
2. 收录后可以编辑，后续不自动跟随公开版本变化。
3. 重复收录同一来源版本时打开已有入口，不重复创建。
4. 系统和广场公共图片由平台公共资源池承担，不计入收录人的图片空间。
5. 用户替换或新增的图片计入当前空间。
6. 从广场加入长期计划时，可以先完成收录再加入计划。

菜谱数量默认值见 `configuration.md`。数量超额时不删除已有菜谱，只限制继续创建、收录和迁入；其他模块是否受限取决于空间是否也超额。

### 普通保存与技术快照

当前 Free/Plus 都不提供用户可见的编辑历史。普通保存只更新当前菜谱，不在界面中生成历史版本。

底层仍使用不可变内容快照保证历史计划、分享和迁出快照不被后来编辑改变：内容无变化时不创建新快照；旧快照没有任何计划、分享或迁出引用时可以清理；仍被引用时只作为技术数据保留，用户不需要管理。

### 另存为新做法

“另存为新做法”是 Plus 便利权益，不是编辑历史：

1. Free 不显示该按钮，但仍可从空白手动创建菜谱。
2. 个人 Plus 用户可以在有写权限的当前空间使用；饭搭子 Plus 允许所有有菜谱写权限的成员使用。
3. 同一个系列根菜谱最多存在 2 个未永久删除的派生做法。
4. 只有系列根菜谱可以派生，派生做法不能再次派生。
5. 派生做法进入 Plus 回收站时仍占派生名额，永久删除后释放。
6. 每个派生做法是独立菜谱，计入菜谱数量和空间；未修改图片继续复用。
7. 会员到期不删除已有派生做法，仍可查看、编辑和加入计划，但不能继续另存。
8. 根菜谱仍有派生做法时不能单独永久删除；用户需先删除派生做法或删除整个系列。

目标数据关系使用系列根菜谱作为锚点，不提前增加独立系列表：

```text
根菜谱：rootRecipeId = null
派生做法：rootRecipeId = 根菜谱 ID
```

建议目标字段包括 `dishConceptId`、`rootRecipeId`、`variantName`、`originType`、`sourceVersionId` 和 `currentVersionId`。`ROOT / VARIANT`、派生数量、派生上限和是否可派生由服务端计算，不作为易漂移字段永久保存。最终字段名在 v0.2 API 与数据库契约中冻结。

`originType` 目标语义为 `MANUAL / SYSTEM / PUBLIC / SPACE_IMPORT / CARRY_BACK / DERIVED`。不保存“派生 1 / 派生 2”作为身份编号；用户看到的是“原做法、少糖版、儿童版”等名称，派生列表按稳定 ID 和创建时间管理。

## 五、退出、恢复与带回

长期成员退出后：

```text
原空间       -> 恢复为活跃单人饭搭子
原饭搭子     -> 停止完整实时访问
退出成员     -> 获得私有迁出快照
```

迁出是复制，不是移动；源饭搭子保留原数据，原空间获得独立副本，后续不再同步。

### 菜谱带回

退出人可以选择退出前有权查看的任意菜谱，包括其他成员创建的菜谱，并支持单个、批量或全部带回。

可带回名称、配料、用量、步骤、菜谱图片、时间、份量、难度、来源和固定版本。不带回饭搭子内部成员备注、成员身份评价、计划、库存和购物历史。

数据可携带不受普通导入次数限制。带回后超过个人额度时不删除数据，恢复的原空间进入相应超额状态。带回仅授予个人做菜副本，不自动授予再次公开或商业使用权。

### 冰箱带回

只带回用户确认真实拿走的物品，并在原空间建立待确认库存。

### 计划与参与

1. `MealPlan` 属于饭搭子，参与关系属于用户。
2. 已确认参加的未来计划在退出后继续显示，不自动取消。
3. 用户可以取消，主理人可以移除参与人，计划取消时参与关系结束。
4. 未确认参加的未来计划在退出后不再显示。
5. 已完成且本人参加过的记录保留在“我的饭局”。
6. 未参加的历史计划不保留为个人数据。

### 购物带回

只带回尚未购买、仍然需要、归属本人并由本人主动选择的项目。

## 六、迁出快照

迁出快照是退出成功时冻结的私有导入源：

1. 主动退出和被移除默认生成；安全、违规或合规冻结可例外。
2. 仅退出人本人可见，不实时读取源饭搭子。
3. 有效期内支持分批导入，所有导入必须幂等。
4. 已导入数据永久保留，不受快照到期影响。
5. 用户可以提前永久删除；重新加入同一饭搭子后旧快照失效。
6. 快照优先保存清单和固定版本引用，不在创建时复制全部图片。
7. 快照有效期在创建时解析并固化；会员到期或配置变化只影响新快照。

默认期限和清理规则见 `configuration.md`。

## 七、饭局

统一产品名称：

- 对象：`饭局`
- 发起：`邀请来吃饭`
- 接收：`饭局邀请`
- 点菜：`参与点菜`
- 个人记录：`我的饭局`

饭局是依附于真实用餐计划的临时参与关系，不创建新饭搭子，不占长期成员席位。

临时参与人可以接受、拒绝、取消参加，查看时间、地点、候选和最终菜单，参与点菜，提交本次口味快照，保留本人参与记录，并带回主理人明确共享的菜谱。

临时参与人不能查看冰箱、购物清单、其他内部计划、完整菜谱库、长期成员列表、会员额度和迁入迁出功能。

## 八、我的口味

“我的口味”属于用户本人，不属于饭搭子，不迁移。内容包括过敏原、严格忌口、不喜欢的食材和口味偏好。

参加饭局或计划时，用户可以一键使用个人资料、针对本次调整并提交固定快照。菜谱可以动态显示适合、过敏冲突、忌口冲突、偏好不匹配或信息不足；结果不写入菜谱内容。

过敏和忌口安全提示永久免费，原始资料不得暴露给无关参与人，也不计入会员空间。

## 九、购物需求归属

购物项目必须区分：

```text
需求范围：GROUP / USER
需求人
创建人
采购负责人
完成人
```

建议契约概念为 `needScope`、`needUserId`、`createdByUserId`、`assignedToUserId`、`completedByUserId`。最终字段名须在 v0.2 API 与数据库契约中冻结。

退出时只有 `USER` 范围、需求人为当前用户、尚未购买且由用户主动选择的项目可以带回。共同需求不会因创建人退出而迁走。

## 十、状态语义草案

以下是 v0.2 目标语义，不表示当前代码已经实现：

| 对象 | 状态 |
| --- | --- |
| 长期成员 | `ACTIVE / RESTRICTED / ENDED` |
| 结束原因 | `LEFT / REMOVED / GROUP_DOWNGRADED / GROUP_DISSOLVED` |
| 长期邀请 | `PENDING / ACCEPTED / DECLINED / REVOKED / EXPIRED` |
| 原空间 | `ACTIVE / FROZEN` |
| 迁出快照 | `AVAILABLE / EXPIRED / DELETED / INVALIDATED` |
| 空间 | `NORMAL / OVER_RECIPE_LIMIT / OVER_STORAGE_READONLY` |
| 菜谱 | `ACTIVE / ARCHIVED / RECYCLED` |

单人或多人由有效成员数量推导，不另存容易漂移的协作状态。Free 删除不进入 `RECYCLED`；Plus 删除进入回收站。

## 十一、实施边界

当前不接入小票识别、OCR、AI、冰箱物品图片、Pro、多家庭协作或多饭搭子切换。不得为这些 Reserved 能力提前增加业务入口、通用中心、数据库枚举或占位服务。

具体实施顺序见 `plans/dining-group-lifecycle-plan.md`。
