# 可复用组件

## 编写原则

只记录真正共享、稳定、或被多个页面重复使用的组件。

单页面私有组件、一次性业务组件、边界还没稳定的组件，不进入共享组件文档。

## 组件准入规则

一个组件只有在满足以下至少一项时，才建议进入共享组件层：

1. 被两个及以上页面复用。
2. 承担明确稳定的通用 UI 职责。
3. 需要统一视觉、交互或输入输出规范。
4. 已经确认后续不会频繁改边界。

uni-app 小程序端还需要同时满足分包边界：只服务单个分包的组件默认留在分包内，跨分包真实复用后再考虑提升到根公共组件。细则见 `docs/uniapp.md`。

以下情况不建议直接抽成共享组件：

1. 只在一个页面使用。
2. 还在快速变化，需求边界未稳定。
3. 主要承载页面级编排逻辑。
4. 只是为了“看起来更规范”而提前抽离。

## 组件拆分边界

默认规则：

1. 页面负责主流程编排。
2. 组件负责单一 UI 职责。
3. 组件不负责页面级路由跳转组织。
4. 组件不直接承载底层请求细节。
5. 组件输入输出保持显式，不依赖隐式外部状态。

允许组件内部处理的内容：

1. 本组件显示所需的局部状态。
2. 明确属于本组件的交互行为。
3. 与本组件展示直接相关的显示逻辑。

不建议放进组件的内容：

1. 页面级数据加载编排。
2. 跨区域状态协调。
3. 多模块共享业务决策。
4. 临时拼接的接口协议处理。

## 组件命名规则

1. 名称按职责命名，不按位置凑名字。
2. 组件名使用简短驼峰，最多 3 个单词。
3. 优先使用能表达结果和用途的名字。
4. 不使用边界模糊的抽象名词。
5. 不为了通用而起空泛名称。
6. 禁止使用 `normalized`、`formatted`、`processed` 这类只描述加工过程的词。
7. 少用 `Page`、`Common`、`Base` 这类没有新增语义的前缀。
8. 只有在确实解决歧义时，才补额外限定词；如果仍需解释，通过组件注释说明职责。

示例倾向：

- `Header`
- `Navigation`
- `ChatMessageList`
- `MealCard`
- `RecipeList`

不推荐这类名称：

- `PageHeader`
- `CommonBox`
- `BaseCard`
- `InfoManager`
- `NormalizedRecipePanel`
- `UniversalCard`

## Props 与事件规则

1. `props` 只暴露组件真正需要的输入。
2. 输入字段优先保持稳定，不频繁改名。
3. 事件名直接描述用户动作或结果。
4. 不通过事件回传过多隐式上下文。
5. 能传明确值，就不要让父组件猜。

推荐倾向：

- `@submit`
- `@close`
- `@change`
- `@select`
- `@retry`

不推荐倾向：

- `@handleClick`
- `@doAction`
- `@callback`

## 示例条目

### Header

- 位置：`components/Header/*`
- 职责：提供统一头部结构与基础操作入口
- 适用范围：多个页面共用的顶部区域
- 输入：标题、返回模式、右侧插槽、视觉状态
- 输出：返回、操作点击事件
- 依赖：路由、主题、图标资源
- 不承载什么：页面业务编排、页面级请求逻辑
- 备注：如果某个页面头部结构明显特殊，应先留在页面内，不强行复用

### ChatMessageList

- 位置：`components/ChatMessageList/*`
- 职责：负责消息列表展示与列表内交互透传
- 适用范围：多个聊天或留言场景
- 输入：消息列表、加载状态、渲染配置
- 输出：回复、举报、滚动、重试等事件
- 依赖：消息渲染子组件、滚动容器
- 不承载什么：页面级聊天编排、接口协议兼容、跨房间状态同步
- 备注：当不同场景的消息规则差异过大时，应拆场景组件，而不是继续堆条件

## 一句话规则

共享组件应该是“职责稳定后的复用结果”，不是“提前抽象的愿望”。
