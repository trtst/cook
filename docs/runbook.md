# 工程执行手册

## 目的

本文定义前后端调试、验证与交付的最低执行纪律。

## 三端联合开发流程

当前项目按小程序端、后端 API、后台管理三端并行推进。每个功能必须先形成最小纵切链路，再分别落到三端任务。

标准流程：

1. 确认最小业务流程：用户目标、触发条件、成功路径、失败路径和结束状态。
2. 确认页面行为：入口、展示、操作、加载、空态、失败态和操作后的页面变化。
3. 确认权限和状态：数据 owner、读写主体、状态机、额度、并发和幂等。
4. 基于前三项设计最小接口，再设计最小数据表、约束和真实查询索引。
5. CTO 分别与小程序、后端、后台开发者确认最小任务和不做项。
6. 契约冻结后进入实现；小程序和后台可先使用 mock，但 mock 必须与功能执行单一致。
7. 三端接入真实接口，验证成功、失败、权限以及相关的并发或幂等路径。
8. 功能完成以纵切链路真实验收为准，不以某一端“开发完成”为准。

现有页面、接口、OpenAPI、数据库表和 migration 只能作为候选实现，不能作为业务已确认的证据。未完成业务流程和页面行为确认时，任务不得进入接口契约、数据库设计或编码阶段。

功能执行单使用 `docs/templates/feature_execution_template.md`，按功能存放到 `docs/plans/`。功能执行单记录拆解、开发者确认、联调清单、验收状态和风险；长期工程规则仍写入顶层 `docs/*.md`。

任务状态统一为：

```text
待拆解 -> 待确认 -> 可开发 -> 开发中 -> 待联调 -> 联调中 -> 待验收 -> 已验收
```

进入下一状态的最低条件：

1. `待确认` 到 `可开发`：业务流程、页面行为、权限状态、最小接口和最小数据约束均有确认记录，各端已确认最小任务和不做项。
2. `可开发` 到 `开发中`：接口契约和数据边界已冻结，阻塞项已写明。
3. `开发中` 到 `待联调`：本端主路径可跑通，必要 mock 或接口测试可用。
4. `待联调` 到 `联调中`：真实接口、权限和数据源准备完成。
5. `联调中` 到 `待验收`：小程序、后端、后台主路径跑通。
6. `待验收` 到 `已验收`：机器检查、手动验收和风险记录完成。

## 仓库启动基线

启动基线需要写，但只写最小闭环，目的是保证接手者或几天后的自己可以快速跑起当前仓库。

建议至少写清以下内容：

1. 前端运行时版本要求。
2. 后端运行时版本要求。
3. 安装命令。
4. 前端启动命令。
5. 后端启动命令。
6. 构建或服务运行命令。
7. 环境变量文件名与最少必填项。
8. 本地接口地址、代理方式或 mock 方案。
9. 提交前最低验证项。

- 前端运行时版本：落到具体仓库时确认，并同步写入 `.nvmrc` 或等效文件
- 后端运行时版本：落到具体仓库时确认，并同步写入 `.python-version`、`requirements.txt` 或等效文件

- 数据源切换方式：写明通过环境变量、配置文件或工厂方法切换

## 提交前最低检查

每次提交前至少确认：

1. 依赖可安装。
2. 前后端都能正常启动。
3. 前端构建或后端服务启动命令通过。
4. 统一返回结构符合约定。
5. 受影响页面的主路径已手动验证。
6. 控制台与服务日志无新增明显报错。
7. `docs/plans/minor_change_log.md` 已记录本次实际改动和验证；大改动同时链接独立执行文档。

## 联合开发最低检查

涉及三端协作的功能，提交或合并前还需要确认：

1. `docs/api-contract.md` 或功能执行单中的接口契约已更新。
2. 后端 DTO、OpenAPI 与接口契约一致。
3. 小程序端本地 API 类型与接口契约一致，且没有绕过 API 层。
4. 后台端本地 API 类型与后台接口契约一致。
5. 后端错误码、权限和幂等行为与契约一致。
6. mock 数据与真实接口字段一致，不能用 mock 掩盖契约缺口。
7. 影响发布的未验收项已写入功能执行单风险区。
8. 饭搭子关系变更已对照 `docs/dining-group.md`，菜谱已对照 `docs/recipe.md`，权益和空间已对照 `docs/configuration.md`。

## 饭搭子纵切最低检查

涉及饭搭子、菜谱、会员或空间时，至少验证：

1. 每个用户最多主理一个饭搭子，并可在本人套餐额度内加入多个。
2. 接受邀请同时校验主理人邀请额度和接受人加入额度，不能并发突破。
3. 加入、退出和移除不修改任何个人菜谱、冰箱、计划或购物清单。
4. 降级超额后只允许查看、退出和移除，降低到当前额度后自动恢复。
5. 菜谱文本覆盖、图片独立化、固定版本引用和来源删除保留符合 `recipe.md`。
6. 冰箱和购物清单不能被其他饭搭子成员读取或写入。
7. 空间与菜谱数量超额采用不同限制；只读时仍可查看、永久清理、导出和续费。
8. Free/Plus/Pro/Ultra 的菜谱、空间、图片、派生和回收站分别按服务端权益解析。
9. 清理任务重复执行不重复删除，仍被引用的版本和图片不会被错误物理删除。

## 调试基线

在给出问题结论前，应先收集：

1. 复现路径
2. 前端可见行为
3. 控制台证据
4. 网络证据
5. 服务端日志或错误摘要

## 排查顺序

1. 确认预期规则或需求。
2. 确认复现路径。
3. 检查前端运行时行为。
4. 检查网络请求与统一返回结构。
5. 检查服务端日志、错误码与数据流阶段。
6. 运行时画像清晰后，再回到代码。

## 最低验证要求

### UI 改动

需验证：

1. 视觉结果
2. 布局稳定性
3. 相关时的相邻状态

### 交互改动

需验证：

1. 点击、输入、切换或导航行为
2. 成功路径
3. 相关时的失败或阻断路径

### 数据改动

需验证：

1. 请求结构
2. 响应消费方式
3. 兜底行为

### 后端改动

需验证：

1. 参数校验是否明确。
2. 返回结构是否统一。
3. 错误码是否明确。
4. 数据源切换是否仍可工作。
5. 日志是否保留必要摘要而未泄露敏感信息。
6. 文件读取场景是否仍限制在安全目录内。
7. 配置与密钥是否仍通过环境变量或本地忽略配置读取。

## 分支检查清单

以下情况在相关时要显式检查：

1. 空状态
2. 错误状态
3. 加载状态
4. 登录态与未登录态
5. 返回导航
6. 重复交互
7. 参数错误
8. 资源不存在
9. 服务异常
10. 数据源切换
11. 文件读取越界

## 交付说明

一份合格的交付说明应包含：

1. 改了什么
2. 为什么选择这个方案
3. 验证了什么
4. 还剩什么风险或缺口
5. 是否影响前后端接口协议或数据源行为
6. 本次改动在中央变更记录中的对应条目

三端联合功能的交付说明还应包含：

1. 小程序、后端、后台各自完成了什么。
2. 本次是否修改 `docs/api-contract.md`、OpenAPI 或任一应用的本地 API 类型。
3. mock 是否已经替换为真实接口。
4. 哪些验收项已经通过，哪些仍是风险。
