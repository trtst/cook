# 食材与计量单位规则

## 文档定位

本文是系统食材库、个人食材、计量单位、审核入库和菜谱用量表达的当前产品权威文档。本文只确认产品行为和数据语义，不冻结 API、DTO、表、索引、换算精度或迁移。

## 一、统一食材库

系统只建立一套统一食材库，不分别建立蔬菜库、佐料库或调味品库。食材通过系统分类组织。

首版系统分类：

1. 蔬果菌菇。
2. 肉禽蛋。
3. 水产海鲜。
4. 豆乳制品。
5. 米面杂粮。
6. 调味料。
7. 干货腌制。
8. 酒水饮料。

系统内部额外保留一个隐藏兜底分类：`待归类`。该分类不对前台和后台常规录入开放，只用于历史脏数据、导入异常和临时过渡治理。

“原料、配料、调料”不是食材自身属性。如产品需要区分，应由具体菜谱中的食材关系表达，不能把同一食材复制成多个系统食材。

分类本身不配置上传图片。个人食材不配置单项图片；系统食材允许由后台在后期补传单张小图，当前终存 `50x50`，用于后续小图展示。这样既能控制图片治理成本，也避免把图片变成个人创建食材时的必填身份信息。

系统食材治理补充规则：

1. 后台支持把系统分类和系统食材设为 `启用中 / 已下架`；下架后不再进入前台新增和编辑选择口径。
2. 系统分类和系统食材仅在没有任何食材、菜谱、冰箱、购物、审核、归并或营养映射引用时允许后台物理删除；有引用时只能下架。
3. 已下架系统食材不再出现在新建和编辑菜谱的食材选择器里。
4. 已发布菜谱中的食材名称快照不因系统食材下架或重新上架被回写。
5. 已下架系统食材重新上架后继续使用原食材身份，但恢复时按当前分类末尾重新参与系统排序。
6. 前台可对系统食材提交纠错，当前只收口 `名字 / 分类 / 备注`，用于描述名称、分类或图片展示不符等问题。
7. 系统食材纠错进入后台人工审核；审核采纳后直接更新对应系统食材，驳回只记录审核备注，不生成新的系统食材。后台可删除仍为待审核状态的纠错记录，删除不修改系统食材。
8. 系统食材额外维护一组轻量结构化属性：`proteinType`、`isStaple`、`isSpicyIngredient`、`aliases`。这组属性只用于菜谱自动标签、推荐和后台治理，不替代食材分类本身。
9. `proteinType` 只标记稳定主蛋白事实，如 `猪 / 鸡 / 牛 / 羊 / 鸭 / 海鲜 / 鸡蛋 / 豆腐 / 无`；`isStaple` 用于标记主食类食材；`isSpicyIngredient` 只表达“这是辣味驱动食材”，不直接等于最终菜谱辣度；`aliases` 仅作为后台治理和后续识别辅助，不作为前台展示主名称。

系统食材审核状态：

1. `PENDING`：后台导入或审核流程创建，尚未通过人工确认；不进入前台食材选择器。
2. `ACTIVE`：已审核通过，可被正式菜谱引用。
3. `DISABLED`：已下架，不可用于新建或发布菜谱。
4. `MERGED`：已归并到其他系统食材，正式引用必须切换到目标食材。

后台可将一条 `ACTIVE / DISABLED` 系统食材软归并到另一条 `ACTIVE` 系统食材。来源保留原 ID、名称和分类并转为 `MERGED` 归并项，目标作为唯一主食材；关系只允许一层，来源不能指向自己，已有指向来源的归并项必须同时改指最终主食材。仍被归并项指向的主食材不能直接下架；如需停用，应将该主食材继续归并到另一条 `ACTIVE` 主食材，由事务把已有归并项统一改指最终目标。目标资料不会被来源覆盖，首版不支持解除归并、批量归并、模糊匹配或通用别名表。

归并时只迁移仍可变的引用：冰箱和购物条目仅切换 `ingredientId`，保留名称、数量、单位、备注、状态和条目身份；未发布 JSON 导入草稿切换到主食材 ID，并同步主食材当前名称和分类。已发布 `RecipeContentVersion`、审核历史、来源营养映射和来源单位换算不改写。从历史固定菜谱版本新建购物数据时，若引用的是有效 `MERGED` 项，则新购物数据使用其 `ACTIVE` 主食材；目标失效时阻止生成并提示先治理。

JSON 导入未匹配到的食材，自动创建或复用 `PENDING` 系统食材，不创建个人食材，也不得直接设为 `ACTIVE`。引用该食材的导入项在审核通过、归并或重新匹配前不能发布。

JSON 导入按名称命中已有系统食材时，匹配优先级固定为 `ACTIVE > MERGED（取 ACTIVE 主食材） > PENDING > DISABLED`，并以最终食材当前分类覆盖导入文件中的分类建议。命中 `ACTIVE` 直接复用；命中 `MERGED` 保存主食材 ID、名称和分类；命中 `PENDING` 保留待审核引用；命中 `DISABLED` 也保留引用并显示“已下架”，但不得自动恢复上架，也不得另建同名 `PENDING`。只有系统库中确实不存在该名称时才创建新的 `PENDING`；归并目标缺失、非系统食材或不再为 `ACTIVE` 时不得继续导入。

导入草稿一旦已有真实 `ingredientId`，食材名称和分类都以该系统食材为权威：后台分类控件只读，保存时服务端按引用 ID 批量重写当前系统名称与分类；该 ID 若已是 `MERGED`，必须先解析并保存其 `ACTIVE` 主食材身份。待审核食材通过、归并或拒绝后，所有未发布导入草稿的引用、名称和分类必须一起刷新，不能留下旧 `categoryCode`。

即使 JSON 没有提供可识别的单位，真实食材名称也必须先落为 `PENDING`，默认单位保持 `null`，含义固定为“待管理员补充”，不得猜测默认单位或创建占位单位。管理员审核通过时必须补齐可选分类和系统默认单位；数据库保证 `ACTIVE` 系统食材的默认单位非空。

后台统一使用“待审核食材”作为入口名称，同时展示 JSON 导入生成的系统待审核食材和用户推荐产生的待审核记录；不再使用“待审核个人食材”作为总入口名称。

名称与别名重复治理规则：

1. 名称匹配统一使用同一标准化口径：去除首尾空白、统一大小写、移除内部空白；不使用模糊相似度或自动猜测同义词。
2. 同一份 JSON 内，正式名称和别名标准化后不得重复；正式名称不能出现在自己的别名中。发现重复时阻止该导入条目继续审核。
3. 导入、后台新建、编辑、用户推荐和归并都必须同时检查正式名称与别名，不能只检查 `name`。
4. 一个导入名称或别名只命中一个最终系统食材时，复用该食材身份；命中多个不同最终食材时，标记为匹配冲突并人工确认，不自动创建或合并。
5. 没有命中时才创建 `PENDING` 系统食材；创建、审核、修正和归并写入前必须再次检查名称与别名，遇到并发冲突时停止本次写入并重新读取处理结果。
6. `MERGED` 来源名称和别名继续作为历史搜索入口，搜索结果展示最终 `ACTIVE` 主食材；来源原 ID 保留为归并记录，不能因为来源 ID 仍存在而再次创建同名食材。

## 二、食材选择器

食材选择器包含：

1. 搜索框。
2. `全部食材 / 我的` 来源切换。
3. 左侧系统分类。
4. 右侧三列文字宫格。

搜索同时覆盖系统食材和本人食材，但结果必须保留来源识别。选择器不因分类过多变成长页面列表。

选择器补充规则：

1. 默认进入 `全部食材`，显示系统食材和本人仍可用的个人食材；排序固定为系统食材在前、个人食材在后。
2. `我的` 只显示本人仍可直接使用的个人食材；已通过并转成系统食材后，不再出现在 `我的`。
3. 个人食材条目提供 `编辑` 和 `推荐` 明确操作；推荐确认弹窗标题保持 `推荐入系统库`；审核状态不放进选择器弹层。
4. 搜索无结果时允许直接进入“创建个人食材”，创建成功后立即回到当前菜谱选择流。
5. 菜谱食材行一旦绑定真实 `ingredientId`，名称只读；更换食材必须重新打开选择器，并整体替换食材身份、当前分类和默认单位，不能直接改名后重新匹配或隐式创建另一条食材。
6. 选择不同 `ingredientId` 时，原精确数量立即清空并切换到新食材默认单位；重新选择同一食材时保留当前数量和单位。

## 三、新建我的食材

用户找不到需要的食材时，可以新建个人食材。

个人食材必填：

1. 名称。
2. 默认单位。
3. 一个系统分类。

新建后立即在本人食材库可用，不需要等待审核。个人食材不会因加入饭搭子而共享给其他成员。

用户通过明确操作推荐入系统库，不能在创建时默认投稿。后台审核结果包括：

1. 新增为系统食材。
2. 合并到已有系统食材。
3. 拒绝。

补充规则：

1. 审核中不允许再编辑该个人食材，但不影响继续用于当前菜谱。
2. 拒绝后恢复可编辑，并允许用户修改名称、分类和默认单位后重新推荐。
3. 后台审核通过时可修改 `名称 + 分类 + 默认单位`。
4. 若系统库已有同名食材，创建个人食材时直接拦截；若推荐时命中启用中的同名系统食材，则直接归并，不再进入待审队列；若只命中已下架同名系统食材，则继续进入后台审核，由后台决定是否恢复复用。
5. 合并后把本人仍可编辑的菜谱草稿引用切到系统食材，不保留一条继续对外可见的重复个人食材；已经发布的固定 `RecipeContentVersion` 保持不变，后续从历史版本生成新的可变数据时再解析到当前主食材。
6. 推荐审核结果统一收口到“通知中心 -> 推荐审核”查看。

## 四、计量单位

系统单位当前只保留：`克 / 千克 / 毫升 / 升 / 个 / 瓣 / 汤匙 / 包 / 盒 / 瓶 / 罐`。

规则：

1. 有更通用、更标准的单位时，不保留近义或重复单位。
2. 重量优先使用 `克 / 千克`，容量优先使用 `毫升 / 升`。
3. 个体默认优先使用 `个`，只有像 `大蒜` 这样明显更自然的场景才保留 `瓣`。
4. 包装单位只保留 `包 / 盒 / 瓶 / 罐`，`袋` 并入 `包`。
5. `汤匙` 只作为少数调味液体的系统单位保留，不扩展成全品类通用单位。
6. 系统真实类型只保留 `重量 / 体积 / 常用 / 包装` 四类，对应 `WEIGHT / VOLUME / COMMON / PACKAGE`。

前台不再直接创建个人单位：

1. 用户只提交“单位建议”，通过后台审核后进入系统单位。
2. 后台审核结果包括：新增为系统单位、归并到现有系统单位、拒绝。
3. 后台审核通过前可调整 `名称 + 类型`，拒绝时可填写简短说明。
4. 菜谱编辑里的单位选择优先使用系统单位；另提供唯一的模糊用量“适量”，但它不属于系统单位。
5. 历史个人单位数据暂不作为前台常规创建入口继续开放。

菜谱正文允许互斥保存精确用量 `{ kind: "EXACT", quantity, unitId }` 或模糊用量 `{ kind: "FUZZY", text: "适量" }`。只保留“适量”；历史“少许 / 按需”在读取或来源转换时统一归一为“适量”。“适量”只允许用于当前系统分类代码为 `SEASONING` 的食材；命中真实食材后必须以该食材当前分类为准，不信任草稿或导入文件自填分类。

## 五、菜谱和购物用量

1. 菜谱食材用量优先使用精确数量加单位；只有当前 `categoryCode = SEASONING` 且确实难以准确计量时可使用“适量”，其他分类必须填写精确数量和单位。
2. 基准人数变化只调整精确数量。
3. 多道菜进入计划、饭局或购物清单时，只合并相同食材且单位一致的精确数量。
4. “适量”保持逐项提示，不自动换算或求和为虚假的精确值。
5. 旧单位不做历史兼容展示，残留数据按当前系统单位口径统一清理。
6. 已选“适量”后若更换为非 `SEASONING` 食材，立即清空模糊用量并切回空数量的精确用量；原数量不恢复。

## 六、冰箱库存批次

食材列表表达“我的库存里有哪些食材”，同一最终有效食材身份只出现一次；别名仍命中同一个 `ingredientId`，后台明确归并的食材按现有 `MERGED + mergedToId` 解析到主食材，不新增库存专用父子树。

`fridge_items` 的每一行代表一次购买或入库形成的库存批次。详情页展示同一食材的当前批次，新增库存创建新批次，不把新数量覆盖到旧批次。相同系统单位的批次只在读取时汇总，不保存可被页面直接修改的总量副本；没有可靠换算关系时保留分段数量，并在购物清单中进入待确认状态，用户可主动确认够用、保留采购项或暂不处理。

库存生命周期与到期提醒分开：到期只改变提醒和分组，过期但仍有数量的批次仍可使用；扣减至 `0` 的批次才进入历史批次。历史默认收起，15 天只影响前台重点展示，不删除批次。采购完成等入库流程，以及详情页手动精准扣减，统一按食材总量新增或扣减；手动精准扣减按最早到期批次跨批次分摊，数量不足或单位不可比较时整次失败。做饭完成的低摩擦自动消耗允许按 FEFO 扣除可比较的现有数量，数量不足、数量未知或单位不可比较进入结果摘要，不阻止整顿做饭；“适量”不做虚假精确扣减。购物清单的库存预占仍不等于真实扣减。

历史未绑定 `ingredientId` 的库存不按名称或别名猜测归并，列表以待确认状态保留，旧批次深链只能查看该条记录并引导新增或确认身份。

## 七、食材补库优先级与后续边界

系统食材库优先服务家庭做饭、饮品和小吃的实际录入，不追求一次建立完整的水果或食品百科。首批补库由平台人工整理 `200～300` 个高频食材及常用系统单位，优先覆盖真实菜谱录入和购物合并需求。

食材补库按以下顺序推进：

1. 第一优先级：家庭高频使用的蔬菜、肉禽蛋、水产、豆乳制品、米面杂粮和常用调味料。
2. 第二优先级：日常较常见、且能稳定用于做饭、饮品、小吃或烘焙的水果、干果和果脯。
3. 第三优先级：低频、地域性、季节性或特殊用途食材。它们可以进入系统库，但不应挤占首批高频食材的补充名额；山竹、鳄梨、菠萝蜜属于此类示例，具体仍以实际菜谱和使用频率复核。

补库排序的判断权重固定为：家庭使用频率和菜谱覆盖优先，多用途场景其次，营养数据、分类和单位是否完整作为入库准备条件。能做饮品或小吃只能提高同一优先级内的排序，不能让低频食材越过高频基础食材。

水果、干果和果脯仍按食材本身归入现有分类，不新增“饮品食材”或“小吃食材”分类；具体用途由菜谱中的使用关系表达。营养库是营养关联的数据来源，不是首批食材清单，不得按营养库内容全量导入。

以下内容本轮不冻结：

1. 完整初始食材清单。
2. 系统食材名称和别名之外的完整通用同义词词典范围。
3. 单位建议审核通过后的扩容边界。
4. API、DTO、索引和后台后续批量治理能力。

进入实现前必须依据 `api-database-rules.md` 单独完成契约、约束、成本和迁移评审。
