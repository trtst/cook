# 食材与计量单位规则

## 文档定位

本文是系统食材库、个人食材、计量单位、审核入库和菜谱用量表达的当前产品权威文档。本文只确认产品行为和数据语义，不冻结 API、DTO、表、索引、换算精度或迁移。

## 一、统一食材库

系统只建立一套统一食材库，不分别建立蔬菜库、佐料库或调味品库。食材通过系统分类组织。

首版系统分类：

1. 蔬菜。
2. 肉禽蛋。
3. 水产海鲜。
4. 豆制品。
5. 乳制品。
6. 水果。
7. 主食干货。
8. 调味酱料。
9. 甜点饮品。
10. 冷冻食品。
11. 零食速食。
12. 其他。

“原料、配料、调料”不是食材自身属性。如产品需要区分，应由具体菜谱中的食材关系表达，不能把同一食材复制成多个系统食材。

系统食材和个人食材都不配置单项图片，只保留分类图标。这样可以降低初始数据与图片治理成本，并避免用户误以为图片决定食材身份。

## 二、食材选择器

食材选择器包含：

1. 搜索框。
2. `全部 / 系统食材 / 我的食材` 来源切换。
3. 左侧系统分类。
4. 右侧三列文字宫格。

搜索同时覆盖系统食材和本人食材，但结果必须保留来源识别。选择器不因分类过多变成长页面列表。

## 三、新建我的食材

用户找不到需要的食材时，可以新建个人食材。

个人食材必填：

1. 名称。
2. 默认单位。
3. 一个系统分类。

新建后立即在本人食材库可用，不需要等待审核。个人食材不会因加入饭搭子而共享给其他成员。

用户通过明确操作推荐入系统库，不能在创建时默认投稿。后台审核结果包括：

1. 新增为系统食材。
2. 合并到已有系统食材。
3. 拒绝。

拒绝不影响个人继续使用。合并后必须保留已有菜谱和个人记录的可读性，具体迁移和别名策略在进入 API 与数据库设计前确认。

## 四、计量单位

系统单位按语义区分重量、容量、数量、容器和包装等类型。只有产品确认存在稳定关系的单位才允许换算，不能因为名称相似就自动换算。

用户可以新建个人单位并立即使用：

1. 相同个人单位的精确数量可以相加。
2. 审核或换算关系确认前，不允许个人单位与其他单位跨单位换算。
3. 个人单位可通过明确操作推荐入系统库，审核不影响本人继续使用。

`适量 / 少许 / 按需` 是模糊用量，不是计量单位，不参与数学换算。

## 五、菜谱和购物换算

1. 菜谱食材用量可以是精确数量加单位，也可以是模糊用量。
2. 基准人数变化只换算精确数量。
3. 多道菜进入计划、饭局或购物清单时，只合并相同食材且单位相同，或存在已确认换算关系的精确数量。
4. 模糊用量保持逐项提示，不自动求和为虚假的精确值。
5. 任何自动换算都必须保留用户可理解的原始用量事实。

## 六、初始数据与后续边界

首版建议由平台人工整理 `200～300` 个高频食材及常用系统单位，优先覆盖真实菜谱录入和购物合并需求。

以下内容本轮不冻结：

1. 完整初始食材清单。
2. 单位换算精度和舍入规则。
3. 名称、别名和同义词的唯一性范围。
4. 个人食材合并后的历史数据迁移方式。
5. API、DTO、表、索引、审核队列和后台页面。

进入实现前必须依据 `api-database-rules.md` 单独完成契约、约束、成本和迁移评审。
