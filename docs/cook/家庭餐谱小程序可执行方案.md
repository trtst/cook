# 家庭餐谱小程序可执行方案

> **历史状态（2026-07-20）**：本文保留早期完整产品讨论，不再是当前饭搭子生命周期、会员、空间和 V1 范围的实现权威。文中的“创建 1、加入 3、餐厅切换、免费 4 人、共享 Plus、饭票、OCR/AI”等规则已被 `../dining-group.md`、`../configuration.md` 和 `../plans/dining-group-lifecycle-plan.md` 替代。不得直接按本文修改当前 API、Schema 或客户端。

> 暂定产品名：**下一餐**  
> 产品定义：一家人共同决定下一顿吃什么，管理冰箱与购物清单，并在系统推荐广场发现可导入菜谱、分享自家餐食记忆的轻量小程序。  
> 核心表达：**不是菜谱大全，而是你家的下一餐。**
> 原冻结状态仅表示当时版本；当前实现必须先对照顶层权威文档。

## 一、执行摘要

参考产品以“分类菜谱库”为核心，用户主要浏览、添加和管理菜谱。本产品虽然提供菜谱大厅，但重心仍是把“发现一道菜”转化为“我们下一顿吃什么”，不以内容消费时长为目标。

首版要跑通一个完整闭环：

1. 用户创建自己的餐厅并邀请成员；每人最多创建 1 个餐厅、加入其他 3 个餐厅。
2. 每个人都可以制作和收藏自己的菜谱，也可以从系统推荐中导入菜谱。
3. 主理人或管理员发起“今天想吃什么”的点菜征集。
4. 家庭成员选择菜谱，也可以附一条简短备注。
5. 主理人汇总结果，形成并确认下一餐计划。
6. 系统在首页持续展示下一餐，并在需要时提醒相关成员。
7. 用户也可以随机生成一桌餐食，或把菜谱、餐食计划分享给别人导入。
8. 系统根据餐食计划和餐厅冰箱，计算已有、需确认和需要购买的食材。
9. 缺少的食材一键进入购物清单，用户在超市可以边买边快速勾选。
10. 冰箱里的食材反过来帮助系统推荐“现在能做什么”和“还差一两样就能做什么”。
11. 菜谱大厅 V1 提供系统推荐广场和系统精选菜谱，用户可以一键加入自己的餐厅。
12. 用户公共投稿、优秀推荐、低曝光尝鲜和公共曝光晋级暂不开放，仅保留数据模型和接口骨架，后续再启用。

产品不是聊天工具。所有协作都围绕菜谱、征集和餐食计划发生；备注只能附着在具体事项上，不能脱离事项单独发送。

商业化在 V1 核心闭环稳定后启动：用户级 `个人 Plus` 服务单人效率，餐厅级 `共享 Plus` 服务 2 人及以上的共享协作，饭票可兑换个人权益或抵扣升级共享版。基础用餐闭环、隐私安全和基础数据导出长期免费。

## 二、产品定位与边界

### 2.1 解决的问题

- 家庭每天反复讨论“吃什么”，决策成本高。
- 自家会做、爱吃的菜散落在相册、聊天记录和记忆里。
- 菜谱平台内容很多，但不能代表一个家庭真正会做、愿意吃的菜。
- 家庭成员能提出想法，但通常缺少一个方便汇总并落实为下一餐的工具。
- 去超市前临时回忆要买什么，容易漏买或重复购买。
- 冰箱里已有的食材没有被有效利用，临期食材容易浪费。

### 2.2 核心价值

- **家庭菜谱沉淀**：留下自家真正会做、经常做的菜。
- **共同决策**：成员点菜，主理人快速汇总并确认。
- **下一餐计划**：把“想吃”转化为明确的待做菜单。
- **条件随机**：不是盲抽一道菜，而是按人数、餐次和偏好随机一桌饭。
- **冰箱反向推荐**：根据现有食材找到现在能做或只差少量食材的菜。
- **自动购物清单**：从想做的菜自动计算缺少的食材，购物时快速勾选。
- **菜谱大厅**：V1 先发现系统精选和系统推荐菜谱，并一键加入自己的餐厅；优秀家庭做法后续再加入。
- **家庭口味记忆**：逐步知道谁爱吃什么、最近吃过什么。

### 2.3 明确不做

- V1 不开放用户公共投稿、优秀推荐曝光晋级、关注关系、评论区、私信和用户动态信息流。
- 不做聊天、群聊、语音和表情消息。
- 不做餐食订单、外卖、食材电商和履约闭环；V1.1 的支付只用于会员和明确的数字增值服务。
- 首版不做价格比对、超市导购、收银、采购商城和精细财务记账。
- 冰箱只做家庭食材记录，不做仓储级批次、成本和损耗核算。
- 首版不依赖 AI 才能完成核心流程。

## 三、统一概念

为避免“菜谱、菜单、餐谱、计划”混用，产品内统一使用以下名称：

| 名称 | 定义 | 示例 |
| --- | --- | --- |
| 菜谱 | 一道菜及其做法，可以只有简单记录，也可以包含完整步骤 | 西红柿炒鸡蛋 |
| 菜谱大厅 | V1 的系统推荐广场和系统精选菜谱集合；后续可接入优秀推荐 | 系统精选、现在能做 |
| 公共菜谱 | 预留的后续能力，从私人菜谱生成脱敏、不可变公开版本，不与餐厅内容实时同步 | 后续优秀推荐做法 |
| 餐食计划 | 某个日期、某一餐准备做的一组菜 | 今天晚餐：鸡翅 + 青菜 + 蛋花汤 |
| 点菜征集 | 主理人或管理员向家庭成员发起的选择事项 | 今晚想吃什么？ |
| 餐厅 | 一份共享菜谱、计划、冰箱和购物清单对应的家庭协作空间，不代表商业门店 | 我们家餐厅 |
| 冰箱 | 某个餐厅共享的现有食材记录，包含冷藏、冷冻和常温储物 | 鸡蛋还有、番茄快用完 |
| 购物清单 | 某个餐厅待购买的食材集合，可由菜谱缺口生成，也可手动添加 | 鸡蛋 6 个、番茄 2 个 |
| 家庭动态 | 由征集、推荐、确认等操作产生的事项记录 | 待点菜、计划已确认 |
| 备注 | 附着于菜谱、点菜结果或计划的短文本 | 少辣、18:30 开饭 |

## 四、用户与权限

### 4.1 身份模型

- 每个注册用户都有个人账号空间，可以收藏和草拟菜谱。
- 每个用户最多创建 1 个“我的餐厅”，创建后自动成为主理人。
- 每个用户最多加入其他用户创建的 3 个餐厅，在其中担任管理员或成员。
- “我的餐厅”拥有独立的菜谱库、餐食计划、冰箱和购物清单；加入的餐厅也各自隔离。
- 顶部餐厅切换器展示“我的餐厅 + 已加入餐厅”，所有写操作都必须明确当前餐厅。

### 4.2 餐厅数量与成员上限

- 每个用户最多创建 1 个餐厅。
- 每个用户最多加入其他人的 3 个餐厅，不计算自己创建的餐厅。
- 每个免费餐厅最多 4 人：1 名主理人 + 最多 3 名受邀成员。
- 创建数、加入数和餐厅成员数都做成后台配置，便于后续会员扩容。

餐厅协作状态与付费状态分离：有效成员只有主理人时为 `PERSONAL`，达到 2 人时为 `SHARED`。成员加入或退出后由服务端事务自动重算协作状态，但不会自动购买、取消或退款会员。

- 个人 Plus 用户邀请成员后，个人权益仍只属于该用户；新成员只获得餐厅免费权益。
- 主理人可以主动把自己的个人 Plus 补差升级为该餐厅的共享 Plus，也可以保持个人 Plus 不变。
- 餐厅从多人降回 1 人时，仍在有效期内的共享 Plus 继续服务至到期，不自动降级或退款；续费时引导改用个人 Plus。

## 五、产品结构

底部使用五个一级入口：

1. **首页**：下一餐、待处理事项、快捷操作和家庭动态。
2. **菜谱**：使用“我的餐厅 / 菜谱大厅”页签，承载私人菜谱、系统推荐广场、系统精选、搜索和添加；用户投稿后续开放。
3. **计划**：下一餐、一周安排、历史餐食和计划模板。
4. **清单**：购物清单与餐厅冰箱，支持超市购物模式。
5. **我的**：餐厅成员、口味偏好、通知授权和产品设置；V1.1 增加个人/共享会员、饭票与订单入口。

参考图中的“订单”和“发现”不保留；“厨房”拆分为更明确的首页与菜谱库。

### 5.1 首页优先级

首页首屏按以下顺序展示：

1. 当前餐厅名称、餐厅切换器与家庭动态入口。
2. “下一餐”主区域：日期、餐次、菜品、状态和用餐人数。
3. 四个快捷操作：发起点菜、随机一桌、购物清单、添加菜谱。
4. 冰箱建议：能做什么、临期先吃什么。
5. 待我处理：待点菜、待确认的推荐计划。
6. 最近家庭动态：只展示最近 3 至 5 条。

当还没有下一餐时，主区域直接提供“添加菜品”“发起点菜”“随机一桌”，不展示空白数据页。

### 5.2 低输入交互原则

产品让用户表达意图，不要求用户负责整理数据。所有主要流程遵循：

`系统自动判断 -> 带入默认值 -> 点选调整 -> 搜索选择 -> 手动输入兜底`

- 创建餐厅默认使用用户昵称生成名称，通过微信卡片一键邀请和加入。
- 发起点菜自动带入当前餐次、常用成员、常用截止时间和系统候选菜。
- 成员通过“我想吃”、快捷偏好和“不在家吃”等点选完成表达，备注可选。
- 菜谱优先从系统推荐、分享和相似模板导入，自建菜谱只强制菜名、范围和分类。
- 发布到大厅时自动带入当前菜谱，用户只确认公开字段、来源权利和可选公开昵称；缺少公共最低字段时再点选补全。
- 冰箱默认只点选“有 / 不多 / 用完”，精确数量隐藏为二级入口。
- 购物清单优先由菜谱和计划生成，超市使用整行勾选和常用商品快捷添加。
- 数据尽量从点菜、购物和做饭行为中顺带产生，避免要求用户额外维护。

过敏、严重忌口、食材歧义和不可换算单位不能由系统猜测，必须保留明确确认入口。自动化失败时提供轻量兜底，不能只显示“无法计算”。

## 六、核心功能

### 6.1 餐厅菜谱库

菜谱创建采用“先记下来，再逐步补全”的方式，降低录入成本。

**最低必填**

- 菜名。
- 所属范围：个人草稿或加入指定餐厅。
- 分类：荤菜、素菜、汤羹、主食、早餐、饮品等。

**可选内容**

- 封面图片。
- 适用餐次：早餐、午餐、晚餐。
- 口味、难度、预计时间、适合人数。
- 食材和用量。
- 制作步骤。
- 一句话诀窍或家庭备注。
- 标签：清淡、下饭、孩子爱吃、快手、宴客等。

图片不是必填项。无图片菜谱使用稳定的分类色块和菜名字卡，避免产品再次变成普通图片菜谱墙。

菜谱不填写食材时仍可用于点菜、计划和分享。食材能力按数据完整度三级降级，不能因为数据不完整让整份计划失效：

| 菜谱数据 | 系统能力 |
| --- | --- |
| 有结构化食材、数量和单位 | 按人数换算需求，计算数量缺口并生成清单 |
| 有结构化食材但没有精确数量 | 判断食材“已有 / 需确认 / 缺少”，数量由用户确认 |
| 没有食材记录 | 匹配系统参考模板，或让用户点选主要食材、手动快速加清单 |

无食材菜谱点击“看看缺什么”时，系统按以下顺序处理：

1. 精确匹配餐厅或系统同名菜谱。
2. 通过确认过的菜名别名匹配，例如“番茄炒蛋”和“西红柿炒鸡蛋”。
3. 展示相似系统菜谱的“参考食材，尚未验证”，由用户勾选确认。
4. 匹配不到时展示常用食材快捷点选和手动快速添加。

V1 不从全网抓取食材组合，也不根据任意菜名自由编造食材。参考食材不自动进入购物清单，过敏和忌口食材必须由用户明确确认。

一份计划中只有部分菜谱具备食材时，系统照常计算可计算部分，并明确显示“已计算 2/3 道菜”；未计算菜品提供补全模板或手动清单入口。

用户保存自建菜谱时执行餐厅内三级重复提示：

- 内容版本完全一致：提示“这道菜已经存在”，默认查看已有版本，不重复创建。
- 属于同一个菜品概念但做法不同：提示“餐厅已有同名菜”，允许保存为另一种做法。
- 主要食材和烹饪方式相似：提示“可能已有类似菜”，允许继续创建，不自动合并。

精确重复可以阻止，相似内容只能提示。私人菜谱的相似指纹只在当前餐厅内使用，不能用于发现其他餐厅的私人做法。

**菜谱操作**

- 加入下一餐。
- 发给家庭成员。
- 发起点菜。
- 分享给微信用户。
- 查看冰箱是否够用。
- 将缺少食材加入购物清单。
- 使用系统模板补全主要食材。
- 复制或导入到指定餐厅。
- 推荐到菜谱大厅。
- 编辑、归类、停用。

### 6.2 下一餐与餐食计划

一份餐食计划包含：

- 日期和餐次。
- 用餐人数及参与成员。
- 菜品列表，可包含临时菜名。
- 主食、汤饮等可选分组。
- 计划备注，例如“少辣”“18:30 开饭”。
- 创建人、可选掌勺人和状态。

计划状态统一为：

`草稿 -> 征集中 -> 已确认 -> 准备中 -> 已完成`

另有“已跳过”和“已取消”两个结束状态。V1 界面可弱化“准备中”，但数据层保留，方便未来增加备菜清单。

计划详情支持：

- 增删菜品、调整人数和时间。
- 锁定某道菜，继续随机替换其他菜。
- 推荐给指定家庭成员。
- 主理人指定掌勺人，或成员点击“我来做”；同一计划同时只有一位有效掌勺人。
- 另存为计划模板。
- 完成后记录“喜欢、一般、下次不做”及一句备注。
- 完成后可点选氛围标签，并选填一条不超过 50 字的家庭金句；文字完全可选，不作为完成计划的前置条件。
- 完成后生成非强制的“饭搭子合影卡”，也可稍后从历史计划重新生成。

### 6.3 今日点菜

成员侧统一使用一个“我想吃”入口，不要求成员理解“参与征集”和“主动推荐”的区别：

- 当前餐次存在进行中的点菜征集时，“我想吃”提交到该征集。
- 没有进行中的征集时，所选菜品进入主理人的“想吃池”，并标记期望餐次和提交人。
- 成员组合了多道菜时，可以作为计划建议发送给主理人或指定成员，但仍从“我想吃”进入。
- 主理人和管理员保留“发起点菜”入口，用于设置参与人、候选菜和截止时间。

主理人或管理员发起征集时设置：

- 哪一天、哪一餐。
- 参与成员。
- 候选菜，可手选，也可由系统根据家庭菜谱推荐。
- 每人最多选择几道菜，默认 3 道。
- 截止时间。
- 一条不超过 50 字的备注。

成员收到后可以：

- 从候选菜中勾选。
- 从家庭菜谱补充推荐一道菜。
- 选择“随机吧”。
- 选择“这餐不在家吃”。
- 附一条不超过 50 字的备注，如“少辣”或“想吃点清淡的”。

主理人看到成员选择、票数和备注汇总。系统可以给出“建议菜单”，但最终由主理人或管理员确认，不自动按多数票直接生成结果。

“我想吃”只创建意向或更新当前成员自己的征集回应，不能直接修改已确认计划。主理人采纳后，意向状态变为“已加入计划”；未采纳意向可以保留到下一餐或由提交人撤回。

### 6.4 随机吃什么

随机功能采用“摇骰子”的表现形式，但结果必须受条件约束。

**两种模式**

- 随机一道菜：快速解决“加什么菜”。
- 随机一桌饭：直接生成早餐、午餐或晚餐计划。

**筛选条件**

- 早餐、午餐或晚餐。
- 用餐人数。
- 可用时间：15 分钟、30 分钟、60 分钟以上。
- 是否需要汤、主食和饮品。
- 清淡、少辣等口味。
- 排除过敏、忌口和明确不喜欢的食材。
- 尽量避开最近 3 至 7 天吃过的菜。
- 可选择“优先使用冰箱现有食材”。

**默认组桌建议**

| 人数 | 午餐/晚餐建议 |
| --- | --- |
| 1 人 | 1 道主菜或一份主食套餐 |
| 2 人 | 1 荤 + 1 素，可选汤 |
| 3 至 4 人 | 1 至 2 荤 + 1 至 2 素 + 可选汤 |
| 5 人以上 | 2 荤 + 2 素 + 1 汤，并按人数追加 |

组桌数量和荤素汤槽位是软性推荐，不是必须补齐的条件。算法规则分为：

- 硬规则：过敏、忌口、明确排除和停用菜谱，任何情况下都不能突破。
- 软规则：菜品数量、荤素搭配、是否有汤、近期重复和偏好排序，候选不足时允许降级。

生成时避免主食材重复，并优先使用家庭高频喜欢、近期未吃的菜；开启“优先使用冰箱食材”后，再提高高可信现有食材的覆盖权重。只能生成两道合适菜品时，直接展示“现有菜谱适合做 2 道”，不能为了补齐槽位反复重摇或虚构菜谱。用户可以锁定满意的菜，只重摇其余位置。结果页提供“加入下一餐”“看看缺什么”和“发起征集”三个动作。

家庭菜谱标签不足时，系统应明确显示“按现有菜谱随机”，不能虚构菜谱或强行满足所有搭配规则。

当当前餐厅通过硬规则过滤后的可用菜谱少于配置阈值时，进入冷启动模式：返回所有符合硬规则的餐厅菜谱，并在结果下方推荐可一键加入的大厅菜谱。过敏、忌口等硬规则仍不能跳过，大厅推荐也不能未经用户确认自动加入餐厅。

### 6.5 计划建议与采纳

成员通过“我想吃”组合多道菜后，可以把一份餐食计划建议发送给指定成员。它不是独立聊天入口，而是一张待处理事项卡。

示例：

> 妈妈推荐了“明天午餐计划”给你  
> 备注：这几个菜冰箱里刚好都有

接收人可以：

- 加入下一餐。
- 调整后加入。
- 加入本周计划。
- 收藏为计划模板。
- 暂不采用。

同一推荐只能被采纳一次；采纳后原事项显示“已加入明天午餐”，不产生来回对话。

### 6.6 分享与导入

支持两类跨用户分享：

**分享菜谱**

- 通过微信小程序卡片分享。
- 接收人先查看预览，再选择“加入我的菜谱”。
- 导入后形成独立餐厅入口并固定引用分享快照版本；接收人修改食材或步骤时写时复制，不与来源实时同步。
- 保留“来自某某的分享”来源信息，但允许用户隐藏来源展示。

**分享餐食计划**

- 接收人可以导入为计划草稿、加入下一餐或收藏为模板。
- 导入计划时，可同时导入其中尚未拥有的菜谱。
- 同一分享链接重复打开时提示“已导入”，避免重复创建。

分享链接使用有有效期的分享标识，不直接暴露用户、家庭或菜谱数据库主键。

**饭搭子合影卡**

餐食计划标记“已完成”后，完成页提供“生成饭搭子卡”，不强制弹窗；历史餐食也可以重新生成。卡片自动读取菜品、日期、餐次、可选掌勺人和经分享人确认的参与成员头像，餐桌照片可选。

- 有照片时使用真实餐桌照片。
- 无照片时使用菜谱图片拼图；菜谱也无图时使用稳定的菜名字卡。
- 卡片文案只基于真实字段生成；未记录实际用时，不能出现“用了 XX 分钟”。
- 动态文案按真实照片、菜品数量、掌勺人等条件选择，不编造评价和完成数据。
- 家庭金句只有在分享人明确确认公开后才进入卡片；公共展示前执行文字安全检查。
- 默认不展示冰箱、忌口、过敏、计划备注和成员身份等隐私内容。

分享时生成不可变的只读快照。`shareToken` 绑定该快照而不是可继续变化的计划；接收人无需先完成资料授权即可查看预览，在收藏菜谱、导入计划或创建餐厅时再建立业务身份。分享标识有有效期、可撤销且不暴露内部主键。

接收人可以查看这顿饭、收藏单道菜或导入整份计划。饭搭子卡列为 V1-P1，承担传播闭环，但照片处理和多模板系统不作为 V1 前置条件。

### 6.7 家庭动态与轻备注

产品内不设置聊天列表。家庭动态是结构化事项流，包括：

- 待参与的点菜征集。
- 待处理的计划推荐。
- 下一餐已确认或发生调整。
- 某成员向家庭菜谱库添加了菜谱。
- 征集即将截止或已经结束。

每条动态必须关联菜谱、征集或餐食计划，并包含发起人、目标人、时间、状态和可选备注。备注不超过 50 字，不能单独发送，不能回复形成会话。

动态状态为：`待处理 / 已处理 / 已过期`。不提供正在输入、消息撤回、表情、语音、连续已读回执等聊天能力。

微信订阅消息只作为补充提醒，用于“待点菜”“计划已确认”“临近开饭”等高价值事件，并遵守用户主动授权规则；应用内家庭动态才是完整记录。

订阅授权不在首次进入时强弹，只在用户能理解价值的动作后请求：主理人第一次发布征集时订阅回应结果，成员首次加入或完成点菜时订阅计划确认。成员必须为自己授权，主理人不能替其他成员授权。拒绝后保留“提醒家人”分享卡片和应用内红点，V1 不使用服务号或短信自动兜底。

### 6.8 家庭口味记忆

V1 先采集基础数据，V1.1 再增强推荐：

- 成员主动设置忌口、过敏和偏好。
- 记录成员点过哪些菜。
- 记录计划完成时间，帮助随机时避免短期重复。
- 完成一餐后用“喜欢、一般、下次不做”快速反馈。
- 统计“本家常吃”“孩子爱吃”“很久没吃”等家庭标签。

过敏和忌口是硬性排除；喜欢程度只影响排序，不能覆盖安全限制。

### 6.9 菜谱大厅与系统推荐

菜谱大厅 V1 只承载平台整理的系统菜谱和系统推荐广场。大厅负责发现、收藏、导入和分享，不提供用户公共投稿、关注、评论、私信和公开家庭动态。

“菜谱”一级页顶部使用：

- “我的餐厅”：当前餐厅的私人菜谱和收藏入口。
- “菜谱大厅”：系统精选、系统推荐广场、分类搜索、冰箱能做和已拥有状态。

系统菜谱必须有结构化食材、用量、份数、步骤、餐次、用时和主要食材标签，才能参与冰箱匹配和缺货计算。无图片时使用统一菜名字卡。

推荐入口包括：

- 今日推荐：结合餐次、季节和家庭偏好。
- 现在能做：主要食材均为高可信现有状态。
- 确认一下就能做：存在中低可信食材记录，需要一次点选确认。
- 还差一点：已经明确缺少 1 至 2 种主要食材。
- 临期先吃：优先消耗即将过期的食材。
- 快手菜：按 15、30、60 分钟筛选。
- 最近没吃：避开近期重复。
- 后续优秀推荐：预留入口，不在 V1 展示。

大厅按菜品概念聚合结果，不能平铺大量同名菜谱。搜索“番茄炒蛋”时，优先展示当前餐厅已有做法，其次展示系统精选和系统推荐。随机一桌中，同一个菜品概念最多出现一次。

用户点击“加入我的餐厅”后，餐厅入口固定引用具体系统内容版本，不完整复制系统食材和步骤；用户修改食材或步骤时才写时复制为家庭修订。系统来源后续更新不覆盖餐厅已采用版本。

用户浏览加入的其他餐厅时，只能按当前权限将系统菜谱加入该餐厅；按钮必须明确显示目标餐厅名称，避免加错空间。

### 6.10 餐厅冰箱

每个餐厅拥有一份成员共享的冰箱记录，覆盖冷藏、冷冻和常温储物。所有成员都可添加或更新食材，修改会记录操作人和时间。

为了降低维护成本，冰箱主界面默认只提供三态点选：

- `有`
- `不多`
- `用完`

数量、单位、购买日期、保质期和存放位置隐藏在“编辑数量”二级入口中，不在日常更新时强制填写。购物清单中已有明确购买数量时，结束购物可直接带入冰箱，只在数量缺失或单位不明确时请用户确认。

每项食材至少包含标准食材、状态和更新时间；数量、单位和保质期均可选。系统不再用统一“7 天未确认”，而是计算库存可信度：

- `confidenceDays`：按食材分类配置的可信周期，表示多久未确认后开始降级。
- `expireAt`：用户明确录入的保质期，是独立的确定日期，优先于系统周期。
- 可信周期保存在服务端配置中，不写死在小程序前端；V1 可以先用少量分类档位，不要求完整运营后台。

库存可信度分为高、中、低，并随最后确认时间、食材分类、购物入库和做饭后更新动态变化。界面同时使用状态图标和文字，不能只靠颜色表达。

**快速录入方式**

- 搜索食材后点选添加。
- 从已购购物清单批量选择“加入冰箱”。
- 使用最近添加和常用食材快捷入口。
- 支持一次粘贴多行食材，逐条确认后保存。

用户不需要定期逐项巡检冰箱，只在相关使用场景顺带确认：

- 推荐菜谱依赖中低可信食材时，直接点选“还有 / 不多 / 用完”。
- 购物结束时，从已购物品一键更新冰箱。
- 一餐完成时，只询问本餐使用过的主要食材。
- 首页最多提示 3 项可能过期或需要确认的生鲜，不展示整页待办。

**能做什么的匹配规则**

- “现在能做”：所有主要食材为高可信“有”，辅料允许缺少。
- “确认一下就能做”：主要食材存在中低可信记录，或状态为“不多”。
- “还差一点”：已经确认缺少 1 至 2 种主要食材。
- “暂时不能做”：缺少超过 2 种主要食材。

“之前买过”只能进入“确认一下”，不能直接视为现有或缺少。用户确认后立即重新计算分类。每个结果都展示匹配依据和缺少项，不能只给一个不透明的匹配百分比。过敏、忌口仍然优先于库存匹配。

完成餐食计划后，系统列出本餐使用过的主要食材，请用户快速更新为“还有、不多、用完”。V1 不强制自动扣减数量，避免用量不准导致库存越来越错误。

### 6.11 购物清单

购物清单是底部一级入口“清单”的默认页面，归属于当前餐厅，餐厅成员共享。

V1 每个餐厅只保留一份进行中的购物清单，完成后归档到历史；再次添加商品时自动创建新的进行中清单，避免用户先理解“该选哪一张清单”。

**清单来源**

- 手动快速添加食材或生活用品。
- 从单个菜谱的缺少食材生成。
- 从下一餐或一周计划合并生成。
- 从冰箱中的“不多”或临期替换需求生成。

**从菜谱生成清单**

1. 用户在菜谱或计划中点击“看看缺什么”。
2. 系统按实际用餐人数换算食材需求。
3. 与当前餐厅冰箱对比，分成“已有”“需确认”“需要购买”。
4. 用户确认不确定项，一键把需要购买的食材加入清单。
5. 同名、同单位食材自动合并并标注来源菜谱；无法换算的单位保持独立并提醒确认。

**超市购物模式**

- 未购买项目固定在上方，已购买项目在稳定时机统一移动到底部并折叠。
- 每行使用大尺寸复选框，点击整行即可标记，适合单手操作。
- 展示名称、数量、单位和来源；备注保持单行，不挤压主信息。
- 按蔬菜、肉蛋、水产、粮油、调味、日用品等区域分组，减少来回找货。
- 用户可以调整分类分组顺序，顺序按“用户 + 餐厅”保存，不改变其他成员的购物路线；V1 不做共享商品级自由排序。
- 底部常驻“快速添加”，输入菜名后即可加入，不需要打开复杂表单。
- 支持撤销刚才的勾选，避免误触。
- 多名成员同时购物时同步勾选状态，并展示最后操作人。
- 勾选时先在本机立即反馈，再后台同步；弱网失败显示待同步状态并自动重试。
- 操作写入持久化本地队列，小程序关闭后仍可重试；重新进入时先与服务端状态对账。
- 远端成员的操作先在原位置更新状态，不在用户正要点击时突然重排列表；用户停止操作或主动刷新后再统一下沉已购项。

采购完成后提供“结束购物”：已购买食材可批量选择加入冰箱，购物清单已有的数量直接带入，仅对缺失或歧义数量进行可选确认。系统不自动把全部已购商品写入冰箱，避免把即刻使用的食材或生活用品错误计入库存。

未购买项目不能直接进入冰箱。结束购物时逐批选择：

- “下次再买”：迁移到下一份进行中购物清单。
- “不需要了”：标记取消，不继续出现。
- “家里已有”：从购物清单移除，并引导一键确认冰箱状态。

迁移操作必须在服务端事务中完成，同一项目只迁移一次，不能因重复点击或多人同时结束购物生成多份清单项。

**清单状态**

`待购买 / 已购买 / 下次再买 / 不需要 / 家里已有`

一项清单可关联多个菜谱或计划来源。删除计划时只解除来源关系，不应误删用户手动添加或被其他计划共同需要的清单项。

### 6.12 后续优秀推荐预留

V1 不开放用户把菜谱推荐到公共大厅，不展示“推荐到大厅”“我的投稿”“最新尝鲜”等入口。

后续如果开放优秀推荐，仍使用公共菜谱的预留模型：从有发布权的餐厅版本生成脱敏、不可变公共版本，不能实时读取私人菜谱。默认移除家庭备注、成员信息、冰箱、过敏和餐食计划数据。餐厅后续修改不影响已公开版本；更新公共内容时创建候选版本，重新完成安全检查。

**状态与曝光分离**

| 维度 | 状态 |
| --- | --- |
| publicationStatus | `draft / published / hidden / deleted` |
| safetyStatus | `pending / passed / review_required / rejected` |
| exposureLevel | `none / low / normal / hot` |

只有 `publicationStatus=published` 且 `safetyStatus=passed` 时，曝光等级才能是 `low / normal / hot`。`pending、review_required、rejected、hidden、deleted` 的曝光必须为 `none`，该约束由服务端和数据库共同保证，不能依赖前端隐藏。

**后续安全检查时序**

1. 同步校验最低完整度、发布频率和基础格式。
2. 创建候选公共版本，设置 `safetyStatus=pending、exposureLevel=none`。
3. 异步检查全部公开文字、图片、图片文字、广告和明显非菜谱内容。
4. 检查通过后原子切换为 `passed + low`；疑似风险或超时进入 `review_required + none`；明确违规进入 `rejected + none`。

机器检查未完成前不能进入任何公共列表。内容安全接口的具体能力、限制和费用在启用前按当期平台官方文档确认，产品方案不绑定某个接口名称或“免费”假设。

**公开版本更新**

- 当前公开版本继续服务，作者修改时创建唯一候选版本。
- 候选版本检查通过后，原子切换为当前版本并从低曝光重新积累。
- 候选版本被拒绝时，旧公开版本继续展示，作者收到原因。
- 已导入餐厅继续固定使用旧版本，不受公共版本更新影响。

**曝光晋级**

- `low`：出现在最新尝鲜和作者分享链接中，推荐权重低。
- `normal`：被多个合格餐厅采用并保留后，进入搜索、分类和个性推荐。
- `hot`：在 normal 基础上出现真实计划确认或完成、保留率稳定且举报率低，进入大厅首页和热门专题。

合格采用按餐厅去重；发布者自己的餐厅不计，同一操作人在多个已加入餐厅重复添加只作为风险信号，短时间删除不计。IP 和设备只能作为风控信号，不能直接否决家庭共享网络中的正常操作。用户侧不展示精确晋级阈值，只提示“被更多家庭真实采用后，有机会进入推荐”。

**举报与处置**

举报、隐藏、恢复、限流和操作审计是后续公共投稿上线前必须补齐的能力：

- 严重违规举报触发机器复检和临时降曝光；复检失败立即隐藏。
- 多个独立高可信举报一致时临时隐藏并进入人工队列。
- 广告、图文不符、质量较低等按唯一举报人数、举报率和内容曝光量降权。
- 单个普通举报不能无条件下架，举报人高频异常时限流并降低权重。
- 运营必须能查看原因、一键隐藏、恢复、限制发布并保留审计记录。
- 作者收到下架原因，并至少拥有客服或反馈式申诉入口。

普通作者下架只停止大厅展示，不删除其他餐厅此前合法采用的固定版本；严重违法、侵权或隐私清除另走平台强制处理流程。

    B --> C["系统汇总选择与偏好"]

    E --> F["对比餐厅冰箱"]

### 7.1 新餐厅首次使用

1. 微信登录后创建“我的餐厅”。
2. 设置餐厅名称，系统校验该账号尚未创建其他餐厅。
3. 通过微信卡片邀请最多 3 位成员。
4. 从系统推荐加入 3 至 5 道常吃菜，也可以自己创建菜谱。
5. 可跳过或快速登记几项冰箱食材。
6. 发起第一次“今晚吃什么”。
7. 成员选择后，主理人确认下一餐并查看缺少食材。

首次引导不要要求用户完整填写家庭资料或一次录入很多菜谱。首个成功目标是完成一份下一餐计划。

### 7.2 主理人征集下一餐

1. 首页点击“发起点菜”。
2. 选择今天晚餐、参与成员和截止时间。
3. 选择候选菜或让系统推荐。
4. 填写可选备注并发布。
5. 成员在待处理卡片中完成选择。
6. 主理人查看汇总，点击“生成建议菜单”。
7. 调整后确认，计划进入首页“下一餐”。

### 7.3 成员提交“我想吃”

1. 成员从首页统一进入“我想吃”。
2. 有进行中征集时，直接勾选候选菜或补充一道菜，更新自己的征集回应。
3. 没有征集时，选择一道或多道菜，提交到主理人的“想吃池”。
4. 组合多道菜时，可选择发送给主理人或指定成员作为计划建议。
5. 接收人采纳后，事项显示“已加入某餐计划”；未采纳时保留、撤回或稍后处理，不进入聊天会话。

### 7.4 随机一桌饭

1. 首页点击“随机一桌”。
2. 选择餐次、人数、时间和口味条件。
3. 摇骰子生成菜单。
4. 锁定满意的菜，重摇其他菜。
5. 直接加入下一餐，或发起家庭点菜确认。

### 7.5 从冰箱找能做的菜

1. 用户进入“清单 -> 我的冰箱”。
2. 快速记录现有食材，数量可以留空。
3. 点击“看看能做什么”。
4. 系统按“现在能做、确认一下就能做、还差一点”展示菜谱。
5. 用户选择菜谱并加入下一餐。
6. 对缺少项一键生成购物清单。

### 7.6 想做某道菜并生成采购清单

1. 用户在餐厅菜谱或系统推荐中选择想做的菜。
2. 选择用餐人数，点击“看看缺什么”。
3. 系统换算食材并与当前餐厅冰箱对比。
4. 用户确认“需确认”的项目。
5. 缺少项加入当前餐厅购物清单并合并重复食材。
6. 到超市打开购物模式，边买边勾选。
7. 结束购物后，将选中的已购食材批量加入冰箱。

### 7.7 完成用餐并分享饭搭子卡

1. 主理人、管理员或掌勺人将计划标记为“已完成”。
2. 系统提供“喜欢 / 一般 / 下次不做”的可选反馈，并询问本餐主要食材“还有 / 不多 / 用完”。
3. 完成页非强制展示“生成饭搭子卡”。
4. 系统按真实菜品、参与成员、掌勺人和可选餐桌照片生成不可变分享快照。
5. 分享人确认公开内容后发送；接收人无需先填写资料即可查看只读预览。
6. 接收人在收藏菜谱或导入计划时再建立业务身份，重复导入保持幂等。

### 7.8 从菜谱大厅加入餐厅

1. 用户进入“菜谱 -> 菜谱大厅”，按推荐、分类、冰箱条件或搜索发现菜谱。
2. 同一个菜品概念聚合展示系统版和当前餐厅做法；后续优秀推荐做法不在 V1 展示。
3. 已加入当前餐厅的版本显示“已拥有 · 查看”，不能重复导入。
4. 用户选择具体系统版本和目标餐厅，点击“加入我的餐厅”。
5. 系统创建轻量餐厅入口并固定引用该不可变版本；用户修改内容时再写时复制。
6. 加入下一餐或生成缺口清单时继续使用该固定版本，不受大厅后续更新影响。

### 7.9 后续优秀推荐

V1 不开放用户公共投稿。公共模型、接口骨架和曝光状态机只作为后续优秀推荐的预留能力；客户端不展示提交入口。

| FridgeItem | id、restaurantId、ingredientId、状态、数量、单位、位置、购买日期、expireAt、lastConfirmedAt、更新时间、更新人、version |
| ShoppingList | id、restaurantId、名称、状态、创建人、完成时间、version |
| ShoppingItem | id、listId、ingredientId、展示名称、数量、单位、分类、状态、来源类型、操作人、操作时间、version |
| ShoppingItemSource | shoppingItemId、recipeVersionId 或 planId、需求量、单位 |
| Activity | 类型、关联对象、发起人、目标人、备注、处理状态、时间 |
| ShareSnapshot | id、类型、来源资源 id、不可变公开内容、创建人、创建时间、状态 |
| ShareToken | snapshotId、创建人、有效期、权限、撤销时间、状态 |
| ShareImport | userId、restaurantId、snapshotId、导入资源 id、导入时间，三者组合唯一 |
| RecipeImport | restaurantId、sourceVersionId 或 shareSnapshotId、restaurantRecipeId、导入时间，来源组合唯一 |
| IdempotencyRecord | operationId、userId、操作类型、请求摘要、结果引用、过期时间 |
| AuditEvent | restaurantId、对象类型、对象 id、操作人、前后状态、operationId、服务端时间 |
| RecipeFeedback | planId、recipeVersionId、成员、评价、备注 |

所有修改、删除、确认计划、冰箱、购物清单和成员管理操作都必须在服务端进行餐厅身份与角色校验，不能只依赖小程序前端隐藏按钮。

会员商品必须保存版本化权益快照，历史订单不能随着运营修改当前套餐而变化。`MembershipSubscription.subjectType`区分用户级个人版与餐厅级共享版，`EntitlementGrant`表示最终可执行权益，`UsageQuota`负责有限次数能力；这些事实不能只压缩成 User 或 Restaurant 上一个 `isVip` 布尔值。

权益解析固定遵守“功能取并集、额度分账、资源按归属、权限先于付费、个人权益不外溢”。成员上限、共享空间、共享计划和餐厅统计只读取共享权益；识别、模板和导出等能力默认使用餐厅共享额度，也允许用户主动选择自己的个人额度或饭票。同一操作只能选择一个来源，所有接口共用同一权益服务，不能各自实现一套优先级。

饭票和会员只能购买能力，不能绕过餐厅业务权限。任务执行前和产物落库前都校验当前成员关系与写权限；权限失效时不得写入餐厅，并释放冻结额度或饭票。

持久资源不跨作用域借用。餐厅菜谱图片、餐厅报告以及明确保存到餐厅的生成产物只能记入餐厅 `StorageAllocation`；个人草稿、个人回顾和个人导出文件只能记入用户空间。对象存储物理文件可以按 SHA-256 复用，但产品容量按各作用域的逻辑引用独立计量。

饭票采用双余额钱包和不可变账本。`PointLedger.operationId`、`RewardClaim`业务组合、支付渠道交易号和退款单号分别建立唯一约束。余额更新、账本写入和业务产物创建需要处于同一事务或使用可补偿状态机，不能出现已扣饭票但产物没有业务记录的中间状态。

菜谱数据逻辑上分为“菜品概念、系统模板、餐厅入口、不可变内容版本”四层。系统和公共版本只存一份；餐厅未修改时物理引用具体版本，修改食材、用量或步骤时基于当前版本写时复制。修改本地名称、备注、分类和展示信息不生成内容版本。

编辑内容采用“可变草稿 -> 点击保存 -> 创建一次不可变版本”。保存时携带 `baseVersionId`；如果当前版本已被其他成员更新，服务端拒绝静默覆盖并返回最新版本。不能使用最后提交者直接覆盖的策略。

`contentHash`用于精确重复和版本完整性，必须基于规范化后的食材 ID、数值、标准单位、主要食材标记、步骤顺序和步骤完整内容生成。`similaritySignature`仅使用主要食材集合和标准烹饪方式生成候选提示，不能作为唯一键或自动合并依据。

MealPlanItem、分享快照和公共版本必须通过外键引用具体 `RecipeContentVersion`。餐厅后来修改菜谱时，历史餐食、既有分享和已导入内容均不得变化。

食材搜索可以使用字符串和模糊匹配给出候选，但最终归一必须由用户或已确认别名规则绑定 `ingredientId`。无法可靠匹配的内容保存为餐厅私有食材，不能擅自污染全局概念。数量换算只处理明确兼容的单位；“1 把”和“300 克”这类无法可靠换算的数据交给用户确认。

图片由服务端计算 SHA-256 后物理复用，哈希和存储路径不暴露给客户端。访问时先校验菜谱、公共版本或分享快照权限，再签发短期地址。引用计数只作辅助，物理清理由异步标记回收和定期引用扫描共同完成。

服务端需要建立并发约束：一个用户只能拥有一个有效餐厅；作为非主理人的有效餐厅成员关系最多三条；餐厅有效成员数不能超过事务内重新计算的当前权益上限；一个餐厅同时最多一份进行中购物清单；同一来源版本在同一餐厅只能导入一次；同一公共菜谱同时最多一个候选版本。购物项勾选请求携带操作标识和数据版本，保证弱网重试不重复写入，多人操作冲突时返回最新状态。

## 十、技术实施建议

### 10.1 推荐架构

- 前端：微信小程序。已有跨端技术栈时可使用 uni-app；没有历史包袱时可直接使用微信原生框架。
- 服务端：用户与权限、餐厅、菜谱版本、菜谱大厅、公共发布、计划、征集、冰箱、购物清单、分享和动态 API。
- 数据库：关系型数据库，便于处理成员关系、计划状态与查询统计。
- 文件存储：对象存储保存菜谱图片，服务端按 SHA-256 复用资源并在权限校验后签发短期访问地址。
- 异步任务：公共内容安全检查、图片处理、通知、审计归档和资源回收。
- 身份：微信登录获取可信用户标识，业务层使用内部 userId。
- 提醒：应用内动态为主，微信订阅消息为辅。
- 分享：使用短期 shareToken 访问不可变公开快照，导入固定版本，修改时写时复制。

如果团队暂时没有服务端基础设施，V1 可使用微信云开发/CloudBase 快速启动；若已有账号体系、支付规划或统一后台，则接入现有 API 服务更合适。

### 10.2 服务模块

- 账号与微信登录。
- 餐厅、成员、创建/加入数量限制与角色权限。
- 菜品概念、系统模板、不可变内容版本、餐厅菜谱入口和重复检测。
- 菜谱大厅、公共版本发布、机器安全检查、曝光晋级和采用统计。
- 餐食计划与状态流转。
- 点菜征集与成员回应。
- 条件随机与搭配规则。
- 冰箱三态、库存可信度、临期状态和菜谱匹配。
- 食材需求换算、缺口计算、购物清单合并与实时勾选。
- 家庭动态与订阅提醒。
- 分享、导入与防重复。
- 商业化基础：个人/共享订阅、权益解析、共享额度策略、原子预留、空间计量、饭票账本、会员升级、任务结算、支付退款和渠道对账；V1 只预留，V1.1 启用。
- 运营治理：系统菜谱导入校验、别名治理、review_required 队列、举报、隐藏、恢复和发布限制。
- 配置后台：餐厅创建数、可加入数、成员上限、系统菜谱、分享有效期、曝光阈值、风险阈值、通知模板、会员权益、额度和饭票规则等。

### 10.3 随机算法的首版实现

首版使用可解释的规则引擎，不需要 AI：

1. 按当前餐厅、餐次、人数、用时和忌口筛选候选菜。
2. 先执行过敏、忌口、明确排除和停用菜谱等硬性过滤。
3. 按近期重复、家庭偏好、用时、主要食材重复和荤素汤建议计算软性分数。
4. 开启“优先使用冰箱食材”时，提高高可信现有食材覆盖率高的菜谱权重。
5. 按人数建议菜品数量，从高分候选中加入少量随机权重后抽取。
6. 候选不足时返回最佳可行结果，不强制补齐槽位，也不反复重摇。

算法返回结果时同时返回选择原因，例如“30 分钟内可完成”“冰箱主要食材已齐”“最近 7 天未吃”“孩子常选”，方便后续调试和提升用户信任。

### 10.4 食材缺口计算

1. 按每道菜的结构化等级决定精确换算、仅判断有无或进入参考补全。
2. 有数量时按菜谱基础份数和计划用餐人数换算需求量；无数量时不制造精确结果。
3. 将多道菜的同一标准食材汇总，同时保留来源菜谱和未计算菜品。
4. 读取当前餐厅冰箱状态、库存可信度和可比较数量。
5. 数量足够且高可信归入“已有”；中低可信、状态“不多”或单位不可换算归入“需确认”；确认缺少归入“需要购买”。
6. 用户确认后写入当前活动购物清单，同食材同单位采用幂等合并。

计划只有部分菜谱可计算时仍返回部分结果，并明确展示覆盖数。缺口结果需要保留计算快照；冰箱随后变化时提示重新核对，不应静默改变用户已经确认的购物清单。

### 10.5 多人协作与并发规则

多人协作采用“共享状态、服务端最终确认、客户端即时反馈”的方式，不建设多人同时编辑富文本。所有可变共享对象至少包含 `version、updatedAt、updatedBy`，所有可重试写操作携带唯一 `operationId`。

| 场景 | 服务端规则 | 用户可见结果 |
| --- | --- | --- |
| 两人添加同一购物项 | 按活动清单、ingredientId、兼容单位原子合并，来源关系幂等写入 | 合并为一项，显示多个来源 |
| 两人勾选同一商品 | operationId 去重并检查版本，相同目标状态重复提交直接成功 | 显示“某某刚刚购买” |
| 一人勾选、一人取消 | 服务端按有效版本接受操作并推送最新状态 | 冲突端收到最新状态和操作人 |
| 购物结束与未购项迁移 | 单事务完成归档、迁移和可选入库，同一清单只能结束一次 | 重复点击返回同一完成结果 |
| 冰箱入库或消耗 | 入库使用原子增量；直接修改数量或状态使用版本检查 | 不静默覆盖其他成员刚完成的更新 |
| 成员提交点菜、管理员确认 | 每人每征集一份回应并可覆盖自己的旧回应；确认计划与关闭征集同事务完成 | 截止后提交明确提示未计入 |
| 多管理员修改计划 | 修改携带计划版本；版本过期拒绝覆盖并返回最新计划 | 提示“计划已被某某更新，请重新确认” |
| 多成员编辑同一菜谱 | 保存携带 baseVersionId；当前版本变化后拒绝覆盖，保留用户草稿 | 提示查看最新版本或保存为另一种做法 |
| 多人点击“我来做” | 掌勺人变更检查计划版本，同一时刻只有一位有效掌勺人 | 后到者看到最新掌勺人，可再次申请变更 |
| 多人接受邀请 | 在数据库事务内校验创建数、加入数和餐厅成员上限 | 超限者收到明确原因 |
| 主理人转让与成员变化 | 锁定餐厅、双方用户、订阅和成员关系，校验新主理人自有餐厅及原主理人加入上限 | 全部成功或全部不变，不出现无主餐厅 |
| 重复导入分享 | 按用户、目标餐厅和 snapshotId 建立幂等键 | 重复打开显示已导入，不生成副本 |
| 多人抢最后一份共享额度 | 按 operationId 原子冻结整次所需额度，只有一人成功；任务成功结算、失败释放 | 失败者选择个人额度或饭票，不自动改扣 |
| 多任务占用最后空间 | 任务开始预留预计空间，落库前按实际大小结算；不足时压缩、清理、扩容或失败释放 | 不静默转个人空间，不强行超额写入 |
| 任务期间成员被移除 | 产物落库前再次校验成员与写权限，失效则取消餐厅写入并释放额度/饭票 | 明确提示权限已变化，个人购买力不能绕过权限 |

购物模式、点菜结果和计划详情在页面活跃期间进行实时同步；其他页面在进入前台、切换餐厅或收到家庭动态时刷新。弱网下先在本机显示操作结果，并将 `operationId、对象、目标状态、baseVersion、重试次数` 写入持久化本地队列；失败时标记“待同步”并支持自动/手动重试。重新进入页面先与服务端对账，远端操作不得在用户点击瞬间重排列表。

确认计划、关闭征集、结束购物、批量入库、成员加入/移除等跨对象操作必须使用数据库事务。关键状态变化写入轻量审计记录，至少保留操作人、对象、前后状态、operationId 和服务端时间。

### 10.6 分享快照与访问控制

- 饭搭子卡、菜谱和计划分享均先生成不可变公开快照，再签发有期限的 shareToken。
- 只读预览不依赖完整用户资料；收藏、导入和创建餐厅等写操作需要可信微信身份。
- 分享人可以撤销 token，但撤销不删除接收人已经合法导入的副本。
- 快照创建时执行隐私字段白名单，只写允许公开的菜品、图片、日期、餐次、可选成员和掌勺信息。
- 卡片文案由快照中的真实字段决定，缺失字段直接不展示，不允许补造时间、评价和参与信息。

### 10.7 菜谱版本、去重与导入

菜谱内容统一使用不可变 `RecipeContentVersion`，系统版本、家庭修订和公共快照在业务上分层，在物理版本层统一引用。核心流程：

**导入系统或公共菜谱**

1. 校验当前餐厅是否已经存在相同 `sourceVersionId`。
2. 不存在时创建轻量 `RestaurantRecipe`，`sourceVersionId` 与 `currentVersionId` 都指向来源版本。
3. 不复制来源食材、步骤和图片；本地名称、备注和分类单独保存。
4. 用户修改内容时才创建以当前版本为父级的家庭版本，并原子切换 `currentVersionId`。

**编辑家庭菜谱**

1. 客户端加载 `baseVersionId` 和可变草稿。
2. 修改本地名称、备注和展示信息时只更新餐厅入口元数据。
3. 修改食材、用量、步骤内容或顺序时，保存为新的不可变版本。
4. 保存前检查当前版本是否仍等于 `baseVersionId`；不一致时拒绝覆盖。
5. 系统模板后续发布新版时，V1 不自动升级既有餐厅引用。

**重复判断**

- 相同来源版本或分享快照：数据库唯一约束阻止重复导入。
- `contentHash`完全一致：判定精确重复，默认查看已有版本。
- `dishConceptId`一致但内容不同：允许保存为另一种做法。
- `similaritySignature`一致：仅提示相似，不能自动合并。

`contentHash`使用稳定的规范化序列生成并保存算法版本号，避免算法升级后旧哈希失去可解释性。`similaritySignature`只在当前餐厅和公共系统内容中使用，私人家庭版本不能跨餐厅检索或统计。

相似度数值不作为当前冻结常量。技术评审启动前，产品或内容负责人准备 50 至 100 组标注菜谱对，分别标为“确定同一道、确定不同、不确定”；阈值必须服务端配置，开发阶段使用该测试集评估误报和漏报，产品在联调结束、测试验收开始前确认首发值。无论阈值多少，相似结果只能提示，不能自动合并。

系统菜谱版本升级、家庭版本差异对比、疑似重复整理、归档合并和撤销合并放到 V1.1。合并只改变主列表入口，历史计划仍引用原版本。

### 10.8 后续公共菜谱状态机与曝光

公共菜谱更新采用“当前版本 + 唯一候选版本”：

```text
私人菜谱
  -> 提交候选公共版本
  -> publication=published, safety=pending, exposure=none
  -> 基础安全检查

通过
  -> safety=passed, exposure=low
  -> 合格餐厅采用并保留
  -> exposure=normal
  -> 出现真实计划确认/完成且风险稳定
  -> exposure=hot

疑似风险或超时
  -> safety=review_required, exposure=none

明确违规
  -> safety=rejected, exposure=none
```

作者修改公开内容时，当前公开版本继续展示，候选版本独立检查。候选通过后在事务中切换 `currentPublicVersionId`，新版本从 low 重新积累；候选失败不影响旧版。公共版本的结构化内容和安全状态均不可原地修改。

数据库约束至少保证：

```text
exposureLevel != none
=> publicationStatus = published AND safetyStatus = passed
```

后续低曝光进入正常推荐需要多个合格餐厅添加并保留；进入热门还需要真实计划使用、稳定保留率和低举报率。发布者自己的餐厅、重复餐厅、短时间删除和明显异常关联不计为合格采用。

### 10.9 内容安全、举报与运营兜底

- 发布频率、最低完整度和格式在同步请求中校验。
- 文字、图片、图片文字和明显广告等基础安全检查完成前，公共曝光始终为 none。
- 外部检查使用异步任务、幂等任务标识、重试上限和超时；超时进入 review_required，不带风险公开。
- 每次公共内容版本变化都重新检查，旧版检查结果不能继承给新版。
- 家庭金句、氛围文字和餐桌照片复用同一内容安全服务，但使用独立的分享检查策略，不进入公共菜谱曝光状态机。
- 仅餐厅内部保存的短备注按平台要求进行基础检查；生成分享卡前重新检查实际分享的文字和图片，检查不通过时阻止对应字段进入卡片，不阻止餐食计划完成。
- 举报按唯一举报人、举报率、风险类型、举报者历史和机器复检组合处置，不能仅凭单个普通举报自动下架。
- 严重风险触发机器复检和临时降曝光；复检失败或多个独立高可信信号一致时隐藏并进入人工队列。
- 运营隐藏、恢复、限制发布和强制下架全部写入不可变审计记录。
- 普通删除采用软删除；违法、侵权和隐私清除保留独立强制处理流程。

公共 UGC 上线前必须有最小可用治理后台。它不承担逐条事前审批，但必须能处理 `review_required`、举报、隐藏、恢复、发布限制和作者反馈。

### 10.10 标准食材与别名治理

标准食材库不追求首日覆盖全部地域别名。用户搜索词先用于模糊候选；无法确认时保存为餐厅私有食材并进入 `IngredientAliasCandidate`，不能直接创建全局标准或自动合并。

- 系统菜谱导入工具必须校验 ingredientId、标准单位、主要食材、步骤和基础份数，存在未确认食材时拒绝发布系统版本。
- 高频自定义词按跨计划使用次数进入运营待治理列表，但不展示其来自哪个私人餐厅。
- 运营确认“蕃茄 -> 番茄”等映射后，将原词保存为已确认别名，并在事务中迁移可安全归一的数据。
- 无法确定为同一食材时保持分离，食材合并必须记录 IngredientMergeEvent 并可追溯。
- 全局 DishAlias 和 Ingredient 别名只包含审核确认内容，用户搜索日志和待确认词不公开。

#### 系统菜谱冷启动

系统菜谱数据由产品或内容负责人主责，开发只提供导入模板、校验器和错误报告。每道至少包含菜品概念、标准名称、确认别名、分类、基础份数、餐次、预计用时、难度、标准食材 ID、数值、单位、主食材标记、步骤顺序、标签、文字来源、授权方式和图片权利证明。

首批 100 至 200 道系统菜谱必须 100% 结构化，无待确认食材、非法单位和精确重复，并能追溯文字与图片来源。不能直接复制网络菜谱正文或未经授权图片；内容导入检查失败时必须定位到具体菜谱和字段。

技术评审启动前必须指定到人的内容负责人并确认来源策略。建议交付节点：第 2 周前完成首批 50 道用于接口和搜索测试，第 4 周前完成至少 100 道支持菜谱大厅联调，第 8 周前完成首发 100 至 200 道的结构与授权验收。团队没有专职内容运营时，由产品负责人承担结果责任，可安排外部整理，但授权和最终验收不能外包失控。

### 10.11 上线合规闸门

产品方案可以冻结，但公共 UGC、付费会员和饭票开放前必须完成当期规则核验，不能引用过期经验或在方案中猜测资质结论：

- 根据微信官方最新规则确认小程序类目、UGC 开放、内容安全接口能力、限额和费用。
- 根据实际主体、经营模式和所在地确认微信支付、会员、饭票、退款及可能涉及的额外资质。
- 用户协议、隐私政策、内容授权、侵权投诉、强制下架和数据删除规则需经过法务或合规负责人审核。
- 合规矩阵记录检查项、依据链接、责任人、核验日期、结论、待办和上线阻断级别。

这些工作不阻塞数据库和接口技术设计，但属于公共 UGC 与支付发布的 P0 闸门；未完成时只能保持相关功能关闭。

最晚节点：技术评审启动前确认合规责任人和检查清单；V1 第 4 周公共模块联调前确认类目、UGC 和内容安全能力可行；第 10 周灰度前关闭全部公共 UGC P0；支付、饭票、退款和相关协议必须在 V1.1 第 1 周开发启动前完成确认，不能边开发支付边等待主体资质结论。

### 10.12 V1 到 V1.1 迁移基线

- 历史菜谱、计划、冰箱和购物清单不复制，会员上线后继续引用原业务数据。
- V1 免费调用记录只进入分析数据，不回填为 V1.1 已消耗额度。
- V1 阶段就记录用户级识别/导出需求、餐厅成员分布、逻辑图片占用、计划跨度和成本型能力调用量。
- V1.1 上线前回填用户与餐厅的实际逻辑存储占用，周期额度从上线当天的零用量开始。
- 迁移脚本必须幂等，支持试跑、分批执行、回滚和差异报告；迁移实现计入 V1.1 排期，字段预留和数据采集计入 V1。
- 迁移失败不得删除或锁定历史数据，免费核心闭环不依赖迁移成功才能继续使用。

## 十一、商业化与盈利方案

商业化不改变产品定位。基础闭环“选菜 -> 计划 -> 核对冰箱 -> 生成清单 -> 采购 -> 做饭 -> 基础分享”长期免费；付费购买的是更大的家庭容量、更高的录入效率、更长的计划能力和更好的家庭记忆输出，不能通过削弱免费体验制造付费动机。

参考方案只借鉴“权益对比、积分账本、任务入口”的信息结构，不照搬每日签到、积分转赠、偷菜、随机点菜扣费、高频激励广告等机制。这些机制与家庭协作目标无关，容易制造虚假活跃和付费焦虑。

### 11.1 收入结构与上线顺序

首要收入来自个人版和共享版订阅，次要收入来自有明确成本或增值价值的单次服务；品牌合作和实物履约只能在用户规模与合规能力成熟后尝试。

| 收入层 | 产品形态 | 上线建议 | 边界 |
| --- | --- | --- | --- |
| 核心收入 | `个人 Plus` 用户订阅 | V1.1 | 绑定购买人，只提升个人录入、模板和输出效率，不给所在餐厅其他成员共享 |
| 核心收入 | `共享 Plus` 餐厅订阅 | V1.1 | 面向 2 人及以上餐厅，由主理人开通，同一餐厅有效成员共享权益 |
| 补充收入 | 图片/长图识别、高清卡片、精装 PDF、年度报告等单次服务 | V1.1 先开放最小闭环，V1.2 扩展 | 可使用套餐额度或饭票，不影响基础流程 |
| 后续收入 | 节日菜谱专题、品牌联合模板、实体菜谱册打印 | V2 以后 | 明确标注商业合作，不使用私人冰箱、过敏和家庭行为做定向出售 |
| 暂不采用 | 开屏广告、核心流程插屏、UGC 付费分成、积分转赠/提现 | 不进入当前路线 | 避免破坏信任并降低支付、税务和内容版权复杂度 |

V1 只预留权益、用量和支付数据结构，不展示不可购买的会员入口。V1.1 上线个人版和共享版时，饭票必须同时至少具备一个真实获得入口、一个真实消耗入口和一条可验证的会员升级路径，不能先发放一批无处使用的积分。

### 11.2 个人 Plus 与共享 Plus

`个人 Plus` 按用户订阅，适合独自使用或只希望提升自己效率的成员；购买人可以在自己有写权限的任一餐厅使用个人识别、模板和导出额度，但不能解锁该餐厅的共享计划、共享空间、成员扩容或家庭统计。

`共享 Plus` 按餐厅订阅，面向含主理人在内至少 2 名有效成员的餐厅，覆盖家人、朋友、室友、同事等共同用餐关系。正式套餐名称统一使用“共享版”，“搭伙”等词只作为运营文案。只有主理人可以开通、续费、从个人版升级和申请退款，权益由该餐厅当前有效成员共享。

个人 Plus 用户邀请成员后不会自动升级或扣费。餐厅进入多人协作状态，但个人权益仍只属于购买者；新成员只使用免费权益。主理人主动升级共享 Plus 后，个人版剩余价值按升级规则抵扣，共享权益才向餐厅成员开放。

建议首发价先按“个人版约为共享版的 50% 至 65%”灰度：个人版可测试 `4.9 元/月、39 元/年`，共享版可测试 `9.9 元/月、78 元/年`。两份个人版价格应与一份共享版接近，让 2 人及以上自然选择共享权益，而不是通过功能阉割强迫升级。价格、试用、活动、饭票换购和渠道折扣必须通过商品版本配置，不能写死在客户端。不提供永久会员，因为图片存储、内容安全、识别和报告生成都有持续成本。

建议首发权益如下，具体数值在灰度前结合真实人数、存储和识别成本再次确认：

| 权益 | 免费版 | 个人 Plus | 共享 Plus |
| --- | --- | --- | --- |
| 核心用餐闭环 | 完整可用 | 完整可用 | 完整可用 |
| 权益作用域 | 免费餐厅基础能力 | 仅购买用户 | 目标餐厅全部有效成员 |
| 餐厅成员 | 主理人 + 3 名成员 | 不扩成员 | 建议主理人 + 7 名成员，可后台配置 |
| 每人创建/加入餐厅 | 创建 1 个、加入其他 3 个 | 保持一致 | V1.1 保持一致，不用多餐厅制造升级压力 |
| 个人草稿图片空间 | 建议 200 MB/用户 | 建议 2 GB/用户 | 仍按成员各自个人权益 |
| 餐厅共享图片空间 | 建议 500 MB/餐厅 | 不扩共享空间 | 建议 5 GB/餐厅 |
| 共享计划范围 | 下一餐与基础 7 天 | 不扩共享计划 | 30 天计划与计划模板 |
| 菜谱与购物清单 | 不限基础条目 | 不限基础条目 | 不限基础条目 |
| 图片/长图识别 | 新用户体验额度或饭票兑换 | 购买人每月个人额度 | 餐厅每月共享额度，成员均可使用 |
| 饭搭子卡 | 基础模板与标准清晰度 | 购买人的精选模板与高清额度 | 全体成员共享模板与高清额度 |
| 数据统计 | 基础历史和评价 | 个人创建、掌勺和输出回顾 | 餐厅口味、掌勺、月度/年度回顾 |
| 数据导出 | 原始数据基础导出免费 | 购买人的精装输出额度 | 餐厅共享精装 PDF/打印版额度 |
| 支持 | 普通反馈 | 个人优先反馈 | 餐厅优先反馈，不承诺固定人工在线时长 |

个人额度和餐厅共享额度按自然月或订阅周期重置，不结转、不折现。用户同时拥有个人 Plus 并处于共享 Plus 餐厅时，功能取并集、额度分别记账：默认使用共享额度，但确认页允许切换并记忆该用户在当前餐厅的上次选择；共享额度不足时再提示个人额度或饭票。同一次操作只能消耗一个完整来源，个人额度不能被其他成员使用。

批量任务必须由一个来源覆盖整批所需额度，共享额度不足时不能部分扣共享、部分扣个人。成员上限、30 天计划、共享空间和餐厅统计只看共享 Plus，不与个人 Plus 叠加。

### 11.3 到期与降级

会员到期不得删除、隐藏或篡改用户已有数据：

- 个人版到期只收回该用户的个人额度、模板使用权和个人空间增量，不改变其所在餐厅其他成员的权益。
- 共享版到期后，餐厅恢复免费共享权益；成员各自仍有效的个人版继续可用，但不会自动转换成餐厅共享权益。
- 个人或餐厅图片空间超过对应免费额度时，已有图片继续可读，暂停该作用域的新上传和替换，直至续费或清理到限额以下。
- 已创建的远期计划继续可查看、完成和取消；到期后不能新建或扩展超出免费计划窗口的内容。
- 已生成的高清卡片、PDF 和年度报告永久保留访问能力，不因到期加水印或降清晰度。
- 高级模板生成的既有内容保持原样，但不能继续新建需要会员权益的内容。
- 餐厅成员超过免费上限时提供 30 天宽限期。宽限期后由主理人选择保留“主理人 + 3 名活跃成员”，其余成员转为只读，不自动移除、不丢失其历史贡献；续费或恢复名额后可重新激活。
- 餐厅从多人降为 1 人时，协作状态自动变为 PERSONAL，但共享 Plus 继续有效至到期；不自动折算、降级或退款，到期续费时推荐个人 Plus。
- 到期任务和请求同时发生时，以服务端权益有效时间和事务结果为准；客户端缓存不得延长权益。

到期前 7 天、前 1 天和到期后首次进入时可以提醒，但不得用连续弹窗阻断下一餐、购物清单或已有数据访问。

### 11.4 饭票积分

`饭票`是个人级应用内积分，不是餐厅共享余额。没有个人 Plus 或共享 Plus 的成员，只要是当前餐厅有效成员、具备对应写权限且饭票充足，也可以购买图片识别等单次能力。饭票只能购买能力，不能绕过餐厅权限；产物保存到餐厅后归餐厅并占用餐厅空间。饭票不得转赠、提现、兑换现金或用于用户之间交易。

饭票分为充值饭票和赠送饭票两个子余额：

- 赠送饭票可以设置有效期，规则变更不追溯已结算记录，到期时间必须在领取前明示。
- 充值饭票是否开放以及有效期规则，必须在微信支付与虚拟权益合规评审后确定；V1.1 可先用“直接购买单次服务包”替代充值。
- 消耗时优先使用最早到期的赠送饭票，再使用充值饭票；退款时按原支付来源逆向返还。
- 所有余额变化只通过不可变账本发生，钱包余额是账本汇总后的缓存，不允许运营直接改余额而不留记录。

#### 使用饭票升级会员

饭票升级提供两种明确路径：

1. **兑换固定会员时长**：用户可以用已结算饭票兑换 7 天或 30 天个人版；拥有至少 2 名有效成员的餐厅，可由主理人兑换固定时长共享版。兑换权益到期即结束，不自动续费。
2. **个人版补差升级共享版**：个人版有效期内，当用户是目标餐厅主理人且餐厅至少 2 人时，可升级为同到期日的共享版。服务端按购买时商品版本、剩余完整天数和目标升级规则计算补差，未使用的个人版价值先抵扣，剩余部分可由饭票全部或部分支付，仍不足时再支付现金。

升级规则必须满足：

- 只有 `settled` 饭票可使用，pending 奖励不能提前消费。
- 饭票会员价和补差抵扣规则独立配置，不向用户承诺通用“饭票兑人民币”汇率。
- 个人版转共享版成功后，原个人订阅状态变为 `converted`，相同剩余周期不再重复发放个人额度；共享版立即生效并沿用原到期日。
- 用户可以选择本次使用多少饭票，确认页必须显示个人版剩余价值、饭票抵扣、现金补差、目标餐厅和新到期时间，并明确说明转换后个人权益在其他餐厅也不再继续使用。
- 全饭票支付仍创建金额为零的升级订单、会员升级记录和积分账目，不能直接修改订阅字段。
- 升级先冻结饭票；现金支付和共享权益切换成功后再结算，支付失败、超时或付款人/餐厅/目标资格失效时完整释放；合法下单后仅成员数下降不撤销支付意图。
- 已生效升级不能把饭票部分兑换为现金。符合退款规则并整体撤销时，现金按实付退回，饭票按原充值/赠送类型退回；已过期赠送饭票按退款规则给予短期可用期，不制造立即过期余额。
- 餐厅后来降为 1 人不追回已生效共享版；到期续费时不满足 2 人条件则引导改用个人版。

#### 单次能力与持久权益

| 类型 | 示例 | 可购买者 | 支付方式 | 产物/权益归属 |
| --- | --- | --- | --- | --- |
| 个人单次能力 | 个人回顾、个人导出 | 用户本人 | 个人额度、饭票或现金 | 个人空间 |
| 餐厅单次能力 | 图片识别、高清卡片、精装 PDF | 具备对应写权限的有效成员 | 共享额度、个人额度或本人饭票 | 保存到餐厅时归餐厅并占餐厅空间 |

个人年度回顾只能由用户本人生成并保存到个人空间。餐厅年度报告只允许主理人或管理员生成，保存到餐厅空间，只包含该角色有权查看的餐厅聚合数据，不展示其他成员的个人偏好明细。

餐厅单次任务开始前检查成员、业务权限、额度和目标空间，冻结选定来源；落库前再次校验权限。任务失败、空间不足或成员权限失效时释放冻结额度或饭票。任务成功并保存到餐厅后，成员退出或个人会员到期不删除产物；管理员后续主动删除已交付产物不自动退还饭票。

### 11.5 订单、权益与并发

付费和积分链路必须遵守以下工程约束：

1. 客户端先创建服务端订单，订单保存商品名称、权益、价格、目标餐厅和资格快照；共享版下单时校验主理人、成员数和餐厅状态，客户端金额不作为结算依据。
2. 下单请求携带 `operationId`，同一用户、商品和业务意图的重试返回原订单，不能重复创建或重复扣款。
3. 支付回调验签后按渠道交易号幂等处理，在同一事务中把订单写为 `PAID_PENDING_GRANT` 并创建 OutboxEvent；权益授予成功后转为 `PAID`。重复回调和 Outbox 重试不重复延长会员。
4. 饭票领取、冻结、结算、消费、过期和退款都写 `PointLedger`，业务对象与操作标识建立唯一约束。
5. 需要等待有效性的奖励先写 `pending RewardClaim`，到期后由任务重新检查条件再结算；条件失效则取消，不采用“先发再强行扣回”造成负余额。
6. 接近到期时接受成员邀请，必须锁定餐厅和当前权益后重新计算有效成员上限，避免并发突破限制。
7. 退款不删除餐厅数据。会员退款后撤销尚未使用的未来权益；已消费的单次服务按平台公示规则判断是否可退，并保留完整订单、退款和人工操作审计。
8. 每日对支付渠道订单、PaymentOrder、权益授予和积分账本做自动对账，差异进入运营队列，禁止脚本直接补余额而不生成纠正账目。
9. 图片识别、PDF 等异步任务先冻结套餐额度或饭票；任务成功后结算，最终失败或取消时释放。权益在任务受理时有效即可完成该任务，到期不应中断已经合法受理的生成过程。
10. 个人转共享的混合支付升级必须锁定个人订阅、目标餐厅和饭票钱包；现金支付成功后在一个可补偿流程中完成原订阅 converted、共享订阅 active、饭票结算和权益刷新，任一步失败都不得留下双会员或重复额度。

状态机使用单向、可审计流转：`PaymentOrder: created -> paying -> paid_pending_grant -> paid/closed -> refunding -> partially_refunded/refunded`，`MembershipSubscription: pending -> active -> grace -> expired/canceled/refunded/converted`，`RewardClaim: pending -> settled/canceled`。禁止从失败、converted 或退款终态直接改回成功；需要恢复时创建新的订单、订阅或纠正账目。

共享版订单创建后的短有效期内，成员数减少不撤销已经合法创建的支付意图，支付成功后仍可授予至原到期规则；如果回调时付款人已不是主理人、餐厅已解散或目标失效，则不授予权益并自动创建退款单。用户重新打开小程序时必须查询服务端订单并恢复 `PAID_PENDING_GRANT` 状态，不依赖原支付页面驻留。

#### 共享额度治理

- `sharedQuotaPolicy`提供 `ALL_WRITERS`、`ADMINS_ONLY`、`OWNER_ONLY` 三档，默认 `ALL_WRITERS`，只有主理人可以调整。
- 策略只决定谁能消费共享额度，不改变成员原有业务权限；无业务写权限的用户不能因为额度策略开放而执行操作。
- 策略变更递增 `policyVersion`并只影响之后的新预留；`UsageReservation`保存冻结时版本，已经冻结且业务权限仍有效的任务可以完成，落库时不因策略后来收紧而拒绝。
- 用户可以在确认页选择共享额度、个人额度或本人饭票，系统将“用户 + 餐厅 + 能力”的上次选择保存到服务端 `UserRestaurantPreference`，跨设备同步；本地缓存只作弱网兜底，不得在额度不足时静默改扣其他来源。
- 共享额度、个人额度和饭票统一采用 `RESERVED -> SETTLED/RELEASED`；批量任务一次冻结整批所需额度，同一 operationId 重试返回原结果。
- 每次消费记录使用人、餐厅、能力、来源、数量、targetScope 和产物；主理人可查看餐厅共享额度明细，不能查看成员个人饭票余额。
- 共享额度每个周期最多发送一次 20% 提醒和一次耗尽提醒，应用内消息为主，订阅消息为辅，不自动续费或扣除主理人饭票。
- 空间任务先预留预计字节，完成后按实际大小结算；明确以餐厅为目标的任务不能自动转个人保存或借用个人空间。

#### 共享权益、付款人和退出

- 共享 Plus 的使用权属于目标餐厅，支付订单和退款资金归原付款人；普通成员退出或被移除不影响餐厅共享权益。
- 主理人不能直接退出形成无主餐厅，必须先转让主理人或解散餐厅。
- 新主理人必须没有其他自有餐厅；原主理人转为普通成员时还要校验其“最多加入其他 3 个餐厅”上限，整个转让在单一事务中完成。
- 转让时如果存在有效共享 Plus，必须选择“带权益转让”或“先处理退款再转让”。带权益转让时权益继续留在餐厅至到期，新主理人负责后续续费，退出本身不触发退款；先退款时按公示规则处理并原路退给原付款人，权益终止或降级后再完成转让。
- 转让后若历史订单退款会影响当前餐厅权益，必须由原付款人与当前主理人共同确认；不承诺无条件按剩余天数退款。
- 同一餐厅重复购买共享 Plus 只从 `max(当前时间, 当前到期时间)`顺延，不叠加成员上限、共享空间或月度额度；累计有效期最多到未来 24 个月，超过上限时不创建订单。
- 不同餐厅的共享 Plus 在 V1.1 不自动合并。跨餐厅会员价值转移与菜谱、历史、冰箱、成员迁移是两个独立流程，后续确有需求时再建设双主理人确认和剩余价值转换。

### 11.7 商业化验收标准

- 免费用户不付费也能完成选菜、计划、冰箱匹配、生成清单、购物、做饭和基础分享。
- 个人版只向购买用户授予个人额度，在同一餐厅的其他成员不能读取或消费；共享版只需餐厅一份有效订阅，全部有效成员按共享额度策略使用权益。
- 只有含主理人在内至少 2 名有效成员的餐厅能新开或续费共享版；成员降为 1 人时既有共享版持续至到期，不被中途追回。
- 用户在共享版餐厅执行增值能力时一次只选择共享额度、个人额度或本人饭票中的一个来源；默认与记忆来源均可在确认前切换，不静默改扣。
- `ALL_WRITERS/ADMINS_ONLY/OWNER_ONLY` 三档策略能正确限制共享额度使用，但不能放宽菜谱、报告等业务权限。
- 主理人调整共享额度策略后，只影响新任务；调整前已成功冻结额度且冻结时权限有效的任务可以完成，`policyVersion` 和权限快照可追溯。
- 共享额度只剩 1 次时，两名成员并发请求只有一人冻结成功；失败者选择其他来源，任务失败后额度完整释放。
- 批量任务不能拆分消耗多个来源；需要 5 次而共享只剩 2 次时，必须整批切换个人额度或饭票。
- 无个人或共享会员的有效成员可以使用自己的饭票购买单次能力，但只读、被移除或无写权限成员不能付费绕过权限。
- 餐厅资源只占用餐厅空间，个人资源只占用个人空间；共享空间不足时不会自动借用成员个人空间。
- 使用个人额度或饭票生成并保存到餐厅的产物归餐厅，用户退出或个人会员到期后仍保留；执行前明确提示目标空间。
- 共享空间、成员扩容、共享额度包和共享 Plus 只有主理人可以使用自己的饭票或现金购买。
- 个人年度回顾只能由本人生成到个人空间；餐厅年度报告只能由主理人或管理员生成到餐厅空间。
- 同一支付回调重复 10 次只产生一次订单状态变化和一次权益授予。
- 支付成功但回调延迟时，用户关闭并重新打开小程序后可以从服务端恢复订单状态；订单处于 `PAID_PENDING_GRANT` 时显示处理中，不诱导用户重复支付。
- 支付回调已成功但权益授予暂时失败时，订单保持 `PAID_PENDING_GRANT`，Outbox 重试最终只授予一次；达到重试上限后进入对账/运营队列，不把订单误标为未支付。
- 共享 Plus 下单时资格有效、支付前成员数降为 1 人时，原短有效期订单仍可正常授予；回调时付款人已非主理人、餐厅已解散或目标失效时不授予并自动创建退款单。
- 用户支付成功后立即申请退款且权益尚未使用时，按公示规则原路处理并保留订单、退款和权益撤销审计，不直接删除成功支付记录。
- 同餐厅续费从 `max(当前时间, 当前到期时间)`顺延，最多延长至未来 24 个月；超过上限时下单即被阻止，不产生待支付订单。
- 同一饭票消费请求弱网重试不重复扣除，余额不足时不生成付费产物。
- 会员额度和饭票不能在同一次操作中重复消耗，用户在执行前能看见本次实际成本。
- “用户 + 餐厅 + 能力”的额度来源偏好保存在服务端，同一用户跨设备保持一致；本地缓存失效或弱网时只回退默认展示，不据此直接扣费。
- 会员到期、续费和多人同时接受邀请发生竞争时，有效成员数不超过事务内权益上限，续费不会重复累计时长。
- 个人版补差升级共享版后，原订阅只出现一次 converted、目标餐厅只出现一份共享订阅；弱网重试不会重复扣饭票或重复创建共享额度。
- 全饭票兑换和现金加饭票升级都生成可对账升级订单，支付失败、付款人/餐厅/目标资格失效或权益切换失败时释放冻结饭票并保持原个人版有效；合法下单后的单纯人数下降不触发失败。
- 会员到期和退款不会删除图片、计划、成员贡献和已生成产物；超限状态按只读或暂停新增规则降级。
- 分享奖励在观察期内显示 pending，接收餐厅短期删除后不结算；已结算记录有完整业务依据。
- 每个 PublicRecipe 只获得一次 normal 晋级奖励，发布新版和反复下架不能重复领取。
- 基础数据导出免费，高级排版失败时不扣饭票或自动原路退回。
- 异步增值任务最终失败时，冻结的会员额度或饭票完整释放；回调和补偿重试不会生成第二份账目。
- 对账任务能发现“渠道已支付但未授予权益”和“已授予权益但无成功支付”两类差异，并支持有审计的纠正处理。
- 主理人有有效共享 Plus 时不能直接退出；带权益转让后订阅留在餐厅，普通成员退出不影响共享权益，同餐厅续费只延长时间而不叠加容量。
- 新主理人已有自有餐厅或原主理人转成员后会超过加入上限时，转让事务失败且角色、订阅、付款人与成员关系均不产生部分变化。

### 11.8 商业化指标与止损线

商业化先观察“价值是否被认可”，不能用广告曝光或积分发放量掩盖真实留存：

- 免费用户到个人 Plus、2 人以上餐厅到共享 Plus 的转化率，以及个人转共享升级率、饭票升级占比、年卡占比、续费率和退款率。
- 付费餐厅的 4 周计划完成率与免费餐厅的差异，确认付费来自长期价值而非一次冲动。
- 每个个人付费用户和付费餐厅的月均收入、图片存储成本、识别/生成成本、支付渠道成本和毛利。
- 会员月度额度使用率、超额饭票消费率，以及因额度提示放弃操作的比例。
- 共享额度按角色消费分布、原子冻结竞争失败率、任务失败释放率、低额度通知打开率和共享额度策略分布。
- 饭票获得/消耗比、30 天未消耗余额占比、pending 奖励结算率和异常任务拦截率。
- 到期后 30 天续费率、超限成员选择率、因降级产生的投诉和数据导出率。

若某项增值能力的直接成本长期接近或超过实际收入，优先调整额度、批处理和供应商成本，不得转而限制基础闭环。若付费弹窗显著降低计划确认或购物完成率，应立即降低触发频次并回查入口设计。

## 十四、V1 验收标准

### 14.1 核心业务

- 新用户能在 3 分钟内创建餐厅并发出邀请。
- 同一用户不能创建第 2 个餐厅，也不能加入第 4 个其他餐厅。
- 成员通过邀请进入正确餐厅，单餐厅超过免费成员上限时无法继续加入。
- 任意成员都能创建自己的菜谱并选择加入哪个有权限的餐厅。
- 用户能在菜谱大厅浏览系统和公共菜谱，按菜品概念查看其他做法，并把固定版本加入自己的餐厅。
- 已加入当前餐厅的来源版本显示“已拥有”，重复点击不会新增餐厅菜谱。
- 保存自建菜谱时，精确重复、同概念不同做法和相似做法得到不同提示，相似内容不会被自动合并。
- 管理员能发起点菜；成员从统一“我想吃”入口在 30 秒内完成选择和可选备注。
- 有征集时“我想吃”更新成员自己的回应；无征集时进入想吃池，不能直接修改已确认计划。
- 管理员能从点菜结果生成计划，并在两步内确认为下一餐。
- 计划可以指定掌勺人或由成员点击“我来做”，同时只有一位有效掌勺人。
- 用户能按餐次和人数随机一桌，候选不足时返回柔性结果，锁定菜品后只重摇未锁定部分。
- 菜谱和计划可以分享给非家庭用户，对方能预览并导入。
- 同一分享重复导入不会生成重复数据。
- 无食材菜谱仍能点菜和计划；点击缺口时可以匹配系统参考、点选主要食材或手动加清单。
- 一份计划部分菜谱可计算时，返回部分缺口并明确显示计算覆盖数。
- 用户能用“有 / 不多 / 用完”记录冰箱，精确数量不是主流程必填。
- 推荐结果能区分“现在能做、确认一下就能做、还差一点”，并显示匹配依据。
- 用户选择菜谱和人数后，能看到“已有、需确认、需要购买”三类食材。
- 缺少食材能一键加入购物清单，同名同单位食材不会重复堆叠。
- 超市购物模式可点击整行快速勾选，已购项目不会遮挡未购项目。
- 结束购物时，用户可以选择把已购物品批量加入当前餐厅冰箱。
- 未购项可以原子迁移到下次清单、标记不需要或确认为家里已有，不能直接写入冰箱。
- 完成计划后可非强制生成饭搭子卡，无照片和无菜谱图时也有稳定的菜名字卡降级。
- 所有备注都附着于业务对象，系统不存在发送纯文本聊天消息的入口。

### 14.2 权限与安全

- 成员不能确认餐厅下一餐或编辑他人的餐厅菜谱。
- 管理员不能转让主理人或解散家庭。
- 用户不能通过修改请求参数访问其他餐厅的菜谱、冰箱和购物清单。
- 被移除成员立即失去餐厅数据访问权限，但保留自己的个人草稿。
- 过期或失效的分享标识不能继续导入内容。
- 饭搭子卡只包含用户确认公开的白名单字段，不包含冰箱、忌口、过敏和内部主键。
- 分享预览可以在未完善资料时只读打开，收藏、导入等写操作必须建立可信身份。
- 私人餐厅菜谱不能通过全局搜索、公共相似指纹或采用统计被其他餐厅发现。
- 公共版本只能读取脱敏白名单字段，不能通过来源引用回查私人备注和家庭成员数据。

### 14.3 体验与稳定性

- 无图片菜谱也能正常展示，且不会破坏列表布局。
- 首页始终有明确的下一步动作，不出现无法理解的空白状态。
- 点菜、确认和推荐等关键操作有清晰成功状态，重复点击不会产生重复计划。
- 订阅消息未授权或发送失败时，不影响应用内待办与动态。
- 首次进入不强弹订阅授权；主理人和成员分别在能理解提醒价值的动作后授权，任何用户不能替别人授权。
- 冰箱数量未知或单位不可换算时必须提示用户确认，不能给出虚假精确缺口。
- 多人同时勾选购物项时，最终状态一致且能看到最后操作人。
- 库存可信度同时使用文字和状态图标，不只依赖颜色传达。
- 远端购物更新不能在用户点击瞬间重排列表；弱网操作有明确待同步和失败状态。
- 关闭并重新打开小程序后，未同步购物操作仍保留并可自动或手动重试；服务端幂等避免重复写入。
- 某成员调整购物分类顺序不会改变其他成员的列表顺序。
- 自动化无法完成时必须提供模板补全、主要食材点选或手动清单兜底，不能只显示“无法计算”。

### 14.4 并发与幂等

- 同一购物项的重复添加和弱网重试不会生成重复条目或重复来源。
- 同一清单只能成功结束一次，重复请求返回相同完成结果。
- 点菜提交与征集关闭竞争时，以服务端事务结果为准，未计入选择有明确提示。
- 计划版本过期时不能覆盖他人修改，客户端能展示最新版本和操作人。
- 多人同时接受邀请不会突破用户加入上限或餐厅成员上限。
- 同一分享快照重复导入到同一餐厅只生成一份副本。
- 同一系统或公共来源版本重复导入同一餐厅只生成一条 RestaurantRecipe。
- 两名成员同时编辑菜谱时，基于旧版本的提交不能覆盖最新版本，用户草稿仍可保留。

### 14.5 饭搭子卡

- 未记录实际用时，卡片不得展示“用了 XX 分钟”等推测内容。
- 分享后修改原计划，不会改变已经生成的分享快照。
- 分享人撤销 token 后新访问失效，但接收人此前合法导入的数据不被删除。
- 没有照片、成员头像或掌勺人时，卡片省略对应内容并保持完整布局，不补造信息。
- 家庭金句不填写时不出现输入阻断；填写后只有分享人明确确认并通过安全检查才进入公开卡片。
- 生成分享卡时文字和图片检查失败只移除或阻止风险字段，不影响餐食计划完成，也不进入公共菜谱曝光状态机。

### 14.6 菜谱版本与去重

- 100 个餐厅导入同一系统菜谱时，系统模板和内容版本各保持一份，只新增 100 条轻量餐厅入口。
- 其中一个餐厅修改食材或步骤时只新增一个家庭内容版本，其他餐厅不受影响。
- 修改本地菜名、备注、分类或展示信息不创建内容版本。
- `contentHash`包含标准食材、数值、单位、主要标记、步骤顺序和完整内容；不同单位不能产生相同精确哈希。
- MealPlanItem、公共版本和分享快照强制引用具体不可变版本，禁止引用可变餐厅入口作为内容来源。
- 系统发布新版本后，V1 已导入餐厅仍固定在原版本，不自动升级。
- 图片复用不绕过权限校验，未授权用户无法根据哈希或存储地址读取其他餐厅图片。
- 系统菜谱导入包含未确认食材或非法单位时失败，并给出具体行错误；用户待确认食材别名不会自动成为全局标准。
- 首批系统菜谱均有文字来源、授权方式和图片权利记录，缺少来源证明时不能发布为系统精选。
- 相似度阈值由服务端配置，上线前通过人工标注菜谱对测试集确认误报与漏报；阈值变化不触发自动合并。

### 14.7 菜谱大厅与公共模型占位

- V1 客户端不展示用户公共投稿、我的投稿、最新尝鲜和优秀推荐入口。
- Public 相关表、枚举和接口骨架保留，接口统一返回 503。
- V1 中所有公共版本 `exposureLevel` 保持 none，不进入任何公共列表。
- 系统推荐广场只能展示系统菜谱和系统运营确认内容。
- 后续开放优秀推荐前，必须补齐最低完整度、安全检查、举报、隐藏、恢复、发布限制和审计。

### 14.8 商业化预埋

- V1 数据库迁移包含 USER/RESTAURANT 双作用域的版本化权益、订阅转换、配额预留、逻辑存储归属、钱包账本、奖励领取、支付和退款对象，但所有付费能力使用关闭状态配置。
- 免费餐厅成员上限通过统一权益计算获得，不能在邀请、成员列表和后台任务中分别写死不同常量。
- 图片空间、识别次数、计划窗口和高清导出均能记录真实用量，V1 不因达到未来付费阈值阻止用户。
- 订单、饭票和权益接口默认不可由 V1 客户端调用，服务端仍执行鉴权和功能开关，不能只隐藏页面。
- 埋点分别统计用户级识别/导出需求与餐厅级成员、共享空间、计划窗口和餐厅统计需求，为个人版/共享版定价提供依据，但不采集菜谱正文、过敏等敏感内容用于营销画像。
- V1.1 迁移试跑能输出空间回填、异常归属、漏记引用和前后总量差异；V1 免费调用不回填为已用额度，V1.1 周期额度从零开始。

## 十五、上线后观察指标

**核心指标**：每周至少完成一份“已确认餐食计划”的活跃餐厅数。

**激活与决策**

- 新餐厅 24 小时内完成首次计划的比例。
- 餐厅邀请成功率和点菜征集参与率。
- “我想吃”意向被加入计划的比例。
- 随机结果加入计划的比例；不能只统计摇骰子次数。
- 每个活跃餐厅每周确认和完成的计划数。

**食材结构化与缺口能力**

- 系统菜谱结构化率，目标为 100%。
- 自建菜谱匹配系统模板的成功率。
- 餐食计划中可进行完整或部分计算的菜品覆盖率。
- 点击“看看缺什么”后成功得到完整、部分或手动清单的比例。
- 无食材菜谱通过参考模板或主要食材点选完成补全的比例。

不能用“自建菜谱结构化率低于 30%”作为关闭自动缺口的单一阈值。数据越完整，结果越精确；数据不足时逐级降级，并持续观察计划级可计算覆盖率和实际清单转化。

**库存可信度漏斗**

- 冰箱推荐曝光后触发库存确认的比例。
- “原本显示有，确认后变为用完”的库存纠错率。
- 库存确认后菜谱加入计划的比例。
- 缺货项加入购物清单的比例。
- 因库存不准离开推荐流程的比例。
- 购物结束后一键入库率。

单独的“冰箱匹配后加入购物清单转化率”不能证明库存机制有效，因为高转化也可能代表库存长期失真。需要结合纠错率、退出率和一键入库率判断。

**购物、并发与传播**

- 购物清单完成率、未购项迁移率和平均漏项回退次数。
- 弱网重试失败率、购物项重复合并率和多人状态冲突率。
- 饭搭子卡生成率、分享率、只读预览打开率和菜谱/计划导入率。
- 分享快照撤销率和隐私字段投诉数。

**菜谱大厅、版本与后续公共模型**

- 大厅浏览到加入餐厅、加入下一餐和生成购物清单的转化率。
- 系统来源的重复导入拦截率，以及餐厅内精确/同概念/相似提示后的选择分布。
- 公共接口 503 命中量，用于判断后续优秀推荐需求，不作为 V1 成功指标。
- 后续开放后再统计公共菜谱提交量、安全检查通过率、晋级率、举报率和申诉反馈量。
- 单个系统版本的餐厅引用数、家庭写时复制率和每个餐厅平均自定义版本数。

大厅曝光量和浏览量只用于分析发现效率，不能替代“加入餐厅、进入计划、实际完成”等真实使用指标。

不要把菜谱浏览量作为第一核心指标，因为产品价值在于形成家庭用餐决策，而不是制造内容消费时长。

## 十六、主要风险与处理

| 风险 | 处理方式 |
| --- | --- |
| 用户不愿意录入完整菜谱 | 菜名 + 分类即可保存；需要缺口时使用三级降级、相似模板和手动清单兜底 |
| 随机结果不好吃或不合理 | 过敏忌口硬排除，荤素汤柔性评分；候选不足直接返回最佳可行结果 |
| 家庭通知被误做成聊天 | 只允许结构化事项和 50 字附属备注，不允许独立发消息 |
| 微信订阅提醒受授权限制 | 应用内待处理为主，订阅消息失败不影响业务 |
| 成员和菜谱归属混乱 | 所有餐厅数据明确 restaurantId 和 createdBy，写入前要求用户确认当前餐厅 |
| 分享造成重复、内容变化或隐私泄露 | 使用不可变白名单快照、可撤销 token、导入副本和幂等校验 |
| 冰箱记录很快失真 | 使用有/不多/用完、分类可信周期和使用时确认，不要求用户定期逐项巡检 |
| 同一种食材写法不同 | 模糊搜索只给候选，最终绑定标准 ingredientId；无法匹配时保留自定义食材 |
| 单位无法可靠换算 | 只自动合并兼容单位，不兼容时并列展示并让用户确认 |
| 多人购物重复购买或列表误触 | 服务端幂等、实时状态、最后操作人；远端更新不在点击瞬间重排列表 |
| 多管理员覆盖计划 | 使用版本检查和事务确认，冲突时返回最新计划，不静默覆盖 |
| 饭搭子卡编造或泄露信息 | 文案只读取真实快照字段，分享前确认公开内容，无数据则省略 |
| 系统菜谱被大量完整复制 | 固定引用不可变来源版本，家庭修改时才写时复制，图片按 SHA-256 物理复用 |
| 同名菜谱让搜索和随机失效 | 使用 DishConcept 聚合展示和随机去重，餐厅内精确重复阻止、相似做法只提示 |
| 菜谱版本覆盖历史记录 | MealPlanItem、公共版本和分享快照强制引用 RecipeContentVersion |
| 私人菜谱通过指纹泄露 | 全局只检索系统和已公开内容，私人相似检测限制在当前餐厅 |
| 后续公共投稿出现违规和垃圾内容 | V1 先关闭入口；开放前补齐基础安全检查、频率限制、举报、隐藏、恢复和审计 |
| 后续公共热门被刷量操纵 | 开放后按合格餐厅去重，结合保留、计划使用、举报和异常关联，不公开固定晋级阈值 |
| 后续公共版本更新造成服务中断 | 当前版本继续服务，候选版本检查通过后再原子切换 |
| 会员被做成人为障碍 | 核心用餐闭环与基础数据导出免费，只对容量、效率和精美输出收费 |
| 会员到期导致数据或成员丢失 | 历史数据永久保留，超额图片暂停新增，超额成员宽限后转只读 |
| 个人权益误扩散为全餐厅权益 | 所有权益带 USER/RESTAURANT 作用域，服务端按操作者、目标餐厅和权益来源统一解析 |
| 会员额度和饭票重复扣费 | 确认页明确选择一个完整来源，服务端原子冻结并以 operationId 和产物建立唯一约束，不静默切换或重复扣费 |
| 餐厅资源借用个人空间 | 持久资源按作用域独立计量，餐厅产物只能进入餐厅空间，空间不足不静默转个人 |
| 单个成员耗尽共享额度 | 主理人配置三档使用策略，消费明细可追溯，低额度频控提醒，批量任务整批预留 |
| 共享额度并发超扣 | 使用原子冻结、结算和释放，operationId 幂等，任务与空间均先预留再落库 |
| 付费绕过餐厅权限 | 执行前与落库前两次校验成员和业务权限，失效时释放额度或饭票 |
| 饭票升级被价格差或并发套利 | 补差使用版本化规则与剩余完整天数，锁定订阅/餐厅/钱包，原个人版转换后不重复发额度 |
| 共享版下单后资格发生变化 | 下单保存短期资格快照；成员数下降不撤销合法支付意图，回调时付款人已非主理人、餐厅解散或目标失效则不授予并自动退款 |
| 付款人退出后退款伤害餐厅 | 主理人必须先转让或解散；转让明确共享权益处置，影响现餐厅权益的历史退款需双方确认 |
| 支付回调重复、延迟或权益漏授 | 渠道交易号和 operationId 幂等，回调事务写入 PAID_PENDING_GRANT 与 Outbox，权益成功后再置 PAID，并通过重试和每日对账兜底 |
| 任务和分享奖励被刷 | 业务对象/餐厅/周期去重、pending 观察期、关系风险信号和人工审计组合处理 |
| 积分充值带来合规风险 | V1.1 先用赠送饭票和直接购买服务包，充值饭票经支付与虚拟权益评审后再开放 |
| 识别、存储成本超过收入 | 套餐额度可配置并持续核算单位成本，不通过限制基础流程转嫁成本 |
| 系统菜谱来源侵权或不可用 | 内容负责人维护结构化模板和授权证据，系统内容导入同时校验来源与图片权利 |
| 平台规则或资质判断过期 | 建立带依据、责任人和核验日期的合规矩阵，UGC 与支付发布前完成 P0 闸门检查 |
| V1.1 迁移造成历史数据受限 | V1 预留归属与用量字段，迁移幂等试跑并可回滚，免费核心不依赖迁移成功 |
| 首版功能过多导致延期 | 严格按 V1 清单验收，周计划增强、AI、精细库存和正式付费后置到 V1.1 以后 |

## 十七、已冻结的产品决策

本方案按以下已确认口径执行，原型和开发不得自行改回旧逻辑：

1. 每个用户最多创建 1 个餐厅，并最多加入其他人的 3 个餐厅。
2. 免费餐厅是“主理人 + 最多邀请 3 人”，总人数 4 人。
3. 所有冰箱和购物数据归属于餐厅，不是用户跨餐厅共用的一份库存。
4. 家庭动态不是聊天，备注上限统一为 50 字。
5. 成员侧统一使用“我想吃”；有征集时更新回应，无征集时进入想吃池。
6. 点菜结果由主理人或管理员最终确认，不自动采用票数最高项。
7. 导入菜谱在产品上逻辑独立，但工程上固定引用具体不可变来源版本；修改食材或步骤时写时复制，不与来源实时同步。
8. 所有人可以创建餐厅菜谱，但只有创建者、管理员和主理人可以编辑该菜谱。
9. 冰箱默认“有 / 不多 / 用完”，精确数量可选；`confidenceDays` 与 `expireAt` 独立，V1 不强制自动扣减库存。
10. 无食材菜谱仍可点菜和计划；缺口能力按完整计算、仅判断有无、参考补全/手动清单三级降级，并支持计划部分计算。
11. 食材模糊匹配只用于推荐候选，最终绑定标准 ingredientId；V1 不从全网抓取或自由编造食材组合。
12. 随机算法中，过敏和忌口是硬规则，荤素汤和菜品数量是软规则；V1 不做救急模式。
13. 购物、点菜、计划、掌勺人、成员邀请和分享导入必须有版本、幂等和事务保护。
14. 饭搭子卡列为 V1-P1，非强制生成，只使用真实字段和不可变分享快照。
15. V1 首页围绕“下一餐”设计，菜谱图片流不作为首屏主体验。
16. 菜谱采用“菜品概念、系统模板、餐厅入口、统一不可变内容版本”模型；MealPlanItem、公共版本和分享快照强制引用具体版本。
17. `contentHash`只判断完整内容精确一致，`similaritySignature`只提供当前餐厅内相似提示；相似内容不自动合并。
18. V1 菜谱大厅包含系统推荐广场和系统精选，只做发现、收藏、导入和分享，不开放用户公共投稿、关注、评论、私信和公开家庭动态。
19. 用户公开菜谱、候选不可变公共版本和优秀推荐后续启用；V1 只保留公共模型和接口骨架。
20. 公共曝光 low/normal/hot 分层、合格采用晋级、举报和运营处置均为后续能力；V1 中公共曝光保持 none。
21. 私人餐厅菜谱不能通过全局搜索、指纹或统计被其他餐厅发现；公共版本只包含用户确认的脱敏白名单内容。
22. 用户搜索词和自定义食材先进入私有候选与治理队列，未确认内容不得自动升级为全局标准食材或别名。
23. 订阅授权只在用户能理解价值的动作后请求，每位成员自行授权；拒绝后不使用服务号或短信自动兜底。
24. 购物分类顺序属于“用户 + 餐厅”偏好，不作为多人共享清单状态；弱网操作使用持久化本地队列和服务端幂等对账。
25. 家庭金句完全可选，只在分享人明确确认并通过安全检查后进入饭搭子卡。
26. 基础用餐闭环和基础数据导出长期免费，不为付费限制菜谱创建、随机、计划、冰箱、购物、基础分享或安全能力。
27. 正式会员名称为用户级 `个人 Plus` 和餐厅级 `共享 Plus`；“家庭版”不作为正式套餐名称，个人权益只属于购买人，共享权益服务目标餐厅。
28. 共享版面向含主理人在内 2 人及以上餐厅，只能由主理人开通、升级和续费；V1.1 仍维持每人创建 1 个、加入其他 3 个餐厅的上限。
29. 个人版用于个人空间、识别、模板和输出效率；共享版用于成员容量、计划范围、餐厅空间、共享额度和餐厅统计，不以基础菜谱条数作为付费墙，也不提供永久会员。
30. 会员到期不删除数据和既有产物；超额数据只读或暂停新增，共享版超额成员经 30 天宽限后转只读而非自动移除。
31. 饭票是个人级双余额积分，不属于餐厅资产，不转赠、不提现；核心流程不扣饭票，共享额度、个人额度和饭票不得在同一次操作重复消耗。
32. 已结算饭票可兑换固定时长个人版/共享版，也可抵扣个人版升级同到期日共享版的补差；升级成功后原个人订阅 converted，不重复发放同周期额度。
33. 饭票升级使用版本化会员兑换价和补差规则，不承诺通用人民币汇率；全饭票或混合支付都必须生成升级订单并支持冻结、失败释放和对账。
34. 不设置每日签到奖励；分享、邀请和后续公共菜谱奖励使用真实业务条件、唯一键与 pending 观察期，每个逻辑 PublicRecipe 的 normal 奖励只结算一次。
35. 不做开屏广告和核心流程插屏广告；未来激励广告只能由用户在独立任务入口主动选择，且不能成为完成核心流程的必要条件。
36. 支付、退款、订阅转换、权益、配额和饭票变动必须服务端验权、幂等、可对账并有不可变审计；支付回调先进入 PAID_PENDING_GRANT 并通过 Outbox 可靠授予权益，成功后再转为 PAID。V1 只预留模型和用量埋点，V1.1 同时上线可用权益与最小饭票闭环。
37. 餐厅协作状态与付费状态分离：1 名有效成员为 PERSONAL，2 人及以上为 SHARED；成员变化自动重算协作状态，但不自动购买、取消或退款会员。
38. 个人 Plus 用户邀请成员后，个人权益仍只属于本人，新成员只获免费权益；主理人可以保持个人版，也可以主动补差升级共享 Plus。
39. 共享 Plus 餐厅成员降为 1 人时，共享权益继续至到期，不自动折算、退款或降级；续费时引导选择个人 Plus。
40. 共享 Plus 使用权属于目标餐厅，支付订单和退款资金归原付款人；普通成员退出或被移除不影响共享权益，退出本身不触发退款。
41. 主理人不能直接退出形成无主餐厅，必须先转让或解散。存在有效共享 Plus 时，转让必须明确“带权益转让”或“先退款再转让”；影响当前餐厅权益的历史退款需要原付款人与当前主理人共同确认。
42. 同一餐厅重复购买共享 Plus 只顺延有效期，不叠加成员、空间和周期额度，累计有效期最多到未来 24 个月；不同餐厅的会员与业务数据在 V1.1 不自动合并，会员价值转移和数据迁移必须分开处理。
43. 商业化权益统一遵守“功能取并集、额度分账、资源按归属、权限先于付费、个人权益不外溢”；个人或共享任一来源包含能力时本人可用，但个人权益不开放给其他成员。
44. 个人 Plus 与共享 Plus 同时生效时，同一操作只消耗共享额度、个人额度或饭票中的一个完整来源；默认共享但允许切换并按用户和餐厅记忆，批量任务不得拆分来源。成员上限、30 天计划、共享空间和餐厅统计只看共享 Plus。
45. 任何对当前餐厅具有对应写权限的有效成员，都可以使用自己的饭票购买单次能力；饭票不能绕过成员、角色和业务权限。保存到餐厅的产物归餐厅，成员退出后继续保留，任务失败或权限失效时释放冻结饭票。
46. 持久资源不跨作用域借用：餐厅菜谱图片、餐厅报告及保存到餐厅的生成产物只能占用餐厅空间；个人草稿、个人回顾和个人导出文件占用个人空间。目标作用域在执行前明确，餐厅空间不足时不能静默转个人空间。
47. 共享额度消费权限分为 ALL_WRITERS（默认）、ADMINS_ONLY、OWNER_ONLY，由主理人配置。共享额度采用原子冻结、结算和释放，批量任务一次预留整批额度，空间先预留预计大小。策略变更递增 policyVersion，只影响新预留；已成功冻结且冻结时权限有效的任务可以完成。每次消费记录使用人、餐厅、能力、来源、数量和产物；20% 与耗尽提醒每周期各最多一次，不自动续费或扣饭票。
48. 共享空间、成员扩容、共享 Plus 和共享额度包等持久餐厅权益只能由主理人使用自己的饭票或现金购买。个人年度回顾由本人生成并保存到个人空间；餐厅年度报告仅主理人和管理员可生成，保存到餐厅空间且不展示其他成员的个人偏好明细。

## 十八、落地顺序

现在最合适的执行顺序是：

1. 以第十七节 48 个已冻结口径作为原型、数据库和接口评审基线。
2. 按首页/我想吃、我的菜谱/系统推荐广场、下一餐、食材缺口、购物模式、冰箱可信度、饭搭子卡/分享预览、餐厅管理的顺序输出原型。
3. 同步冻结标准食材与别名、菜品概念、统一版本、可信度配置、公共模型占位、权限矩阵、幂等键、分享快照、USER/RESTAURANT 权益、额度/空间预留、订阅转换和用量字段。
4. 产品或内容负责人立即准备 100 至 200 道结构完整、来源可追溯的系统菜谱；开发负责导入模板、授权字段和校验工具，不能只准备图片和菜名。
5. 产品、运营和合规负责人建立小程序类目、后续 UGC、安全接口、支付、饭票、退款、协议和内容授权矩阵；V1 不因公共投稿阻塞，但必须确认系统内容授权。
6. V1 同步记录逻辑空间和成本型能力需求，V1.1 开发幂等迁移、试跑、回滚和差异报告，历史业务数据不复制。
7. 按 P0 先于 P1 的顺序执行 10 周 V1 排期，并在技术评审后重新确认人天。
8. 找 10 至 20 个真实多人餐厅进行两周灰度，覆盖家人、朋友和室友，重点观察系统推荐导入、版本复用、想吃采纳、库存纠错、购物同步和饭搭子卡传播。
9. 用 V1 真实成员分布、个人/共享空间、计划跨度和识别成本确定个人版与共享版权益、价差和饭票兑换价，不能仅按竞品截图定价。
10. 根据真实使用数据决定先增强系统版本升级、厨房整理、公共推荐、口味记忆、卡片模板还是精细库存。

首版成功的判断标准不是“有多少浏览量”，而是用户能否自然地完成两条闭环：

- 共同用餐：**我想吃 -> 共同选择 -> 确认下一餐 -> 核对冰箱 -> 生成清单 -> 完成采购 -> 做饭 -> 留下并分享记忆**。
- 菜谱流转：**大厅发现或餐厅创建 -> 固定版本加入餐厅 -> 实际进入计划 -> 有权内容公开分享 -> 真实餐厅采用 -> 获得更高曝光**。
