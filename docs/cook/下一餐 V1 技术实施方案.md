# 下一餐 V1 技术实施方案

> **历史状态（2026-07-20）**：本文是 v0.1 技术实施来源，保留用于追溯，不再单独指导饭搭子生命周期、原空间、迁入迁出、饭局、口味、会员和空间实现。当前产品规则见 `../dining-group.md`、`../configuration.md` 与 `../plans/personal-data-refactor-plan.md`；新实现不得覆盖 v0.1 历史材料。

本文档记录 v0.1 当时锁定的技术边界，不再作为当前唯一依据。

## 一、技术栈（已冻结）

| 层级 | 选型 | 版本/备注 |
|---|---|---|

## 二、工程结构（已冻结）

```text
apps/
  client/          # uni-app 小程序（V1 首发目标：mp-weixin）
  admin/           # Vue 3 + Element Plus 运营后台
  api/             # NestJS 后端服务
  worker/          # 独立 Worker：安全检查、Outbox 消费（V1 进程不启动）

packages/
  api-client/      # OpenAPI 生成类型安全客户端
  domain/          # 纯 TS 业务实体、类型定义
  platform/        # 平台适配器接口（登录/支付/存储/分享）
  shared/          # 通用工具、常量

infra/
  docker-compose/  # 本地开发环境
  scripts/         # 数据迁移、导入工具
```

关键约束：

- 业务代码不直接调用 `wx.*`，统一通过 `packages/platform` 适配层。
- 前端与后端共享 `packages/domain` 类型定义。
- 后台管理独立部署，不与小程序共用前端资源。

## 四、核心领域模型（已冻结）

### 4.1 菜谱版本模型

```text
DishConcept（菜品概念）
  ↑
RecipeTemplate（系统模板）
  ↑
RecipeContentVersion（统一内容版本）  ←── contentHash，不可变
  ↑
RestaurantRecipe（餐厅入口）
  ├── sourceVersionId → 引用来源版本
  └── currentVersionId → 指向当前使用的版本
        ↑
（修改时创建新的 ContentVersion，原子切换 currentVersionId）
```

关键约束：

- `RecipeContentVersion` 统一存储所有类型的菜谱内容：系统模板、家庭修订、临时菜谱、公共菜谱。
- 其他表统一引用 `RecipeContentVersion.id`。
- 修改本地名称、备注、分类不创建新版本。
- 修改食材、步骤、用量时基于当前 `currentVersionId` 创建新版本并原子切换。
- `MealPlanItem` 强制引用 `RecipeContentVersion`，禁止引用 `RestaurantRecipe`。
- 系统模板升级不影响已导入餐厅。

### 4.2 公共菜谱状态机（V1 不运行）

```text
private 菜谱
    ↓ 用户提交（V1 不开放）
候选版本创建（safetyStatus=PENDING, exposureLevel=NONE）
    ↓ 机器检查（V1 不执行）
PASSED → LOW → NORMAL → HOT
REVIEW_REQUIRED → 人工队列
REJECTED → 拒绝公开
```

V1 行为：所有公共菜谱的 `exposureLevel` 永远为 `NONE`，不进入任何公共列表。V1 菜谱大厅只开放系统推荐广场；用户公共投稿、优秀推荐和曝光晋级后续再启用。

### 4.3 共享额度治理（V1 Reserved，不启用）

- 额度表已建，但 V1 不进行额度扣减。
- V1 所有用户按免费上限使用。
- V1.1 启用额度预留与结算。

### 4.4 冰箱库存语义（V1）

V1 不做批次库存。`FridgeItem` 表示餐厅内某个食材的最近已知状态，`expireAt` 表示最近一次确认的预计过期时间，不表示每批库存的独立保质期。

关键约束清单：

| 约束 | 说明 |
|---|---|
| DishConcept 全局唯一 | `scope=GLOBAL` 时 `canonicalName` 唯一 |
| DishConcept 餐厅私有唯一 | `scope=RESTAURANT` 时 `(ownerRestaurantId, canonicalName)` 唯一 |

## 七、关键事务边界（已冻结）

### 7.1 写时复制

```text
BEGIN
  1. 查询 currentVersionId
  2. 客户端传入 baseVersionId
  3. 不一致 → 拒绝，返回最新
  4. 生成新 RecipeContentVersion
  5. 原子切换 currentVersionId
COMMIT
```

### 7.2 MealPlanItem 不可变

```text
BEGIN
  1. 用户选择菜谱加入计划
  2. 锁定 currentVersionId
  3. 创建 MealPlanItem，记录 recipeVersionId
  4. 后续菜谱修改不影响此引用
COMMIT
```

### 7.3 购物项幂等合并

```text
BEGIN
  1. 客户端传入 operationId
  2. IdempotencyRecord 去重
  3. 同一 listId + mergeGroupKey → 合并数量
  4. 不同 → 创建新项
  5. 记录 ShoppingItemSource
COMMIT
```

### 7.4 后台导入发布

```text
BEGIN
  1. 创建 ImportBatch（STAGING）
  2. 逐行写入 RecipeImportStaging + 校验
  3. 标记通过/失败
  4. 运营确认 → 原子发布：
     a. 创建/更新 DishConcept
     b. 创建 RecipeContentVersion
     c. 更新 RecipeTemplate.currentVersionId
     d. 标记 ImportBatch = PUBLISHED
  5. 失败回滚，不产生部分数据
COMMIT
```

## 十一、核心原则（最终确认）

- V1 不做商业化、不做公共提交、不做优秀推荐曝光晋级、不做独立 App。
- 表必须建、接口骨架必须写，避免 V1.1 数据迁移返工。
- 后台不是可选项，系统菜谱导入依赖它。
- 所有写操作带 `operationId` 和 `version`，保证幂等与并发安全。
- 版本一旦创建不可变，历史引用永久冻结。
- 业务代码不直接调 `wx.*`，平台差异通过适配层隔离。
